# CSM Portal Webapp

React + TypeScript + Vite frontend for the CSM portal, using the `@wso2/oxygen-ui` (MUI-based) design system, TanStack React Query for data fetching, and `react-router` v7 (the unified `react-router` package — **not** `react-router-dom`). See `README.md` for setup, `window.config` keys, and the `dev:local` local-gateway mode; this file covers code-organization and workflow conventions instead.

## Path aliases

Defined once in `vite.config.ts`, mirrored in `tsconfig.app.json`. Use them instead of relative imports beyond one level.

| `@assets` | `src/assets` |

A handful of narrower aliases (`@case-details*`, `@time-tracking`, `@deployments`, `@update-cards`) point at specific component subfolders inside individual features — a one-off pattern from a couple of features, not something to replicate for new ones.

## Code organization

Feature-based: each `src/features/<name>/` folder owns its own `api/` (React Query hooks), `components/`, `pages/`, `types/`, `utils/`. Tests are colocated as `<File>.test.tsx` next to the file under test, not in a separate `__tests__` tree.

## Routing (`src/App.tsx`)

- Route page components are statically imported (eager), not `React.lazy`-loaded — deliberate, to ship as one JS bundle instead of one chunk per route. Per-route `React.lazy()` caused a real UX bug: navigating to a route not yet visited that session fetched a fresh chunk on the critical path, freezing the UI mid-navigation. See `index.html`'s boot loader (shown until the single bundle finishes loading) for the tradeoff this enables. One dynamic `import()` remains outside routing — the click-triggered PDF export in the Updates feature — since it's not on any navigation path and inlining it would grow the main bundle for a rarely-used feature.
- Declared with `react-router` v7's JSX `<Routes>`/`<Route>` API, not a data router (`createBrowserRouter`).
- Everything except `/401`/`/403`/`/404` sits under `<Route element={<AuthGuard />}>` → `<Route element={<FeatureRouteGuard />}>` (a runtime feature-flag/WIP gate keyed by `CSM_PORTAL_FEATURE_OVERRIDES`).
- Legacy paths (e.g. `/accounts`, `/projects`) are kept as `<Navigate>` redirects for backward compatibility rather than removed outright.

## Not-yet-entitled users (`AuthGuard.tsx`'s `AuthorizedAppShell`)

A signed-in caller whose `/users/me` call still comes back 401/403 after `useAuthApiClient`'s own retry/silent-refresh chain has had its chance (see that hook's own doc comments) is treated as "not entitled to this portal yet", not a transient auth hiccup. Unlike every other API call, `/users/me` (`useGetUsersMe.ts`) passes `skipSignInRedirect: true` — once the retry + silent-reauth + poll chain is exhausted with the 401/403 still standing, its own failure surfaces immediately instead of attempting the usual full-page sign-in redirect. That redirect assumes the browser is about to navigate away (which is why it's written to never resolve — nothing should render behind it mid-navigation), but that assumption breaks when `signIn()` has nothing left to fix and silently no-ops (the caller's IdP session is already fully valid — it's portal-level entitlement that's missing) — a real account in exactly this state was observed hanging forever behind that never-resolving promise, `/users/me` stuck "loading" indefinitely with no error and no redirect ever actually happening. `skipSignInRedirect` exists specifically so `/users/me`'s own gate always reaches a decisive answer.

While that check is still pending — not just once it comes back positive — `AuthorizedAppShell` suppresses the routed page entirely (`AppLayout`'s `children` vs. bare `<AppLayout />`, the same mechanic `AuthPendingShell` above already uses, and for the same reason: the routed page's own components fire their own API calls immediately on mount, e.g. a dashboard widget's config request, so mounting it before `/users/me` had settled meant a caller who was about to be found unauthorized could still see real response data — and use the sidebar to reach other real pages — during that window). A signed-in user only ever sees the routed page once we positively know they're allowed to; until then (and while genuinely not authorized) they see a loading state or `NoPortalAccessPage` respectively, both through `AppLayout` itself (not a bare `ErrorLayout`) via a new `minimalHeader` prop, so the real header/branding still shows — this is a signed-in user, just one without (confirmed or yet-to-be-confirmed) access, not someone who's left the portal. `minimalHeader` widens `Header`'s existing `hideProjectControls` flag to also hide `QuickNav`/`PinnedTabs`/pin-and-recent-views (nothing to search/pin/revisit without real pages) and, inside `UserProfile`'s own avatar menu, "Profile"/"Preferences" (nothing to view/configure without real portal access) — while still showing the theme toggle, the user's own identity (avatar/name/email, sourced from the ID token via `useIdTokenClaims`, not `/users/me`) and "Sign out". `Header.tsx` also adds a `flexGrow` spacer so `Actions` stays right-aligned once the middle elements it used to lean on are gone. The sidebar is suppressed by that same `minimalHeader` prop directly (`AppLayout`'s sidebar condition ANDs in `!minimalHeader` alongside its pre-existing `!isErrorPageDisplayed` context check) — deliberately not routed through `setIsErrorPageDisplayed` alone, since that context update only lands a render later via an effect, which let the sidebar flash on screen for one frame before disappearing (a CodeRabbit catch on the PR that introduced this). Any future full-page "nothing to navigate to" state on `AppLayout` should suppress its sidebar the same way — a prop threaded through the same render as the content, not a context flag updated afterward — for anything that needs to be correct on the very first paint. `NoPortalAccessPage.tsx` is the content shown in this state — deliberately not styled as an "error" (no illustration, no sign-out link): non-technical copy, a plain muted icon.

## In-page navigation via `#hash` anchors (tabs/topics within one route)

`HelpPage.tsx` switches between 13 topics on a single `/help` route by keeping the active topic id in state and the URL's own `#<topic>` hash in sync with it (bookmarkable, browser back/forward works) — the reference shape for any future "one route, many in-page sections linked by real `<a href="#…">` elements" feature (a docs-style sidebar, a Prev/Next pair, etc.):

- **`preventDefault()` every such anchor's click**, and drive the switch entirely through React state — never let the browser's own default fragment-navigation run. If a link's `href` reflects data that changes when the active section changes (e.g. a "Next" link, whose target is always "whatever comes after the *new* active section"), React re-renders that same `<a>` with its `href` already pointing one section further along **before** the browser reads `href` to perform its default action — since that read happens synchronously right after the click's event listeners finish, it follows the just-updated (one-section-too-far) value instead of the one actually clicked. This is invisible in jsdom/Vitest (it doesn't perform real anchor hash-navigation), so it has to be verified in a real browser — see `HelpPage.tsx`'s `navigateToTopic`.
- **Sync state → URL in a `useEffect` keyed on the active id, not inside the click handler.** Writing to `window.location.hash` directly inside a component-defined callback trips `eslint-plugin-react-hooks`'s `react-hooks/immutability` rule ("modifying a variable defined outside a component or hook"); an effect is both what the lint error itself suggests and the architecturally cleaner shape (state is the single source of truth, the URL just follows it). A second effect listening for `hashchange` handles the reverse direction (browser back/forward, a bookmarked/shared link) — guard both directions with an equality check so they don't fight each other in a loop.
- **AppLayout's main content area scrolls itself (`overflow: auto`, `mainContentRef.current`) — the window/document never does**, since the app shell is pinned to `100dvh` with `overflow: hidden`. Any per-page "scroll to top on switch" or "back to top" needs the real scrollable ancestor (walk up from a ref via computed `overflowY`, same approach as `findVerticalScrollAncestor` in `csm-cases/utils/permalinkScroll.ts`), not `window.scrollTo`/`window.scrollY` — the latter silently never fires in production even though it can look like it works under Vitest, which lets a test mock `window.scrollY` directly regardless of real layout.

## Page conventions: Back navigation

- **Position**: a page's own Back button is always the *first* child rendered, above the title/header — never below a tab strip or any other content. See `UserProfilePage.tsx` and `CsmProjectDetailPage.tsx`'s local `BackButton` components for the reference shape (`variant="text"`, `size="small"`, `startIcon={<ArrowLeft size={16} />}`, `sx={{ alignSelf: "flex-start" }}`).
- **Resolving the target**: prefer `location.state.from` (set by whatever list/detail page the caller came from) over a hardcoded fallback path, so Back returns to the exact originating view rather than skipping past it to a generic list — e.g. `const resolvedBackPath = (location.state as { from?: string } | undefined)?.from ?? "/some/hardcoded/default";`. This is the established convention across `CsmProjectDetailPage.tsx`, `CsmCaseDetailPage.tsx`, `ProductVulnerabilitiesTab.tsx`, and the 4 case-type create pages below.
  - **Exceptions** (fixed-destination Back links, deliberately not `state.from`-aware): `CsmDashboardBuilderEditorPage.tsx`'s "Back to dashboards" — only ever reached from `CsmDashboardBuilderListPage.tsx`. `DashboardWidgetPreviewPage.tsx` hardcodes Back to `/dashboard` for a different reason — it's deliberately fully URL-driven (bookmarkable/shareable), not state-based, per its own doc comment. Don't generalize `CsmProjectDetailPage.tsx`'s pattern onto either of these; a genuinely-fixed-destination or genuinely-URL-driven Back link is fine to leave as-is. If a future caller ever links directly into the first one (bypassing its current single list page), revisit whether it still qualifies as fixed-destination.
  - **`CsmAdminLayout.tsx` used to be in this exception list** (a fixed "Back to User management" link for every `/admin/user-management/*` directory page, reasoned as "only ever reached via a tile on that grid"). That reasoning broke once `CsmUsersPage.tsx` gained a second entry point (a dashboard widget's `resourceType: "user"` click-through, which sets `state.from`) — reported live as a page whose Back always forced the tile grid regardless of where the user actually came from. `CsmAdminLayout.tsx` now reads `state.from` like every other page (falling back to the tile-grid index only when absent), and forwards `state.parentState` on Back so a multi-hop chain (dashboard → a directory page → a person's profile → Back → Back) still restores correctly. `CsmUsersPage.tsx` itself no longer renders its own Back button — the layout it's nested under (`CsmAdminLayout`) sees the exact same `location.state` and is the single Back button for every page it wraps, so a page nested under a layout that already renders Back should not also render its own. The takeaway: a "fixed-destination" Back is only safe while every caller is verified to reach that page the same single way — if a second entry point is ever added, the exception no longer holds and it needs to become `state.from`-aware like everything else.
  - **`DirectoryMemberPage.tsx` (backing `RoleMembersPage`/`GroupMembersPage`/`TeamMembersPage`) hit the exact same lesson a second time.** It used to hardcode Back to its own list (`/admin/roles`, `/admin/groups`, `/admin/teams`), reasoned as "only ever reached from the directory list" — true until `DirectoryEntityChip.tsx` (a clickable role/team/group chip, rendered on a case's meta band, an account's detail page, and a user's profile) started linking straight into these same pages too, none of which set any `from`. Reported live as "Back to Teams" from a case always landing on the plain Teams directory instead of back on the case. Fixed the same way: `DirectoryEntityChip.tsx` now passes `state: { name, from: \`${location.pathname}${location.search}${location.hash}\` }`; `DirectoryMemberPage.tsx` reads `state.from`, falling back to its own `listPath` only when absent (a direct/shared link, or the entity's own directory row — which still doesn't set `from`, since for that one caller `from` and `listPath` are the same place anyway); and the label changed from `Back to {listLabel}` to plain `Back` now that the destination is dynamic (the `listLabel` prop was removed entirely, since nothing else used it). `DirectoryMembersList.tsx`'s own row-to-profile links got the matching treatment (`state: { from: <this member list's own location> }`) for the same reason — `UserProfilePage.tsx` already preferred `state.from` over its `navigate(-1)` fallback, it just wasn't being supplied from here. Same takeaway as `CsmAdminLayout.tsx` above, and worth re-checking `CsmDashboardBuilderEditorPage.tsx`/`CsmAnnouncementCreatePage.tsx` (the latter not `state.from`-aware today, safe only because nothing links to `/announcements/new` except the top-level Announcements list) if either one ever gains a second entry point.
- **`location.state` belongs to the route, not the component that reads it.** A component embedded as a sub-tab of a page (e.g. `CsmIssuesView` reused inside a project's `WorkItemsTab`) still sees whatever `from` the *outer* route was reached with, even though the embedding itself isn't a navigation. A page-level component with its own Back button needs an explicit opt-out prop (e.g. `hideBackButton`) before it can be safely embedded inside another page that already has its own Back button — otherwise both render, pointing at the same destination. Never reuse a standalone page's component as an embedded tab without checking for (and passing) this escape hatch. A parent *route layout* rendering the Back button for all of its child routes (`CsmAdminLayout.tsx`) is the same principle one level up: a child page nested under such a layout must not also render its own Back button.
- **Label the button "Back", not "Back to X"**, whenever its destination is resolved dynamically (i.e. can be `state.from` or a hardcoded fallback) — a fixed "Back to cases" label reads wrong once the button might actually be returning to a project instead. Reserve a destination-specific label for a button whose target is genuinely always the same place (see the `CsmDashboardBuilderEditorPage.tsx` exception above) — `CsmDashboardSharedConfigPage.tsx`'s Back-shaped control used to be labeled just `Dashboards` instead of `Back`/`Back to dashboards`, a cosmetic inconsistency fixed alongside the `DirectoryMemberPage.tsx` relabeling below even though its own destination genuinely is fixed.
- **Project → create-flow → new entity's Back must round-trip through the project, tab included.** `CsmProjectDetailPage.tsx`'s "Create case"/"Create service request"/"Create engagement"/"Create security report" menu items pass `state: { from: projectPath }` when navigating to `/cases/new`, etc., where `projectPath` is `` `${location.pathname}${location.search}` `` — not just the bare `/customers/projects/:id`. Each create page (`CsmCaseCreatePage.tsx`, `CreateServiceRequestPage.tsx`, `CsmEngagementCreatePage.tsx`, `CreateSecurityReportPage.tsx`) reads that same `from` for its own "Back"/"Cancel" buttons (`backTarget = backState?.from ?? "<its own default list>"`), **and** forwards it as `state: { from: backTarget }` on the `navigate(...)` call after a successful create — so the newly created case/engagement/report's own detail page (all backed by `CsmCaseDetailPage.tsx`, which already reads `location.state.from`) returns to the project instead of falling back to that entity type's generic top-level list. Any new "create X from a project" flow must follow this same three-hop chain (project → create page → new detail page), not just the first hop.
  - `CsmProjectDetailPage.tsx`'s own `activeTab` and `WorkItemsTab.tsx`'s own `subTab` are both kept in the URL (`?tab=`/`&subTab=`), not local `useState`, specifically so `projectPath` above captures them — a round trip through a create flow (or any other page navigated away to) restores the exact tab the engineer was on, not just the bare project page defaulting back to Overview. Any project-level tab strip that needs to survive a similar round trip should follow the same URL-backed pattern rather than local state.

## Table conventions

Every paginated data table backed by a real MUI `<Table>` (`ProductVulnerabilitiesTab.tsx`, `DirectoryEntityTable.tsx`, `ChangeRequestsTab.tsx`, `IncidentsTab.tsx`, `ProblemsTab.tsx`) should match this shape — a new one should too. (`ConversationsTab.tsx` used to be listed here too, but it's actually a hand-rolled CSS Grid like `CasesList.tsx` below, not a real `<Table>` — it just has no long-text column today, so the gotcha two paragraphs down doesn't currently apply to it.)

- **Wrapper**: `<Box sx={{ border: 1, borderColor: "divider", borderRadius: 1, overflow: "hidden" }}>` around `<TableContainer>`, not `<Paper variant="outlined">` (the two render visually differently; `Box` is the established one). `TablePagination` (when present) is a sibling of `TableContainer`, inside that same `Box`. `TableContainer`'s own built-in `overflow-x: auto` is what makes a wide table scroll horizontally instead of squishing its columns — don't strip or override it.
- **`<Table size="small" sx={{ "& .MuiTableCell-root": { borderColor: "divider" } }}>`**, with the header row as `<TableRow sx={{ bgcolor: "action.hover" }}>` — a plain `<TableRow>` header with no `sx` reads inconsistently against tables that do set it.
- **Loading skeleton row count must equal the current page size**, not a hardcoded number — `Array.from({ length: rowsPerPage })` (or a `skeletonCount` prop threaded through, per `CasesList.tsx`), so switching "rows per page" to 50 shows 50 skeleton rows, matching what's about to load. A hardcoded `Array.from({ length: 3 })` is the recurring mistake to avoid (it doesn't scale with the selected page size and reads as a different, lesser table). A table with no pagination at all (e.g. `ProjectContactsTab.tsx`, which loads every row up front) has no page-size state to tie to and a small fixed skeleton count is fine there.
- **`TablePagination`**: include `showFirstButton`/`showLastButton` alongside the usual `count`/`page`/`onPageChange`/`rowsPerPage`/`onRowsPerPageChange`/`rowsPerPageOptions`.
- **Status chips default to `variant="outlined"`** (`SemanticChip`/`Chip`), matching `deriveAccessStatus`/`deriveProjectAccessStatus`/registration chips — a filled chip reads as heavier/more alarming than intended for routine status values. `StateChip` (case lifecycle state specifically) is a deliberate, documented exception that renders filled/solid — don't generalize from it to other chips.

**`CasesList.tsx` is the one exception to "real `<Table>`"**: it's a hand-rolled CSS Grid (`display: "grid"` + `grid-template-columns: subgrid` per row), not `<Table>`/`<TableContainer>` — this doc used to (incorrectly) list it alongside the real-`<Table>` group above, which hid a real bug: a CSS grid container's automatic minimum width lets its tracks shrink below their own `minmax(...)` floor to fit whatever space is available, so without `TableContainer`'s built-in scroll behavior, a wide `CasesList` squished/clipped its column content instead of scrolling once several optional columns were on at once. Fixed by wrapping the grid in its own `overflowX: "auto"` layer and giving the grid itself `minWidth: "max-content"` (forces it to only ever overflow that scroll layer, never shrink its own tracks) — the general shape to reuse for any *other* CSS-grid-based table this app ever grows, since `TableContainer`'s convention above doesn't apply to it.

**That same `minWidth: "max-content"` fix has its own follow-on gotcha: it makes *any* free-text column — default or optional — able to force the whole grid to scroll far past what the column count alone would justify**, on the strength of a single unusually long value in just that one column. First reported for a long case Subject with zero optional columns on; then again for Security Reports' Product column (an *optional* column) — same mechanism, different column, because only Subject got the fix the first time. `noWrap`'s ellipsis (used throughout this file — Subject, product, customer, assignee, createdBy) only clips *paint*; it has no effect on a grid item's intrinsic max-content sizing, which is what `minWidth: "max-content"` on the container actually keys off. The fix is a real `maxWidth` (a fixed px value, not a percentage) on the cell's own wrapping `Box` — a grid item's specified max-width *does* clamp its max-content contribution to track sizing, unlike `overflow`/`text-overflow`. Every free-text column now has one: Subject's own `Box` gets `maxWidth: 360` (matching the same Subject column's own already-proven cap on `ChangeRequestsTab.tsx`/`IncidentsTab.tsx`); every optional column's shared wrapper (`effectiveOptionalColumns.map`) gets `maxWidth: 260` uniformly, whether that particular id renders free text (product, customer, assignee, createdBy) or something already-bounded (a `Chip`, a relative-time string) — capping the bounded ones costs nothing and closes the gap for any future optional column type without having to reason per-id about which ones are "safe." The design intent this preserves: adding *more* optional columns (each reasonably capped) needing more total width, and therefore scrolling, is fine and intended — it's *one column* growing disproportionately from a single outlier value, default or optional, that's the bug.

**Pick the cap small enough that the *sum* still fits a normal viewport, not just "bounded."** Subject's cap started at `480` — comfortably bounded against any one pathological value, but 480 (Subject) + 260 (one default-visible optional column, e.g. Security Reports' Product) + the other default columns' own floors still summed to more than a typical content-area width, so the *default* view scrolled horizontally even with everyday-length values, not just outliers — reported live right after the first fix shipped. A cap has to solve both problems at once: bound the worst case, *and* keep the realistic default-view total within a normal viewport. When in doubt, match a value already proven elsewhere in the app for the same semantic column (Subject's `360` here now matches the real-`<Table>` versions) rather than picking a new one that merely "seems reasonable."

**The same class of bug exists in every real `<Table>` too, via a different mechanism, and was found across most of them.** `TableContainer`'s `overflow-x: auto` (the convention above) makes the table scroll instead of squishing — but with the default `table-layout: auto`, a `<TableCell>` holding unbroken free text still has no upper bound on its own, so one long value (a name, a subject) forces that column — and the whole table, via the same scroll behavior — wider than intended, even with nothing else going on. `noWrap` alone (an ellipsis) doesn't fix this any more than it does for the CSS Grid case above: it only clips paint, and `table-layout: auto`'s column-width calculation isn't affected by it. A real `maxWidth` (fixed px, on the `TableCell` itself; a percentage `width` is not a reliable substitute — an unbroken token like a URL can still overflow it) is what actually caps it. Fixed in `ProductVulnerabilitiesTab.tsx` (Component/Product), `DirectoryEntityTable.tsx` (Name), `TasksWidget.tsx` (subject — found with *no* truncation treatment at all), `LinkedChangeRequestsWidget.tsx` (name), `CsmAccountsPage.tsx`/`CsmProjectsPage.tsx` (name), `CsmAnnouncementsPage.tsx` (subject — had a percentage width already, now also has a px cap), and the `UserRefLink` identity cell in `DirectoryMembersList.tsx`/`CsmUsersPage.tsx`/`ProjectContactsTab.tsx`/`CsmAccountDetailPage.tsx`. `ChangeRequestsTab.tsx`/`IncidentsTab.tsx`/`ProblemsTab.tsx` already had this right (`maxWidth: 360`/`480` on the Subject `TableCell`) — that's the reference shape for any new real-`<Table>` column holding freeform text.

**Per-table "Customise columns" control (`ColumnCustomizerButton` + `useColumnPreferences`) belongs next to the table it controls, not in a page header far away from it.** `CasesList.tsx` takes a `columnCustomizer?: ReactNode` prop and renders it in a small toolbar row directly above its own grid; the caller (`CsmIssuesView.tsx`, or a dashboard widget's own preview page) builds the actual `<ColumnCustomizerButton>` (it alone knows that view's `viewId`/available columns/defaults) and passes it through. This split — table renders the slot, caller owns the state — is what let `DashboardWidgetPreviewPage.tsx`'s case-family widget preview gain the exact same column customization the main Cases/Service requests/Security reports/Engagements tabs already have, just by wiring its own `useColumnPreferences` and passing the button into the same prop, without `CasesList` needing to know anything about dashboards. Follow this pattern (a `columnCustomizer`/similar slot prop on the reusable table, not a control baked into one specific page's header) for any other reusable table that gains per-view column customization.

**`ColumnCustomizerButton`'s picker reorders columns by dragging a grip handle** (native HTML5 drag-and-drop — `draggable` + `onDragStart`/`onDragOver`/`onDrop`, no library), not the up/down chevron pair it used to have. The handle's focus + arrow-up/down keys still call `useColumnPreferences`'s `moveColumn` (one slot at a time) as the keyboard-accessible fallback, since native drag-and-drop has no keyboard path of its own — losing that would've been a real accessibility regression, not just a visual one. The drop itself calls a *different* hook method, `reorderColumn(id, targetIndex)`, not a repeated `moveColumn`: `moveColumn` is a `useCallback` closing over that render's `state`, so calling it more than once inside the same synchronous drop handler (which a multi-slot drag needs) would have every call act on the same stale `state.order` and net only a single-slot move no matter the actual drop target. `reorderColumn` computes the whole new order in one atomic update instead. Any future "reorder by dragging, multiple slots in one gesture" UI on a `useColumnPreferences`-backed list should reuse `reorderColumn`, not try to loop `moveColumn`.

**`CasesFilterBar.tsx`'s "Quick filters"/"Advanced" toggle stashes-and-restores instead of disabling.** The Quick filters grid can't represent every filter shape the Advanced builder can (an OR group, `tags`, certain operators) — clicking Quick filters used to just be `disabled` whenever the active filter had anything like that, with no way to even look at the Quick filters grid without first clearing it by hand. It's unconditionally clickable now: clicking it while not Simple-representable resets the active filter to `DEFAULT_CASES_FILTERS` (preserving `search`, which is shared by both modes and edited independently of this toggle) — Quick filters must never silently keep an Advanced-only criterion applied behind a grid that can't display it — but stashes the previous value in local state first, so an accidental click doesn't lose real filter criteria: clicking straight back to Advanced restores it. That stash is dropped the moment a real edit happens in Quick filters (routed through `handleSimpleFieldChange`, not `onChange` directly) — restoring stale Advanced criteria over a filter the user just deliberately changed would be its own kind of surprising data loss. Any other "switching view A to view B loses some of A's state" toggle in this app should follow the same shape: clear-with-a-stash-and-restore, not a disabled control with no path forward.

## Data fetching

TanStack React Query is the only data-fetching layer — no other state-management library. Custom hook naming is verb-prefixed and consistent:

- `useGetX` — read a single resource (`useGetCsmCaseDetail`, `useGetAccount`, `useGetUsersMe`)
- `usePostX` / `usePatchX` — mutations (`usePostCsmCase`, `usePatchUsersMe`)
- `useSearchX` / `useXOptions` — typeahead/autocomplete queries
- Plain domain-named hooks for composed/derived state (`useCaseComposition`, `useIsTeamLead`)

## Testing

- Runner: Vitest (`jsdom` environment), configured inline in `vite.config.ts` — no separate `vitest.config.ts`.
- **`@api/backend/client` and `@config/apiConfig` read `window.config` at module load time**, which doesn't exist under Vitest. Any test that transitively imports the real client/config (even through an unrelated import chain — e.g. a dashboard list-widget renderer pulling in a mapper that imports `@config/apiConfig`) must mock it first:
  ```ts
  vi.mock("@api/backend/client", () => ({ useBackendApi: () => ({ post: postMock }) }));
  vi.mock("@config/apiConfig", () => ({ apiConfig: { backendUrl: "https://example.test" } }));
  ```
- Mock the low-level client when testing a component wired directly to a data hook; mock the hook module itself when testing a component that just *consumes* an already-built hook.
- React Query tests wrap `render`/`renderHook` in `QueryClientProvider` with a fresh `new QueryClient({ defaultOptions: { queries: { retry: false } } })` per test.
- Components needing router context render inside `<MemoryRouter>` (from `react-router`). To assert on where a click actually navigated (not just that a handler fired), wrap in `<Routes>` with a destination route rendering a probe component that reads `useLocation()`, rather than mocking `useNavigate` — see `DashboardWidgetPreviewPage.test.tsx` / `DashboardWidgetTile.test.tsx` for the pattern.
- Charting components (`@wso2/oxygen-ui-charts-react`, a `recharts` wrapper) don't render meaningfully under `jsdom` (`ResponsiveContainer` measures a real layout size, always `0` in `jsdom`) — mock the package to a plain list of clickable stand-ins exposing the data/handlers under test, not the real chart. See `DashboardWidgetTile.test.tsx`'s mock of `Pie`/`Bar`/`PieChart`/`BarChart`.

## Security

- **Never commit secrets or runtime config** — `public/config.js` (the real, per-deployment file copied from `public/config.js.example`) is git-ignored on purpose. It only ever holds *public* runtime values (IdP base URL, OAuth **client id** — not a secret, this is a PKCE/SPA flow with no client secret — backend base URL, theme, log level, feature flags); if a value you're adding isn't safe to ship to a browser, it doesn't belong in `window.config` at all.
- **Auth is Asgardeo's job, not ours** — `AsgardeoProvider` (`AppWithConfig.tsx`) and `useAsgardeo()`/`AuthGuard.tsx` own the whole auth lifecycle; the app **never reads or writes auth tokens itself** (no token in `localStorage`/`sessionStorage` anywhere in this codebase — the SDK manages that internally). Don't add code that pulls a token out of storage or a hook return value to attach it manually; use the existing API client wiring instead. The `sessionStorage` keys outside the SDK are `POST_LOGIN_REDIRECT_KEY` (a post-login redirect **path**) and `csm.sidebar.lastSection` (`CsmSideBar.tsx` — the last-resolved nav section id, so a reload on a route with no owning section, e.g. `/people/:id`, re-highlights it instead of resetting to Dashboard) — neither ever holds a token.
- **Sanitize before `dangerouslySetInnerHTML`, always** — every current use (case-comment rendering, rich-text description/plan fields, product-update content, the admin-configured top banner/announcement HTML) goes through `DOMPurify.sanitize` first (`src/utils/sanitizeHtml.ts` for the shared cases). `sanitizeHtml.ts` also force-hardens every sanitized `target="_blank"` link with `rel="noopener noreferrer"` against reverse tabnabbing — match that when adding any other `target="_blank"` link by hand. Never add a new `dangerouslySetInnerHTML` call that skips sanitization, even for content that looks like it's "our own" (e.g. admin-authored) — an admin-configured field is still attacker-controlled if that admin account is ever compromised.
- **`useLogger()`/`Logger` (`src/hooks/useLogger.ts`, `src/hooks/logger.ts`) is a plain console wrapper with no redaction** — it does not scrub or block sensitive fields before printing. The discipline has to live at the call site: log `error.message`/a short summary, not a whole caught `Error` object, request/response body, or user/profile object, since any of those can carry tokens, PII, or internal ids straight into the browser console (and potentially a session-replay/log-shipping tool downstream).
- **Don't let the client-facing UI surface backend internals** — render whatever (already-generic) message the backend sends; don't append stack traces, raw error objects, or your own extra technical detail on top of it. See the dashboard widget-preview page's URL design below for the same principle applied to URLs, not just error text: prefer a `@me`-style sentinel over embedding a raw internal id in anything bookmarkable/shareable/loggable.
- **No `eval`, `new Function`, or dynamic `<script>` injection** anywhere in `src/` — keep it that way; there's no legitimate use case for it in this app.

## The config-driven dashboard widget system

`AgentsLandingPagePilot` (rendered from `CsmDashboardPage.tsx`, alongside the older `AbtDashboardHeader` dashboard/team switcher) is a **fully backend-config-driven** widget grid — there is no frontend-side widget registry. The backend's `DASHBOARDS_CONFIG` env var (a JSON array, parsed into Go's `dashboard.Dashboard`/`dashboard.WidgetTemplate` — see `apps/csm-portal/backend/internal/dashboard/widgets.go`) is the single source of truth for which dashboards exist, which widgets each one has, and how each widget is filtered. The frontend never hardcodes a widget list; it only knows how to *render* whatever shape/resourceType combination the backend sends.

Other components in this same folder (`CaseCompositionCharts`, `CompositionDonut`, `CaseCountsMatrix`, `CustomerSummarySection`, `RecentActivitySection`, `MyAssignedCases`) are a separate, older composition-chart system that isn't currently wired into `CsmDashboardPage.tsx` — don't confuse them with the widget system below.

### The wire shape (`src/api/backend/types.ts`)

`GET /dashboards` returns `BeDashboardListItem[]` (id/displayName/isDefault/isTeamBased — enough for the dashboard switcher). `GET /dashboards/{id}` returns the full `BeDashboard`, whose `widgets: BeDashboardWidget[]` is the actual per-widget config:

```ts
interface BeDashboardWidget {
  widgetId: string;
  displayName: string;
  description?: string;        // subtitle shown under displayName; not shape-specific by design
  resourceType: BeWidgetResourceType;  // "case" | "incident" | "change_request" | "account" | "project"
                                        // | "user" | "time_card" | "problem" | "product_vulnerability"
  shape: BeWidgetShape;         // "count" | "list" | "pie" | "bar"
  gridWidth: number;            // 1-12, CSS grid columns this widget occupies
  filters: Record<string, unknown>;  // opaque; passed verbatim as the filters of that
                                      // resourceType's own POST /{resourceType}s/search
  groupBy?: string;             // present on the wire; unused today — `slices` (below) is what
                                 // actually drives pie/bar grouping
  listLimit?: number;           // shape "list" only: how many rows to show
  slices?: BeDashboardPieSlice[]; // shapes "pie"/"bar" only: see below
  section?: string;            // groups widgets under a titled sub-heading — see below
}

interface BeDashboardPieSlice {
  label: string;
  color?: BeWidgetPaletteColor;  // "primary" | "secondary" | "success" | "error" | "info" | "warning"
  filters: Record<string, unknown>;  // this slice's own criteria only — merge under the widget's
                                      // own base `filters` (slice keys win) to resolve its total
}
```

Every field beyond `widgetId`/`displayName`/`resourceType`/`shape`/`gridWidth`/`filters` is optional and `omitempty` on the wire — a widget/dashboard that doesn't set them behaves exactly as if the field didn't exist.

### How each `shape` resolves its data

All four shapes ultimately do the same thing — issue that `resourceType`'s own `POST /{resourceType}s/search` and read the response — they just differ in *how many* searches and what they do with the result(s):

- **`count`** (`useWidgetData`, shape `"count"`): one search, `pagination.limit: 1`, reads `total`. Renders a big number, the whole tile is a link to that resource's own tab (`WIDGET_RESOURCE_CONFIG[resourceType].buildHref(filters)`).
- **`list`** (`useWidgetData`, shape `"list"`): one search, `pagination.limit: listLimit ?? 4`, reads the item array. Renders through `WIDGET_LIST_RENDERERS[resourceType]` (`widgetListConfig.tsx`) — reuses each resource's **own real tab component** where one exists (e.g. `case` renders through the identical `CasesList` the Cases tab uses, via the same `mapCaseSearchViewToRow` mapper), falling back to the generic `DashboardMiniTable` otherwise. A "View more" link (shown only once `total > (listLimit ?? 4)`) goes to a dedicated, real, bookmarkable preview route (`DashboardWidgetPreviewPage`, `/dashboard/:previewSlug`) with pagination and search — not directly to the resource's own tab.
- **`pie`** / **`bar`** (`useWidgetPieData`): one search **per `slices` entry**, each with `pagination.limit: 1`, merging that slice's own `filters` under the widget's base `filters` (slice keys win). `useWidgetPieData` is shape-agnostic — it just resolves N labeled totals; `DashboardPieChart`/`DashboardBarChart` (both under `components/`) render the same resolved data as wedges or bars respectively. Each wedge/bar/legend row navigates to that slice's own filtered destination the same way a `count` tile does. A total of `0` across every slice renders an empty state (inbox icon + "Nothing to show here right now"), not an all-grey chart.

`DashboardWidgetTile.tsx` is the per-widget dispatcher: it reads `shape` and picks which of the above to render, plus the shared per-widget loading/error states.

### `section` grouping

`AgentsLandingPagePilot.tsx`'s `groupWidgetsBySection` groups a dashboard's widgets by their `section` value, preserving the order each distinct value (including the untitled default, for widgets with no `section`) first appears among the widgets array. Widgets sharing a `section` render together under one bold heading, separate from the rest — e.g. a handful of SLA-violation `count` widgets can all set `"section": "SLA Violation"` to appear grouped under that heading without needing a separate dashboard. No `section` set anywhere (the common case) renders exactly as before this field existed: one untitled group, with `pie`/`bar` widgets still visually separated from `count`/`list` ones within that group.

### Per-resourceType config (`config/widgetResourceConfig.ts`, `config/widgetListConfig.tsx`)

`WIDGET_RESOURCE_CONFIG` is the one place that knows, per `resourceType`: its search endpoint, response items key, list-row label extractors, tile icon/color, `buildHref` (translates a widget's opaque filters into that resource's **own** tab's URL filter scheme — e.g. the dashboard's lowercase `catastrophic`/`critical`/... severity values get translated to the Cases tab's own `S0`/`S1`/... codes), and `previewSlug` (the URL segment for that resourceType's `/dashboard/:previewSlug` preview page). Adding a new `resourceType` the backend can send means adding an entry here and to `WIDGET_LIST_RENDERERS` — everything else (tile rendering, preview page, pagination) is generic over any entry in these two config objects.

### Current-user placeholder

The backend resolves a `"__current_user__"` filter placeholder into the caller's real platform user id **before** it reaches the frontend (see the backend's `ResolveFilters`/`ResolveSliceFilters`) — the frontend never sees or handles that placeholder for a widget's own data-fetching. Separately, the "View more" preview page's own **URL** masks the current user's id to a `@me` sentinel (`widgetPreviewUrl.ts`'s `buildWidgetPreviewHref`/`resolveCurrentUserSentinels`) purely so a bookmarked/shared link doesn't carry a bare internal user id — that's a frontend-only, URL-display concern, unrelated to the backend's own placeholder resolution.
