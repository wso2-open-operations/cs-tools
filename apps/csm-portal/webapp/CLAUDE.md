# CSM Portal Webapp

React + TypeScript + Vite frontend for the CSM portal, using the `@wso2/oxygen-ui` (MUI-based) design system, TanStack React Query for data fetching, and `react-router` v7 (the unified `react-router` package — **not** `react-router-dom`). See `README.md` for setup, `window.config` keys, and the `dev:local` local-gateway mode; this file covers code-organization and workflow conventions instead.

## Frontend permission gating — an exception, not the norm

The standing project rule (see `src/App.tsx`'s own comment on the role/group/team member routes) is
to **show the action and let the backend reject it, never gate in the frontend** — `usePortalAccess()`
exists mainly so controls the caller definitely cannot use don't clutter the UI, not as the real
security boundary; the backend's `403` is that. The Dashboard Builder route (`DashboardBuilderRouteGuard`,
`dashboardBuilderAccess.ts`) was the one deliberate exception, reasoned there as "this feature has
no backend of its own to enforce it."

**Add User** (`CsmUsersPage.tsx`'s "Add user" button, `AddUserDialog.tsx`) is a second deliberate
exception, gated on `usePortalAccess().canCreateUser` (`portalAccess.ts`) — `admin` only, unlike
every other flag on `PortalAccess`, which `cs_engineer` also holds. Here the backend genuinely
does enforce it (`POST /users` requires `PermAdmin` — see `apps/csm-portal/backend`'s own `CLAUDE.md`),
so this isn't the same "no backend to fall back on" situation Dashboard Builder was — it's client-side
gating on top of a real server-side gate, by explicit choice rather than by the show-and-let-it-reject
default. If a future admin-only action is added, default to the show-and-reject norm unless there's a
specific reason (as here) to also hide it.

`AddUserDialog.tsx` has two independent role-shaped controls that must not be confused with each
other. One narrower, required control: **"User type" (Internal/External)**. entity-service's `user_type` has no plain settable
column — it's derived by a DB trigger from role membership (`recompute_user_type`, migration 0011) —
so this selector works by sending exactly one of `roles: ["internal"]`/`["external"]` on submit, not a
`type` field on the wire; `external` (not `customer`/`partner`/...) is the role every
externally-onboarded contact actually holds, so that's the one this form sends for "External" rather
than a finer-grained refinement it has no way to know at creation time. This was added because the
form previously sent no `roles` at all, so every user it created resolved to `user_type =
NOT_AVAILABLE` (entity-service's trigger fallback) — a real, silent data-quality gap, not a
hypothetical one.

**Selecting "Internal" requires a `@wso2.com` email** — the form blocks submission and shows the
constraint inline (`internalEmailViolation` in `AddUserDialog.tsx`) rather than letting the request
round-trip to find out. This is a display-consistency check only, the same relationship the inline-image
redaction section below describes for its own frontend mitigation: entity-service's `userService.CreateUser`
enforces the identical rule server-side (see that repo's own `CLAUDE.md`), and is what actually
protects the database regardless of what this form does or doesn't check.

**"External" is temporarily disabled** (`USER_TYPE_OPTIONS`'s own `disabled: true`, rendered via
`MenuItem`'s `disabled` prop with "— currently unavailable" appended to the label) — both
entity-service and `apps/csm-portal/backend` reject creating an external-type user regardless of what
this form sends, so there is currently only one real, selectable choice in this dropdown. This is
meant to come out once external-type creation is ready; see entity-service's own `CLAUDE.md` for the
full reasoning.

The second, independent control is **"Portal roles"** — a checkbox per role `GET /roles/grantable`
reports, rendered only when that list is non-empty (`useGetGrantableRoles`, fetched only while the
dialog is open). Selected keys go out as `grantRoles` on submit, a completely separate field from
`roles` above: `roles` only ever shapes entity-service's `user_type`, `grantRoles` only ever grants
Asgardeo-backed portal permissions (`cs_engineer`, `escalator`, ...) via SCIM, once the user already
exists — see `apps/csm-portal/backend`'s own `CLAUDE.md`, "Granting portal roles on user creation", for
the full backend mechanism. This frontend never learns the real identity-provider role name/id behind
a key; `grantableRoleLabels.ts` maps each key to its own display label (falling back to a title-cased
version of the raw key for one this map hasn't been updated for yet, rather than hiding it). Protected
the same way the rest of this dialog already is: **admin-only on both ends** — `GET /roles/grantable`
and `POST /users` share the identical `PermAdmin` gate on the backend, and on this frontend the section
only ever renders inside `AddUserDialog`, which `CsmUsersPage.tsx`'s own `canCreateUser` check already
keeps out of a non-admin's reach entirely (see the "Add User" exception at the top of this section) —
no second, redundant permission check was added inside the dialog itself.

## Code organization

Feature-based: each `src/features/<name>/` folder owns its own `api/` (React Query hooks), `components/`, `pages/`, `types/`, `utils/`. Tests are colocated as `<File>.test.tsx` next to the file under test, not in a separate `__tests__` tree.

## Routing (`src/App.tsx`)

- Route page components are statically imported (eager), not `React.lazy`-loaded — deliberate, to ship as one JS bundle instead of one chunk per route. Per-route `React.lazy()` caused a real UX bug: navigating to a route not yet visited that session fetched a fresh chunk on the critical path, freezing the UI mid-navigation. See `index.html`'s boot loader (shown until the single bundle finishes loading) for the tradeoff this enables. One dynamic `import()` remains outside routing — the click-triggered PDF export in the Updates feature — since it's not on any navigation path and inlining it would grow the main bundle for a rarely-used feature.
- Declared with `react-router` v7's JSX `<Routes>`/`<Route>` API, not a data router (`createBrowserRouter`).
- Everything except `/401`/`/403`/`/404` sits under `<Route element={<AuthGuard />}>` → `<Route element={<FeatureRouteGuard />}>` (a runtime feature-flag/WIP gate keyed by `CSM_PORTAL_FEATURE_OVERRIDES`).
  - **Exception**: `/cs-monitor-dashboard` sits under its own `<Route element={<AuthGuard bare />}>`, deliberately OUTSIDE `FeatureRouteGuard`. It's a standalone, full-screen kiosk/wallboard view with no nav entry of its own to be WIP-gated against — `FeatureRouteGuard`'s whole job is keeping a route's availability consistent with its nav entry's `CSM_PORTAL_FEATURE_OVERRIDES` state, which doesn't apply to a route that was never reachable from the nav in the first place. `AuthGuard`'s own `bare` prop still runs the exact same sign-in/redirect/token-refresh logic as every other route — it only skips rendering `AppLayout` (header/sidebar/banners) once authenticated, rendering a bare `<Outlet />` (in its own `Suspense` boundary, since `AppLayout` is otherwise the only place that provides one) instead.
- Legacy paths (e.g. `/accounts`, `/projects`) are kept as `<Navigate>` redirects for backward compatibility rather than removed outright.

## Not-yet-entitled users (`AuthGuard.tsx`'s `AuthorizedAppShell`)

A signed-in caller whose `/users/me` call still comes back 401/403 after `useAuthApiClient`'s own retry/silent-refresh chain has had its chance (see that hook's own doc comments) is treated as "not entitled to this portal yet", not a transient auth hiccup. Unlike every other API call, `/users/me` (`useGetUsersMe.ts`) passes `skipSignInRedirect: true` — once the retry + silent-reauth + poll chain is exhausted with the 401/403 still standing, its own failure surfaces immediately instead of attempting the usual full-page sign-in redirect. That redirect assumes the browser is about to navigate away (which is why it's written to never resolve — nothing should render behind it mid-navigation), but that assumption breaks when `signIn()` has nothing left to fix and silently no-ops (the caller's IdP session is already fully valid — it's portal-level entitlement that's missing) — a real account in exactly this state was observed hanging forever behind that never-resolving promise, `/users/me` stuck "loading" indefinitely with no error and no redirect ever actually happening. `skipSignInRedirect` exists specifically so `/users/me`'s own gate always reaches a decisive answer.

While that check is still pending — not just once it comes back positive — `AuthorizedAppShell` suppresses the routed page entirely (`AppLayout`'s `children` vs. bare `<AppLayout />`, the same mechanic `AuthPendingShell` above already uses, and for the same reason: the routed page's own components fire their own API calls immediately on mount, e.g. a dashboard widget's config request, so mounting it before `/users/me` had settled meant a caller who was about to be found unauthorized could still see real response data — and use the sidebar to reach other real pages — during that window). A signed-in user only ever sees the routed page once we positively know they're allowed to; until then (and while genuinely not authorized) they see a loading state or `NoPortalAccessPage` respectively, both through `AppLayout` itself (not a bare `ErrorLayout`) via a new `minimalHeader` prop, so the real header/branding still shows — this is a signed-in user, just one without (confirmed or yet-to-be-confirmed) access, not someone who's left the portal. `minimalHeader` widens `Header`'s existing `hideProjectControls` flag to also hide `QuickNav`/`PinnedTabs`/pin-and-recent-views (nothing to search/pin/revisit without real pages) and, inside `UserProfile`'s own avatar menu, "Profile"/"Preferences" (nothing to view/configure without real portal access) — while still showing the theme toggle, the user's own identity (avatar/name/email, sourced from the ID token via `useIdTokenClaims`, not `/users/me`) and "Sign out". `Header.tsx` also adds a `flexGrow` spacer so `Actions` stays right-aligned once the middle elements it used to lean on are gone. The sidebar is suppressed by that same `minimalHeader` prop directly (`AppLayout`'s sidebar condition ANDs in `!minimalHeader` alongside its pre-existing `!isErrorPageDisplayed` context check) — deliberately not routed through `setIsErrorPageDisplayed` alone, since that context update only lands a render later via an effect, which let the sidebar flash on screen for one frame before disappearing (a CodeRabbit catch on the PR that introduced this). Any future full-page "nothing to navigate to" state on `AppLayout` should suppress its sidebar the same way — a prop threaded through the same render as the content, not a context flag updated afterward — for anything that needs to be correct on the very first paint. `NoPortalAccessPage.tsx` is the content shown in this state — deliberately not styled as an "error" (no illustration, no sign-out link): non-technical copy, a plain muted icon.

## In-page navigation via `#hash` anchors (tabs/topics within one route)

`HelpPage.tsx` switches between 13 topics on a single `/help` route by keeping the active topic id in state and the URL's own `#<topic>` hash in sync with it (bookmarkable, browser back/forward works) — the reference shape for any future "one route, many in-page sections linked by real `<a href="#…">` elements" feature (a docs-style sidebar, a Prev/Next pair, etc.):

- **`preventDefault()` every such anchor's click**, and drive the switch entirely through React state — never let the browser's own default fragment-navigation run. If a link's `href` reflects data that changes when the active section changes (e.g. a "Next" link, whose target is always "whatever comes after the *new* active section"), React re-renders that same `<a>` with its `href` already pointing one section further along **before** the browser reads `href` to perform its default action — since that read happens synchronously right after the click's event listeners finish, it follows the just-updated (one-section-too-far) value instead of the one actually clicked. This is invisible in jsdom/Vitest (it doesn't perform real anchor hash-navigation), so it has to be verified in a real browser — see `HelpPage.tsx`'s `navigateToTopic`.
- **Sync state → URL in a `useEffect` keyed on the active id, not inside the click handler.** Writing to `window.location.hash` directly inside a component-defined callback trips `eslint-plugin-react-hooks`'s `react-hooks/immutability` rule ("modifying a variable defined outside a component or hook"); an effect is both what the lint error itself suggests and the architecturally cleaner shape (state is the single source of truth, the URL just follows it). A second effect listening for `hashchange` handles the reverse direction (browser back/forward, a bookmarked/shared link) — guard both directions with an equality check so they don't fight each other in a loop.
- **AppLayout's main content area scrolls itself (`overflow: auto`, `mainContentRef.current`) — the window/document never does**, since the app shell is pinned to `100dvh` with `overflow: hidden`. Any per-page "scroll to top on switch" or "back to top" needs the real scrollable ancestor (walk up from a ref via computed `overflowY`, same approach as `findVerticalScrollAncestor` in `csm-cases/utils/permalinkScroll.ts`), not `window.scrollTo`/`window.scrollY` — the latter silently never fires in production even though it can look like it works under Vitest, which lets a test mock `window.scrollY` directly regardless of real layout.

## Page conventions: Back navigation

- **Position**: a page's own Back button is always the *first* child rendered, above the title/header — never below a tab strip or any other content. See `UserProfilePage.tsx` and `CsmProjectDetailPage.tsx`'s local `BackButton` components for the reference shape (`variant="text"`, `size="small"`, `startIcon={<ArrowLeft size={16} />}`, `sx={{ alignSelf: "flex-start" }}`).
- **Resolving the target**: prefer `location.state.from` (set by whatever list/detail page the caller came from) over a hardcoded fallback path, so Back returns to the exact originating view rather than skipping past it to a generic list — e.g. `const resolvedBackPath = (location.state as { from?: string } | undefined)?.from ?? "/some/hardcoded/default";`. This is the established convention across `CsmProjectDetailPage.tsx`, `CsmCaseDetailPage.tsx`, `ProductVulnerabilitiesTab.tsx`, and the 4 case-type create pages below.
  - **Exceptions** (fixed-destination Back links, deliberately not `state.from`-aware): `CsmDashboardBuilderEditorPage.tsx`'s "Back to dashboards" — only ever reached from `CsmDashboardBuilderListPage.tsx`. `DashboardWidgetPreviewPage.tsx` hardcodes Back to `/dashboard` for a different reason — it's deliberately fully URL-driven (bookmarkable/shareable), not state-based, per its own doc comment. Don't generalize `CsmProjectDetailPage.tsx`'s pattern onto either of these; a genuinely-fixed-destination or genuinely-URL-driven Back link is fine to leave as-is. If a future caller ever links directly into the first one (bypassing its current single list page), revisit whether it still qualifies as fixed-destination.
  - **`CsmAdminLayout.tsx` used to be in this exception list** (a fixed "Back to User management" link for every `/admin/user-management/*` directory page, reasoned as "only ever reached via a tile on that grid"). That reasoning broke once `CsmUsersPage.tsx` gained a second entry point (a dashboard widget's `resourceType: "user"` click-through, which sets `state.from`) — reported live as a page whose Back always forced the tile grid regardless of where the user actually came from. `CsmAdminLayout.tsx` now reads `state.from` like every other page (falling back to the tile-grid index only when absent), and forwards `state.parentState` on Back so a multi-hop chain (dashboard → a directory page → a person's profile → Back → Back) still restores correctly. `CsmUsersPage.tsx` itself no longer renders its own Back button — the layout it's nested under (`CsmAdminLayout`) sees the exact same `location.state` and is the single Back button for every page it wraps, so a page nested under a layout that already renders Back should not also render its own. The takeaway: a "fixed-destination" Back is only safe while every caller is verified to reach that page the same single way — if a second entry point is ever added, the exception no longer holds and it needs to become `state.from`-aware like everything else.
  - **`DirectoryMemberPage.tsx` (backing `RoleMembersPage`/`GroupMembersPage`/`TeamMembersPage`) hit the exact same lesson a second time.** It used to hardcode Back to its own list (`/admin/roles`, `/admin/groups`, `/admin/teams`), reasoned as "only ever reached from the directory list" — true until `DirectoryEntityChip.tsx` (a clickable role/team/group chip, rendered on a case's meta band, an account's detail page, and a user's profile) started linking straight into these same pages too, none of which set any `from`. Reported live as "Back to Teams" from a case always landing on the plain Teams directory instead of back on the case. Fixed the same way: `DirectoryEntityChip.tsx` now passes `state: { name, from: \`${location.pathname}${location.search}${location.hash}\` }`; `DirectoryMemberPage.tsx` reads `state.from`, falling back to its own `listPath` only when absent (a direct/shared link, or the entity's own directory row — which still doesn't set `from`, since for that one caller `from` and `listPath` are the same place anyway); and the label changed from `Back to {listLabel}` to plain `Back` now that the destination is dynamic (the `listLabel` prop was removed entirely, since nothing else used it). `DirectoryMembersList.tsx`'s own row-to-profile links got the matching treatment (`state: { from: <this member list's own location> }`) for the same reason — `UserProfilePage.tsx` already preferred `state.from` over its `navigate(-1)` fallback, it just wasn't being supplied from here. Same takeaway as `CsmAdminLayout.tsx` above, and worth re-checking `CsmDashboardBuilderEditorPage.tsx`/`CsmAnnouncementCreatePage.tsx` (the latter not `state.from`-aware today, safe only because nothing links to `/announcements/new` except the top-level Announcements list) if either one ever gains a second entry point.
- **`location.state` belongs to the route, not the component that reads it.** A component embedded as a sub-tab of a page (e.g. `CsmIssuesView` reused inside a project's `WorkItemsTab`) still sees whatever `from` the *outer* route was reached with, even though the embedding itself isn't a navigation. A page-level component with its own Back button needs an explicit opt-out prop (e.g. `hideBackButton`) before it can be safely embedded inside another page that already has its own Back button — otherwise both render, pointing at the same destination. Never reuse a standalone page's component as an embedded tab without checking for (and passing) this escape hatch. A parent *route layout* rendering the Back button for all of its child routes (`CsmAdminLayout.tsx`) is the same principle one level up: a child page nested under such a layout must not also render its own Back button.
- **Label the button "Back", not "Back to X"**, whenever its destination is resolved dynamically (i.e. can be `state.from` or a hardcoded fallback) — a fixed "Back to cases" label reads wrong once the button might actually be returning to a project instead. Reserve a destination-specific label for a button whose target is genuinely always the same place (see the `CsmDashboardBuilderEditorPage.tsx` exception above) — `CsmDashboardSharedConfigPage.tsx`'s Back-shaped control used to be labeled just `Dashboards` instead of `Back`/`Back to dashboards`, a cosmetic inconsistency fixed alongside the `DirectoryMemberPage.tsx` relabeling below even though its own destination genuinely is fixed.
- **Project → create-flow → new entity's Back must round-trip through the project, tab included.** `CsmProjectDetailPage.tsx`'s "Create case"/"Create service request"/"Create engagement"/"Create security report" menu items pass `state: { from: projectPath }` when navigating to `/cases/new`, etc., where `projectPath` is `` `${location.pathname}${location.search}` `` — not just the bare `/customers/projects/:id`. Each create page (`CsmCaseCreatePage.tsx`, `CreateServiceRequestPage.tsx`, `CsmEngagementCreatePage.tsx`, `CreateSecurityReportPage.tsx`) reads that same `from` for its own "Back"/"Cancel" buttons (`backTarget = backState?.from ?? "<its own default list>"`), **and** forwards it as `state: { from: backTarget }` on the `navigate(...)` call after a successful create — so the newly created case/engagement/report's own detail page (all backed by `CsmCaseDetailPage.tsx`, which already reads `location.state.from`) returns to the project instead of falling back to that entity type's generic top-level list. Any new "create X from a project" flow must follow this same three-hop chain (project → create page → new detail page), not just the first hop.
  - `CsmProjectDetailPage.tsx`'s own `activeTab` and `WorkItemsTab.tsx`'s own `subTab` are both kept in the URL (`?tab=`/`&subTab=`), not local `useState`, specifically so `projectPath` above captures them — a round trip through a create flow (or any other page navigated away to) restores the exact tab the engineer was on, not just the bare project page defaulting back to Overview. Any project-level tab strip that needs to survive a similar round trip should follow the same URL-backed pattern rather than local state.

## Theming: never branch on `palette.mode`

This app drives theming through MUI CssVars (`CssVarsProvider`/`useColorScheme`, via `ThemePreferenceProvider` → oxygen-ui's own theme provider), where **`theme.palette.mode` stays pinned to the default scheme regardless of which one is actually rendering** — a `mode === "dark"` check silently always takes the light branch. It fails at runtime, in one scheme only, with no type or lint error, which makes it expensive to spot: it shipped a case-tab strip whose active tab rendered white-on-white (invisible label) in dark mode, and the same trap had already been hit in `CaseMetaBand.tsx` and `PinThisPageButton.tsx`/`RecentViewsButton.tsx` before that.

Scope per-scheme styling with `theme.applyStyles("dark", { … })` instead, which emits a scheme-scoped selector: write the light/default values as the plain style object and spread the dark overrides over them. See `CaseTabStrip.tsx`'s `activeTabFillStyles`, `CaseMetaBand.tsx`, and `config/a11yThemeOverrides.ts`.

Two knock-on rules:
- **Reach for a per-scheme branch only when the two schemes genuinely need *different colors*, not a different token.** Most "make this stand out" styling should use the relative `action.*` overlay tokens (`action.hover`, `action.selected`), which MUI defines to always increase prominence against the ambient surface in *either* scheme. The absolute tokens (`background.default`, `background.paper`, `text.primary`, …) flip their real lightness between schemes and are the wrong tool for "the currently-emphasized one of several equal siblings" — using `background.default` for a selected item renders it as the *darkest* thing on screen under the dark theme.
- **A styling helper that needs the theme has to return an `sx` callback, not an object** — and every call site then passes it through directly (`sx={helper(x)}`) or uses `sx`'s array form (`sx={[helper(x), { … }]}`) to add its own styles. Spreading a callback into an object literal (`sx={{ ...helper(x), … }}`) type-checks fine and silently drops every style it contains.

## Table conventions

Every paginated data table backed by a real MUI `<Table>` (`ProductVulnerabilitiesTab.tsx`, `DirectoryEntityTable.tsx`, `ChangeRequestsTab.tsx`, `IncidentsTab.tsx`, `ProblemsTab.tsx`) should match this shape — a new one should too. (`ConversationsTab.tsx` used to be listed here too, but it's actually a hand-rolled CSS Grid like `CasesList.tsx` below, not a real `<Table>` — it just has no long-text column today, so the gotcha two paragraphs down doesn't currently apply to it.)

- **Wrapper**: `<Box sx={{ border: 1, borderColor: "divider", borderRadius: 1, overflow: "hidden" }}>` around `<TableContainer>`, not `<Paper variant="outlined">` (the two render visually differently; `Box` is the established one). `TablePagination` (when present) is a sibling of `TableContainer`, inside that same `Box`. `TableContainer`'s own built-in `overflow-x: auto` is what makes a wide table scroll horizontally instead of squishing its columns — don't strip or override it.
- **`<Table size="small" sx={{ "& .MuiTableCell-root": { borderColor: "divider" } }}>`**, with the header row as `<TableRow sx={{ bgcolor: "action.hover" }}>` — a plain `<TableRow>` header with no `sx` reads inconsistently against tables that do set it.
- **Loading skeleton row count must equal the current page size**, not a hardcoded number — `Array.from({ length: rowsPerPage })` (or a `skeletonCount` prop threaded through, per `CasesList.tsx`), so switching "rows per page" to 50 shows 50 skeleton rows, matching what's about to load. A hardcoded `Array.from({ length: 3 })` is the recurring mistake to avoid (it doesn't scale with the selected page size and reads as a different, lesser table). A table with no pagination at all (e.g. `ProjectContactsTab.tsx`, which loads every row up front) has no page-size state to tie to and a small fixed skeleton count is fine there.
- **`TablePagination`**: include `showFirstButton`/`showLastButton` alongside the usual `count`/`page`/`onPageChange`/`rowsPerPage`/`onRowsPerPageChange`/`rowsPerPageOptions`.
- **Status chips default to `variant="outlined"`** (`SemanticChip`/`Chip`), matching `deriveAccessStatus`/`deriveProjectAccessStatus`/registration chips — a filled chip reads as heavier/more alarming than intended for routine status values. `StateChip` (case lifecycle state specifically) is a deliberate, documented exception that renders filled/solid — don't generalize from it to other chips.

**`CasesList.tsx` is the one exception to "real `<Table>`"**: it's a hand-rolled CSS Grid (`display: "grid"` + `grid-template-columns: subgrid` per row), not `<Table>`/`<TableContainer>` — this doc used to (incorrectly) list it alongside the real-`<Table>` group above, which hid a real bug: a CSS grid container's automatic minimum width lets its tracks shrink below their own `minmax(...)` floor to fit whatever space is available, so without `TableContainer`'s built-in scroll behavior, a wide `CasesList` squished/clipped its column content instead of scrolling once several optional columns were on at once. Fixed by wrapping the grid in its own `overflowX: "auto"` layer and giving the grid itself `minWidth: "max-content"` (forces it to only ever overflow that scroll layer, never shrink its own tracks) — the general shape to reuse for any *other* CSS-grid-based table this app ever grows, since `TableContainer`'s convention above doesn't apply to it.

**That same `minWidth: "max-content"` fix has its own follow-on gotcha: it makes *any* free-text column — default or optional — able to force the whole grid to scroll far past what the column count alone would justify**, on the strength of a single unusually long value in just that one column. First reported for a long case Subject with zero optional columns on; then again for Security Reports' Product column (an *optional* column) — same mechanism, different column, because only Subject got the fix the first time. `noWrap`'s ellipsis (used throughout this file — Subject, product, customer, assignee, createdBy) only clips *paint*; it has no effect on a grid item's intrinsic max-content sizing, which is what `minWidth: "max-content"` on the container actually keys off. The fix is a real `maxWidth` (a fixed px value, not a percentage) on the cell's own wrapping `Box` — a grid item's specified max-width *does* clamp its max-content contribution to track sizing, unlike `overflow`/`text-overflow`. Every free-text column now has one: Subject's own `Box` gets `maxWidth: 360` (matching the same Subject column's own already-proven cap on `ChangeRequestsTab.tsx`/`IncidentsTab.tsx`); every optional column's shared wrapper (`effectiveOptionalColumns.map`) gets `maxWidth: 260` uniformly, whether that particular id renders free text (product, customer, assignee, createdBy) or something already-bounded (a `Chip`, a relative-time string) — capping the bounded ones costs nothing and closes the gap for any future optional column type without having to reason per-id about which ones are "safe." The design intent this preserves: adding *more* optional columns (each reasonably capped) needing more total width, and therefore scrolling, is fine and intended — it's *one column* growing disproportionately from a single outlier value, default or optional, that's the bug.

**Pick the cap small enough that the *sum* still fits a normal viewport, not just "bounded."** Subject's cap started at `480` — comfortably bounded against any one pathological value, but 480 (Subject) + 260 (one default-visible optional column, e.g. Security Reports' Product) + the other default columns' own floors still summed to more than a typical content-area width, so the *default* view scrolled horizontally even with everyday-length values, not just outliers — reported live right after the first fix shipped. A cap has to solve both problems at once: bound the worst case, *and* keep the realistic default-view total within a normal viewport. When in doubt, match a value already proven elsewhere in the app for the same semantic column (Subject's `360` here now matches the real-`<Table>` versions) rather than picking a new one that merely "seems reasonable."

**The same class of bug exists in every real `<Table>` too, via a different mechanism, and was found across most of them.** `TableContainer`'s `overflow-x: auto` (the convention above) makes the table scroll instead of squishing — but with the default `table-layout: auto`, a `<TableCell>` holding unbroken free text still has no upper bound on its own, so one long value (a name, a subject) forces that column — and the whole table, via the same scroll behavior — wider than intended, even with nothing else going on. `noWrap` alone (an ellipsis) doesn't fix this any more than it does for the CSS Grid case above: it only clips paint, and `table-layout: auto`'s column-width calculation isn't affected by it. A real `maxWidth` (fixed px, on the `TableCell` itself; a percentage `width` is not a reliable substitute — an unbroken token like a URL can still overflow it) is what actually caps it. Fixed in `ProductVulnerabilitiesTab.tsx` (Component/Product), `DirectoryEntityTable.tsx` (Name), `TasksWidget.tsx` (subject — found with *no* truncation treatment at all), `LinkedChangeRequestsWidget.tsx` (name), `CsmAccountsPage.tsx`/`CsmProjectsPage.tsx` (name), `CsmAnnouncementsPage.tsx` (subject — had a percentage width already, now also has a px cap), and the `UserRefLink` identity cell in `DirectoryMembersList.tsx`/`CsmUsersPage.tsx`/`ProjectContactsTab.tsx`/`CsmAccountDetailPage.tsx`. `ChangeRequestsTab.tsx`/`IncidentsTab.tsx`/`ProblemsTab.tsx` already had this right (`maxWidth: 360`/`480` on the Subject `TableCell`) — that's the reference shape for any new real-`<Table>` column holding freeform text.

**Per-table "Customise columns" control (`ColumnCustomizerButton` + `useColumnPreferences`) belongs next to the table it controls, not in a page header far away from it.** `CasesList.tsx` takes a `columnCustomizer?: ReactNode` prop and renders it in a small toolbar row directly above its own grid; the caller (`CsmIssuesView.tsx`, or a dashboard widget's own preview page) builds the actual `<ColumnCustomizerButton>` (it alone knows that view's `viewId`/available columns/defaults) and passes it through. This split — table renders the slot, caller owns the state — is what let `DashboardWidgetPreviewPage.tsx`'s case-family widget preview gain the exact same column customization the main Cases/Service requests/Security reports/Engagements tabs already have, just by wiring its own `useColumnPreferences` and passing the button into the same prop, without `CasesList` needing to know anything about dashboards. Follow this pattern (a `columnCustomizer`/similar slot prop on the reusable table, not a control baked into one specific page's header) for any other reusable table that gains per-view column customization.

**`ColumnCustomizerButton`'s picker reorders columns by dragging a grip handle** (native HTML5 drag-and-drop — `draggable` + `onDragStart`/`onDragOver`/`onDrop`, no library), not the up/down chevron pair it used to have. The handle's focus + arrow-up/down keys still call `useColumnPreferences`'s `moveColumn` (one slot at a time) as the keyboard-accessible fallback, since native drag-and-drop has no keyboard path of its own — losing that would've been a real accessibility regression, not just a visual one. The drop itself calls a *different* hook method, `reorderColumn(id, targetIndex)`, not a repeated `moveColumn`: `moveColumn` is a `useCallback` closing over that render's `state`, so calling it more than once inside the same synchronous drop handler (which a multi-slot drag needs) would have every call act on the same stale `state.order` and net only a single-slot move no matter the actual drop target. `reorderColumn` computes the whole new order in one atomic update instead. Any future "reorder by dragging, multiple slots in one gesture" UI on a `useColumnPreferences`-backed list should reuse `reorderColumn`, not try to loop `moveColumn`.

**`CasesFilterBar.tsx`'s "Quick filters"/"Advanced" toggle stashes-and-restores instead of disabling.** The Quick filters grid can't represent every filter shape the Advanced builder can (an OR group, `tags`, certain operators) — clicking Quick filters used to just be `disabled` whenever the active filter had anything like that, with no way to even look at the Quick filters grid without first clearing it by hand. It's unconditionally clickable now: clicking it while not Simple-representable resets the active filter to `DEFAULT_CASES_FILTERS` (preserving `search`, which is shared by both modes and edited independently of this toggle) — Quick filters must never silently keep an Advanced-only criterion applied behind a grid that can't display it — but stashes the previous value in local state first, so an accidental click doesn't lose real filter criteria: clicking straight back to Advanced restores it. That stash is dropped the moment a real edit happens in Quick filters (routed through `handleSimpleFieldChange`, not `onChange` directly) — restoring stale Advanced criteria over a filter the user just deliberately changed would be its own kind of surprising data loss. Any other "switching view A to view B loses some of A's state" toggle in this app should follow the same shape: clear-with-a-stash-and-restore, not a disabled control with no path forward.

## Runtime feature flags: `CSM_MIGRATION_*`

Alongside the per-page `CSM_PORTAL_FEATURE_OVERRIDES` map, customer-onboarding cutover features are gated by individual boolean `window.config` keys named `CSM_MIGRATION_<FEATURE>_ENABLED` — the **same name as the backend env var** that registers the route the feature calls, so a deployment flips one name on both sides. Each has a small reader in `src/config/<feature>Config.ts` (e.g. `onboardingStatusConfig.ts`'s `isOnboardingStatusEnabled()`) that returns true only for `true` or the string `"true"` (platform config injection often stringifies) and is read **at call time**, not module load like `apiConfig.ts`, so tests set `window.config` per case. Off is the default and must mean *no behaviour change*: the UI is not rendered **and** the data hook is disabled (`enabled: !!id && isXEnabled()`), so no request is ever made — a hook still has to be called unconditionally for stable hook order, hence gating inside it rather than around it. The key is declared on `Window["config"]` in `authConfig.ts`, listed in `public/config.js.example` and README's runtime-config table.

- `CSM_MIGRATION_ONBOARDING_STATUS_ENABLED` → the **Onboarding column** on `ProjectContactsTab.tsx`. `useGetProjectOnboardingSteps.ts` (`GET /projects/{id}/onboarding-steps`, already grouped per membership and paged through by the backend, so no client-side paging loop) is matched to contact rows **by lower-cased email** (`utils/onboardingStatus.ts`'s `indexOnboardingMembershipsByEmail`/`findOnboardingMembership`) because `BeProjectContact` carries no membership or `project_contact` id; a re-invited address keeps its most recently updated membership. `summarizeOnboarding` collapses a membership's steps to the worst status (FAILED > SKIPPED > SUCCEEDED > none → dash), naming the steps concerned in the chip (`Failed: EMAIL`, `Skipped: IDENTITY, EMAIL`); all-SUCCEEDED reads `Completed` once REGISTRATION is recorded and `In progress` before, since the ledger has no pending state (an unrecorded step is simply absent). `OnboardingStatusChip.tsx` puts every step, its attempt count and a FAILED step's `lastError` in a hover `Tooltip` — `lastError` is upstream error text and is rendered through React's normal text escaping, never `dangerouslySetInnerHTML`. Ledger loading/failure only affects that column (skeleton / "Unavailable" with the error on hover); the contacts query is untouched. A `truncated` response marks the header `(partial)`.

## Data fetching

TanStack React Query is the only data-fetching layer — no other state-management library. Custom hook naming is verb-prefixed and consistent:

- `useGetX` — read a single resource (`useGetCsmCaseDetail`, `useGetAccount`, `useGetUsersMe`)
- `usePostX` / `usePatchX` — mutations (`usePostCsmCase`, `usePatchUsersMe`)
- `useSearchX` / `useXOptions` — typeahead/autocomplete queries
- Plain domain-named hooks for composed/derived state (`useCaseComposition`, `useIsTeamLead`)

**A `useQuery` hook backed by a paginated `POST /.../search` endpoint must page through every result, not just fetch page one.** `useGetCsmCaseComments`/`useGetCsmCaseActivities`/`useGetCsmIncidentComments`/`useGetCsmIncidentActivities`/`useGetCsmChangeRequestComments` used to each issue exactly one request with `pagination: { offset: 0, limit: BE_MAX_PAGE_LIMIT }` and never look at the response's own `hasMore`/`total` — silently dropping every comment/activity past the first `BE_MAX_PAGE_LIMIT` (50) on any heavily-discussed case/incident/change request, independent of and in addition to the print-CSS truncation below (reported live as "printing a case only shows a single page and drops most comments" — two separate bugs behind one symptom). Fixed with a bounded `for` loop that accumulates every page into one array before mapping, breaking on `rows.length < PAGE_LIMIT || !response.hasMore` (a `MAX_..._PAGES = 200` safety bound guards against a wrong/always-true `hasMore`) — see any of the five hooks above, or the pre-existing precedent this mirrors, `useFindMyOngoingCases.ts`'s own paged-loop. Apply the same shape to any future hook wrapping a `BeSearchResponseBase`-shaped (`{ total, limit, offset, hasMore }`) endpoint whose result set isn't guaranteed to fit in one page. `useCsmConversationMessages.ts`/`useCsmCaseAttachments.ts` deliberately keep the single-page shape — each has its own doc comment reasoning why that list is expected to stay short — so a hook backed by this same response shape isn't automatically wrong just for not paging; check whether it actually needs to.

## Filter-bar date ranges must cap at "today" — a picker's own `minDate`/`maxDate` is not enough

Every filter bar offering a from/to date range (`IncidentsFilterBar`'s "Created (UTC)", `ChangeRequestsFilterBar`'s "Closed", `CsmTimeCardsPage`'s `FilterBar` "Work date") caps both ends at the current date — none of these events (an incident being created, a case closing, time being logged) can happen in the future, and letting a picker offer those dates invites a filter that silently never matches anything. Each of the three implements this the same way:

- A local `today...DateOnly()` helper, recomputed **every render** (not `useMemo(..., [])`, which would freeze "today" at the component's mount time and stop matching once a session is left open past a day boundary) — `todayUTCDateOnly()` when the backend interprets the field as a UTC calendar day (Incidents' created dates, Change Requests' closed dates — both sent to the backend as `T00:00:00Z`/`T23:59:59Z`), or a plain local-midnight `todayDateOnly()` when the field has no UTC labeling (time cards' `workDate`, a plain calendar date).
- The "from" field's `maxDate` is `min(today, the "to" field's current value)` — not just `today` outright — so it still can't cross past whatever "to" is already set to.
- The "to" field's `maxDate` is `today` directly (plus its pre-existing `minDate` pinned to "from").
- **The same bound must also be enforced in the onChange handler itself, not just the picker's `maxDate` prop** — MUI's DatePicker still fires `onChange` for an out-of-range value typed directly into the text field, bypassing the calendar popup's own UI-level constraint entirely.

A new date-range filter should follow this exact shape rather than only setting `minDate`/`maxDate` and assuming that alone blocks a future date.

## Native print (Ctrl+P / Cmd+P) vs. "Export as PDF" — two distinct mechanisms

Reported live: native print truncated a case to one page/dropped most comments, AND (unlike ServiceNow) there was no dedicated export button. These are two separate fixes, not one:

- **`src/styles/print.css`'s `.csm-print-expand` class fixes native Ctrl+P/Cmd+P** by defeating `overflow`/fixed-height ancestor containers under `@media print` (a browser print engine clips an `overflow:auto`/`hidden` box to its on-screen height instead of paginating its content) — applied up the specific ancestor chain from `AppLayout` → `AppShellLayout` → the case-tabs content host → `CaseTabIsolatedRouter`'s per-tab scroll container. A real bug (reported live — printing a case truncated to one page) survived an earlier PR's own CSS fix because that PR's test never exercised the *real* component tree: `AppShellLayout.tsx`'s `main` `Box` pairs `flex: "1 1 0"` with a literal `width: 0` (a common "never grow past your allotted flex share" trick) — harmless on screen, but once `.csm-print-expand`'s `flex: none !important` takes that box out of flex layout under print, the same literal `width: 0` becomes a real block-level constraint instead of an inert flex-basis, collapsing that box (and every `width: 100%` descendant resolving against it) to zero. `.csm-print-expand` now also resets `width: auto !important; min-width: 0 !important` for exactly this reason. Any *new* container added to this print-expand chain needs the same width/min-width reset checked, not just `height`/`overflow`/`flex` — and needs verifying against the real component tree (jsdom can't validate `@media print` layout), not a synthetic isolated test. This mechanism is otherwise untouched/unrelated to the export button below — Ctrl+P still renders the on-screen UI, just correctly paginated now.
- **"Export as PDF" (`@components/ExportPdfButton`) is a *different* feature**, added to `CsmCaseDetailPage.tsx`/`CsmIncidentDetailPage.tsx`/`CsmChangeRequestDetailPage.tsx`'s Back-button row (wrapped in a `Box(display:"flex", justifyContent:"space-between")` so Back stays left-aligned; success-render path only). It does **not** call `window.print()` — it builds an actual standalone report document with `jsPDF` (already a dependency — see `features/updates/utils/updateReportPdf.ts`, the pre-existing PDF export this one's structure is modeled on: a manual `{ doc, y }` cursor, `writeWrapped`/`ensureSpace`/word-wrap via `splitTextToSize`, no HTML/DOM rendering). Shared drawing helpers live in `@utils/pdfReportKit`:
  - **`writeReportHeader`** — a colored band with the title/subtitle, the report's one "branding" touch.
  - **`writeDetailsTable`** — a real `jspdf-autotable` table for a case/incident/CR's compact key/value fields (a table works well here: short, bounded-length values). A row can carry a `colorRole` — `error`/`warning`/`success`/`info`/`default`, approximating this app's own chip-color roles — to render a state/severity/priority/impact value in status color.
  - **`writeActivityList`** — the full activity trail (comments, audit entries, attachments, feedback), rendered as a free-flowing list (a bold "When · Actor · Type" line, then a full-width paragraph), **not** a table. It *was* a `jspdf-autotable` table (`writeActivityTable`) originally, matching `writeDetailsTable`'s look — reverted after live feedback: a table cell has to accommodate the single longest wrapped entry in the whole report, and unlike the compact details fields, a comment can be arbitrarily long, so a handful of long comments ballooned the report's page count and squeezed the Details column into awkward narrow wrapping. `writeDetailsTable`'s table format was explicitly kept, since that concern doesn't apply to short key/value fields.
  - Plus the lower-level `writeWrapped`/`writeHeading`/`ensureSpace`/`writeBulletList`/`writeKeyValueLine`/`writeDivider`/`stampFooterPageNumbers`/`safeFileNamePart`/`condenseBlankLines`/`htmlToPdfPlainText` primitives underneath — so a third report generator doesn't have to re-derive the same page-break/list math.

  Each entity type has its own thin generator (`csm-cases/utils/caseReportPdf.ts`, `csm-operations/utils/{incidentReportPdf,changeRequestReportPdf}.ts`) building on that kit and pulling in most of that entity's own detail-endpoint fields (not just a curated handful), since case/incident/change-request each have a different field shape and there's no single generic "detail entity" type to render from.

  - **Rich-text HTML (case `description`, a CR's plan fields, a comment body) must go through `htmlToPdfPlainText` (`@utils/pdfReportKit`), never `@utils/sanitizeHtml`'s `stripHtmlTags`.** `stripHtmlTags` is built for "a subject line stored as plain text" (its own doc comment) and works by removing every tag via DOMPurify (`ALLOWED_TAGS: []`) before reading `textContent` — which has no concept of block boundaries, so `<p>Hi Team,</p><p>We need...</p>` collapses to "Hi Team,We need..." with nothing between them. Reported live: real multi-paragraph/bulleted rich-text content (an outage request with a paragraph intro and a bulleted "Request Details" list — normal, legitimate authoring) rendered in the PDF as a single run-on wall of text, while the identical content rendered correctly, properly spaced, on screen. `htmlToPdfPlainText` instead sanitizes with `sanitizeRichTextHtml` (the same pass used for on-screen `dangerouslySetInnerHTML` rendering, so it keeps block tags) and walks the resulting DOM itself: a block element (`p`/`div`/`li`/`ul`/`h1-h6`/etc.) gets a trailing newline once its children are done, `<li>` gets a leading "• ", and `<br>` becomes a newline — while a purely inline element (`<strong>`/`<em>`/`<a>`/`<span>`) contributes no break of its own, so `<strong>Short Description:</strong> Test outage...` still reads as one line, matching how it looks on screen. Always pipe the result through `condenseBlankLines` afterward (nested block structure can still produce more than one blank line between real paragraphs). Any future PDF report generator must use `htmlToPdfPlainText` for the same reason — `stripHtmlTags` silently drops structure it was never designed to preserve.
  - **The activity list must cover every lane `CaseActivitiesFeed.tsx` merges into its own on-screen feed, not just comments.** That component's "N entries" badge (`CsmCaseDetailPage.tsx`) counts across *four* lanes: `comments` (itself already including the pre-case chat transcript — `mergedComments` on that page), the separate `useGetCsmCaseActivities`/`useGetCsmIncidentActivities` audit-trail query, uploaded attachments, and CSAT feedback submissions. This was fixed in two passes, each reported live as still incomplete: the first pass added only the audit trail (reported as "not getting all the comments"/"all activity response should be there" persisting even after that fix); the second pass added attachments and feedback (case) and attachments (incident) once it was clear the export still didn't match the on-screen "N entries" count. `generateCaseReportPdf`/`generateIncidentReportPdf` now take the full set of parameters each page already has loaded for its own feed — `(detail, comments, activity, attachments, feedback?)` — no extra fetches, just wiring what's already on the page through to the export. Each page must pass the *same* values it passes to its own `CaseActivitiesFeed` (`mergedComments`/`comments`, `activityAudit`, `attachmentList`, `caseFeedback`), not a narrower query result, and `ExportPdfButton` must be `disabled` while any of those queries (comments/activity/attachments/feedback/chat) are still loading — otherwise the export can silently ship built from a partial feed. A field change becomes one plain-text line via `describeAuditEntry` (`@features/csm-cases/utils/caseActivityFeed` — "Label: old → new", multiple changes in one transaction joined with `;`, falling back to the entry's own `description` for an older/synthetic entry with no structured `changes`); an attachment becomes `"<filename> (<size>)"` via `@utils/formatBytes`; feedback becomes `"<ratingLabel>: <comment>"` (or just the rating label with no comment). All rows merge into one array and sort by raw ISO timestamp — never the already-formatted display string, which doesn't sort chronologically as plain text — before being handed to `writeActivityList`, whose heading reads `"Activity (N entries)"`, matching the on-screen badge's own wording exactly rather than a bespoke breakdown that has to be kept in sync by hand. Change requests have no audit-trail *or* attachments lane in their on-screen feed at all (`CsmChangeRequestDetailPage.tsx` itself passes `audit={[]}`/`attachments={[]}` to its own `CaseActivitiesFeed`), so `generateChangeRequestReportPdf` stays comments-only — genuinely everything the API/on-screen feed has for a change request, not an oversight. **Before trusting that a report generator is "complete," diff its parameter list against the exact props the same page passes to its own `CaseActivitiesFeed` — that's the authoritative list of lanes, not the generator's own doc comment.**
  - **`writeHeading`'s level-2 accent underline needs real clearance before the next content, not just its own tight `PDF_LINE_HEIGHT` gap.** The underline used to sit only ~5mm below the heading text's own baseline, then just 2mm before the next line of body text began — tight enough that a normal 10pt line's ascenders (~2.5mm above its own baseline) reached back up past the underline, rendering as a stray horizontal line struck through the first line of text under *every* level-2 heading in the report (reported live, visible under "Description" and, on inspection, every other section). Fixed by widening that specific post-underline gap to 4mm. Any future change to heading spacing needs to re-verify this specific overlap, not just "does the heading look fine on its own."
  - **`writeDivider` (the rule between `writeActivityList` entries) uses its own distinct, more prominent styling — `PDF_STRONG_DIVIDER_COLOR` ([165,171,181], a visibly darker gray) plus a heavier 0.4 line width — rather than reusing `PDF_DIVIDER_COLOR`.** That constant stays as originally tuned, for `writeDetailsTable`'s own subtle grid lines: a rule meant to be barely-there *inside* a bordered table reads as basically invisible when it's the only visual separator between two full activity entries in an otherwise plain list (reported live). `writeDivider` also leaves a real margin (5mm) *after* the rule, not just before it, so the next entry's own "When · Actor · Type" line doesn't feel like it's crowding the divider.
  - **A state/field-change description's "old → new" arrow must go through `toPdfSafeText`'s punctuation-fallback map, or it silently disappears.** `describeAuditEntry` (`@features/csm-cases/utils/caseActivityFeed`) builds its text with a real Unicode "→" — outside jsPDF's WinAnsi/Latin-1 range same as any other non-ASCII character — which the safe-text filter used to just drop with nothing in its place, rendering as "State: Open  Work In Progress" with a blank double-space gap where the arrow belonged (reported live). Fixed by adding `"→": "->"` (and `"←"`/`"⇒"`) to `PDF_PUNCTUATION_FALLBACK` in `@utils/pdfReportKit`, the same mechanism already used for curly quotes/em-dash/ellipsis. Any future report content built with a Unicode arrow (or similar decorative character) needs a fallback entry here too — `toPdfSafeText` has no "render unknown glyph as a placeholder" behavior, unmapped-and-out-of-range always means silently dropped, not visibly wrong.
  - **A comment's `bodyHtml` must go through `commentContent.ts`'s cleanup pipeline before `stripHtmlTags`, not straight through it** — all three report generators call `preprocessCommentBodyHtml` (unwraps `[code]` wrapper tags / renders bot Markdown, then strips the backend sync layer's own "Customer comment added" label) and filter the comment list through `hasDisplayableContent` first. Skipping this (as the PDF export originally did) reproduces a real, previously-fixed bug one level up: `CsmCaseCommentBubble.tsx` already runs every on-screen comment through this exact pipeline (and already hides a comment `hasDisplayableContent` says has nothing left to show) for the same reason — some backend-synced entries carry no real message at all, just that literal label — reported live as the PDF report showing whole rows of "Customer comment added" as if that were the actual comment text, instead of either the real message or (for a label-only sync entry) not being listed at all. `preprocessCommentBodyHtml` (`@features/csm-cases/utils/commentContent`) is the shared extraction of that bubble's own preprocessing memo, kept in one place so a future fix to the pipeline (a new label variant, a new `[code]`-wrapper quirk) only has to happen once and reaches every consumer — the bubble, and any current or future non-bubble renderer of comment content (PDF export today).
  - **Every string drawn into the PDF routes through `toPdfSafeText` first** (inside `writeWrapped`/`writeReportHeader`/the table helpers — no call site needs to remember this itself). jsPDF's standard "helvetica" font only supports the WinAnsi/Latin-1 character set; a display name (or any other free text) carrying an emoji, flag/regional-indicator sequence, or a zero-width/invisible character from its source system renders as visibly garbled, widely-spaced gibberish instead of failing loudly — reported live as a name ending in stray characters like "$æ". `toPdfSafeText` iterates by Unicode code point (`Array.from`, not raw UTF-16 indexing, so a surrogate-pair emoji is consumed as one unit rather than leaving an orphaned half behind), maps common "smart" punctuation (curly quotes, em/en dash, ellipsis, nbsp) to its plain-ASCII equivalent, and drops everything else outside 0x20-0xFF. Any new PDF report generator must draw text through this kit's helpers (not raw `doc.text`/an autoTable `body` built without it) to get this for free.
  - `jspdf`/`jspdf-autotable` are dynamically `import()`ed from each page's `handleExport*Pdf` callback (not statically imported), matching the Updates feature's own convention of keeping them out of the main bundle; unlike that existing precedent, this callback wraps the import in a try/catch and surfaces a failure via `showError` (`ExportPdfButton` itself just tracks the pending/disabled state — it doesn't swallow the error, the caller owns reporting it). The button is disabled while that page's own comments query is still loading, so an export can't ever be built from a partial comment list.

## Change request form: customer project, deployments, deployment products, customer group

The change request create page and edit dialog share `useChangeRequestScope` (`features/csm-operations/hooks`) and `ChangeRequestScopeFields` (`features/csm-operations/components`) for **Customer Project -> Deployments / Deployment products**, plus a read-only **Customer Group** (`ChangeRequestCustomerGroupField`, same file). The hook owns the cascade; its single data source is `useChangeRequestScopeLookups` (`POST /change-requests/link-options`), which returns the project's deployments (each with its `type` — a deployment already carries its environment role, so there is **no Environments field**), the project's `customerContacts` and, for the deployments chosen so far, the deployment products that follow.

- Changing or clearing the project clears the deployments below it and re-derives the Customer Group. Deployment products are never picked — they are derived (`productsReady` is false while the lookup for the current selection is in flight, and the products are then not sent).
- **Customer Group is read-only and derived.** It is the chosen project's registered contacts (the people asked at the customer gates, who answer in the customer portal), shown as name chips with a lock icon, helper "Derived from the customer project's registered contacts" ("Select a Customer Project first." / "—" until a project is chosen, "No registered contacts on this project…" when empty). It is not form state, not in drafts or clones, and **never sent**: the backend refuses `customerGroupId` (and `environmentIds`) with a 400. The detail page shows the same list from `customerContacts`; at a customer gate with an empty list the Approval tab explains that no customer approvers were assigned (`noCustomerContactsHelper`).
- **Refusals of the create are worded by the entity service and shown as written.** A person with no ServiceNow account (a user created in this database, which nothing in the web can tell apart in the picker) or an assignment group ServiceNow does not have is refused by the create itself with a 400 that says who or what cannot be used, why, and which field to change. The create form shows every 4xx message of the entity service as written in its error banner (`CreateChangeRequestPage` `onError`), so keep that wording on the entity-service side and do not replace it with a generic message here.
- Sent only when non-empty. The create page sends `projectId`, `deploymentIds`, `deploymentProductIds` (plus `category`, `comment`, `workNote`); the edit dialog sends the three scope fields **together** when any of them changed (the backend validates them as a unit), and not at all once the CR has reached `implement` (the dialog locks the deployments with the reason; the backend refuses from there on). The **Customer Project itself is editable only in New** (see the next section): after New the dialog shows it read-only and, when only the deployments changed, sends the stored project beside them, which the backend accepts as a no-op. A saved project can be swapped (in New) but not cleared (the patch cannot express "no project").
- Clone carries the project and category, but deliberately **not** deployments / products: they name the deployment the change targets, and a clone exists to promote the change to another one. A draft or clone from before this change may still hold `customerGroupId` / `environmentIds`; they are ignored (not read, not re-saved).
- The draft keeps display names next to the ids (`*Labels`), because the pickers only know ids; without them a restored form shows raw UUIDs.
- The detail response's `category` is the enum value (or an `{id, name|label}` ref on older responses) — always read it through `changeRequestCategoryValue` / `changeRequestCategoryLabel`.
- e2e: `tests/e2e/utils/fakeChangeRequestApi.ts` fakes the whole slice (projects, link-options with per-project contacts, create, PATCH, detail) with the backend's own validation (including the `customerGroupId` / `environmentIds` refusals), so the cascade, wire payload, 400 path and lifecycle are tested without creating records anywhere.

### The customer's part is fixed once approval is requested (Edit dialog, action bar)

Who the customer is (the **Customer Project**, from which the read-only Customer Group is derived) and whether they are asked (the **Customer Approval** / **Customer Review** tick boxes) are fully editable only in the creation phase, the state **New**. The rule, a pure function of `(state, the stored tick box, whether the change has a project)` and therefore computed client-side in `features/csm-operations/utils/changeRequests.ts` exactly as entity-service decides it (the backend stays the authority and answers 400; its message still shows in the dialog's `saveError`):

- **New:** the project and both boxes are editable (a box can be ticked and unticked; a project can be chosen or swapped).
- **After New** (Request Approval was pressed; a change request never returns to New) the Customer Project is **frozen for everyone**: the dialog shows it read-only with "Fixed when approval was requested. ### Customers never decide in the CSM portal

Customers do **not** sign in to the CSM portal: they answer a change request's Customer Approval / Customer Review in the **customer portal** (`apps/customer-portal`). So the Approvals tab only *displays* the customer stages (the Customer Group's rows, Requested) and, once the customer has answered, the outcome (the deciding contact's row Approved / Rejected, the others' Cancelled, the change Scheduled / Closed / Canceled / Rollback); an internal user who is not an approver gets no Approve / Reject there, and nobody on staff can answer for the customer (below). Consequences for tests:

- **Never sign a customer in to CSM** -- there are no `crCustomerContact*` session roles (only `crApprover` and `crInternalApprover`), and no spec drives Approve / Reject as a customer. **Staff never record a customer's approval or review.** While a change request is in Customer Approval or Customer Review it moves on only through the customer's own answer in the Customer Portal: an engineer answering for the customer would write a decision the customer never made into data that is audited, so there is no such action anywhere in the portal -- no button, no "Change state" entry, not even a disabled one -- whether the customer's request is pending or nobody was asked (no registered contacts). (There used to be "Bypass customer approval" / "Bypass customer review" entries; they were removed on purpose, so don't reintroduce them, enabled, disabled or "for when nobody is asked".) The trigger is "no approver row is `REQUESTED`" (`anyApproverBeingAsked`, any stage, any label: a synced customer stage is labelled by its position, and a note that says nobody is asked must never be wrong about a change somebody IS asked about), so it covers a project with no registered contacts (the project-specific reason, `NO_CUSTOMER_CONTACTS_HELPER`, shown even before the approvals load), a project whose only contact is the requester or whose contacts are no longer active, and a legacy change that reached the gate with no stage at all (`NOBODY_ASKED_HELPER` names those causes, because the web cannot tell them apart). ## A time the customer proposed, and WSO2's answer (the banner, Accept, Propose a different time)

The previous system's own mechanism, which the schema already carries: a customer's proposal is written to `change_request.customer_updated_on` (a planned **start**; the planned length is kept) with WSO2's answer in `customer_updated_date_confirmation` (Agree / Disagree). The change **stays in Customer Approval** and the planned window stays what WSO2 planned until WSO2 answers; no stage, approver row or state is touched by the proposal. `{state: "authorize"}` is only the wire name of the Time Change loop (Re-schedule, counter, decline): it never moves the state and never opens a CAB stage (CAB approves once, before the first Customer Approval). The backend's side of this contract (the predicate, the PATCH shapes, every refusal text) is entity-service's `change_request_customer_proposal.go` and its CLAUDE.md / openapi.yaml; the fake API and the vitest fake mirror it.

The page never infers a proposal from the raw columns: `pendingCustomerProposal(cr)` is the backend's verdict (`answer === "pending"`, an allowlist: a change in Authorize with a live CAB stage, one waiting on any other approval or an unknown approval group, a closed or scheduled one, a date equal to the plan, one with a standing answer never match) and only in `customer_approval`. ## Change request Approval tab: Approve / Reject follow the backend, never the state

enable anything from it. The backend keeps an approval actionable only while the change is in its stage's

controls render disabled with the existing "You aren't able to approve or reject this stage" tooltip). A
decision refused with a **409** (the change moved on while the page was open) shows the backend's message
(`ChangeRequestApprovals` shows any 4xx message) and `useDecideChangeRequestApproval` refreshes the approvals,
detail and list queries on it, so the stale row goes away.

## Change request lifecycle stepper

`ChangeRequestLifecycleStepper` (full width, under the detail page's header) plots the **customer portal's eleven-stage "Change Request Workflow"**, in its order and its wording -- New, Assess, Authorize, Customer Approval, Scheduled, Implement, Review, Customer Review, **Rollback**, Closed, **Canceled** -- as a *horizontal* line (the customer portal's is a vertical timeline). Everything it decides is the pure `buildChangeRequestLifecycle` (`features/csm-operations/utils/changeRequestStages.ts`, unit-tested for every state x checkbox combination); the component only draws it.

- **Statuses**: `done` / `current` / `pending` / `not-taken` / `unrecorded` / `rejected` (the customer rejected the change at that stage: an error-coloured ring with a cross, read as "rejected by the customer"). Rollback and Canceled are *exception* stages: while the change is on the path they are `not-taken` (faint, dashed outline, still labelled and iconed -- never `done`); they turn `current` (error colour, Undo2 / Ban icon, red connector into them) only when the change really is in that state.
- **Rollback** (`rollback` is only reachable from Review / Customer Review): everything through Review is `done`; Customer Review reads from its approval stage rows: a REJECTED one is `rejected` (the customer's rejection is what rolls the change back), any other row means it was entered (`done`), and with no row it is `not-taken` only when the project has registered customer contacts (`hasCustomerContacts`: the backend would have asked them on entering Customer Review), else `unrecorded` (a rollback from Customer Review in a project with nobody to ask leaves no row either). **Canceled** (reachable from anywhere, no history kept): a stage is `done` only when the evidence proves it was passed -- a stage row proves every state before its own; an APPROVED stage proves its own *except Review's* (approving Review does not move the change on); `hasCustomerApproved` (`customerApproved`) proves Customer Approval -- every other path stage is `unrecorded`, never `pending`, never skipped. The exception is a REJECTED Customer Approval stage: the backend answers it by canceling the change right there, so the stages before are `done`, Customer Approval is `rejected` and everything after is `not-taken`. The page passes the approvals it already fetches for the header note, `hasCustomerApproved` and whether `customerContacts` is non-empty.
- Customer Approval / Customer Review are left off the line when their checkbox is explicitly `false` and the change is not in that state; an unknown flag keeps them. An **Emergency** change is the exception (see "An Emergency change has one CAB approval and no customer steps"): its boxes are ignored and Assess reads `not-taken`; the e2e `expectStages` letters for it are e.g. `c n p p p p p p n p n` in New and `d n c p p p p p n p n` in Authorize (customer columns dropped by the flags). A state that is none of the eleven keeps the faint line and the "Current state" chip.
- Every stage says its status in words as well as colour (visually-hidden ", done" / ", current" / ", not taken" ... after the label) and carries the customer portal's caption as a tooltip and `aria-description` (the tooltip adds "(not taken)" / "(history not recorded)" / "(rejected by the customer)" for the stages whose faint or crossed marker needs it). Light-theme contrast is a design constraint, measured from screenshots: the current / rejected label uses the tone's *dark* shade on the light theme and its *light* shade on the dark theme (`toneText`; the main shade is 3.3:1 on the light page backdrop and about 4:1 for the error red on the dark one), muted labels are only dimmed to 0.85, and an upcoming stage's ring is `text.secondary` at 0.7 (a ring in the divider colour was 1.2:1) so it stays above 3:1 and clearer than a not-taken one (0.45, dashed). Captions are **not** shown inline: at the page's real content width (about 1110px at a 1440px viewport, 11 stages) adjacent two-line captions touch and the row doubles in height.
- Under 68px per stage the row scrolls **inside its own container** (centred on the current stage), never the page. Test helpers that read a stage's label must drop the hidden status suffix (`stepLabel` in `CsmChangeRequestDetailPage.test.tsx`; the e2e specs match `^<label>, `).
- e2e: `change-request-lifecycle.spec.ts` asserts the stepper through the page object's `stage(label)` and the spec's `expectStages(detail, columns, flags)`, which takes the eleven columns as one letter each (`d` done, `c` current, `p` upcoming, `n` not taken, `u` history not recorded, `r` rejected by the customer) and compares them with the words the stepper reads (", done", ", current", ", upcoming", ", not taken", ", history not recorded", ", rejected by the customer"), dropping Customer Approval / Customer Review when their checkbox is off. "the stepper and the action bar in every state" (fake API) walks a Normal change through every state with the customer checkboxes on and off, asserting all eleven stages *and* the action bar (primary button, Re-schedule, "Change state" entries in order) at each; the Rollback and Canceled screens (rolled back from Review with and without customer contacts, from the customer's rejection; canceled with no approvals, in Review after Peer / CAB, in Review after the Review stage was approved, at Customer Approval, after the customer's approval (their APPROVED stage and `hasCustomerApproved`), and by the customer's rejection) and the checkbox-off line are separate tests; the seeded-fixture describes assert CHG-FIXED-007 / -008 and the stage statuses after each customer answer.

## Comment bodies: laid-out HTML source vs. `white-space: pre-wrap`

`CsmCaseCommentBubble.tsx`'s body container is `white-space: pre-wrap` on purpose: comments authored in the rich-text editor no longer carry a per-run `pre-wrap` (see `stripWhitespaceStyleAndUnwrapSpans` in `richTextEditor.tsx`), and plain-text notes rely on it for their line breaks. The catch is HTML *source* that was laid out for reading — the shape ServiceNow stores and an engineer pastes, with a newline and indentation between every `<ul>`/`<li>`/`<p>`/`<br>` and hard wraps inside the text. `pre-wrap` prints every one of those newlines (reported live: blank gaps between bullets, ragged indented continuation lines), where a browser and ServiceNow treat them as a space.

The fix is not to change the container but to clean the body before it is rendered. `preprocessCommentBodyHtml` (`csm-cases/utils/commentContent.ts`, shared by the bubble and the PDF export) runs `collapseCommentSourceWhitespace` first: inside each `[code]…[/code]` block when the body has any (ServiceNow's marker for raw HTML), plus any laid-out HTML written around the blocks, which is cleaned in one pass with each block masked so its neighbours are judged in context; plain text between blocks keeps its newlines. A body with no `[code]` is cleaned as a whole. It is deliberately narrow:

- Only bodies with real block/`<br>` markup are touched; plain text is returned as is.
- Only whitespace that contains a newline is touched; spaces typed in the editor are kept.
- **`<pre>` and `<code>` content is never touched**, so a snippet keeps its line breaks and indentation — don't "simplify" this by switching the container to `normal`, which collapses a multi-line `<code>` snippet too.
- A newline inside text becomes a space only when the source also has a newline next to a block tag, so a note that mixes a stray `<br>` with intentional line breaks keeps them.
- Markdown bodies (Novera, GitHub-raised descriptions) never go through it.

`apps/customer-portal/webapp`'s comment cards (case Activity tab, service request comments, announcement comments) have the same helper in `features/support/utils/support.ts`, copied rather than shared because the two apps don't share a package; its card makes `<p>` `pre-wrap`, so a hand-wrapped paragraph printed its source line breaks there. Keep the two copies in step.

## Security

- **Never commit secrets or runtime config** — `public/config.js` (the real, per-deployment file copied from `public/config.js.example`) is git-ignored on purpose. It only ever holds *public* runtime values (IdP base URL, OAuth **client id** — not a secret, this is a PKCE/SPA flow with no client secret — backend base URL, theme, log level, feature flags); if a value you're adding isn't safe to ship to a browser, it doesn't belong in `window.config` at all.
- **Auth is Asgardeo's job, not ours** — `AsgardeoProvider` (`AppWithConfig.tsx`) and `useAsgardeo()`/`AuthGuard.tsx` own the whole auth lifecycle; the app **never reads or writes auth tokens itself** (no token in `localStorage`/`sessionStorage` anywhere in this codebase — the SDK manages that internally). Don't add code that pulls a token out of storage or a hook return value to attach it manually; use the existing API client wiring instead. The `sessionStorage` keys outside the SDK are `POST_LOGIN_REDIRECT_KEY` (a post-login redirect **path**) and `csm.sidebar.lastSection` (`CsmSideBar.tsx` — the last-resolved nav section id, so a reload on a route with no owning section, e.g. `/people/:id`, re-highlights it instead of resetting to Dashboard) — neither ever holds a token.
- **Sanitize before `dangerouslySetInnerHTML`, always** — every current use (case-comment rendering, rich-text description/plan fields, product-update content, the admin-configured top banner/announcement HTML) goes through `DOMPurify.sanitize` first (`src/utils/sanitizeHtml.ts` for the shared cases). `sanitizeHtml.ts` also force-hardens every sanitized `target="_blank"` link with `rel="noopener noreferrer"` against reverse tabnabbing — match that when adding any other `target="_blank"` link by hand. Never add a new `dangerouslySetInnerHTML` call that skips sanitization, even for content that looks like it's "our own" (e.g. admin-authored) — an admin-configured field is still attacker-controlled if that admin account is ever compromised.
- **`useLogger()`/`Logger` (`src/hooks/useLogger.ts`, `src/hooks/logger.ts`) is a plain console wrapper with no redaction** — it does not scrub or block sensitive fields before printing. The discipline has to live at the call site: log `error.message`/a short summary, not a whole caught `Error` object, request/response body, or user/profile object, since any of those can carry tokens, PII, or internal ids straight into the browser console (and potentially a session-replay/log-shipping tool downstream).
- **Don't let the client-facing UI surface backend internals** — render whatever (already-generic) message the backend sends; don't append stack traces, raw error objects, or your own extra technical detail on top of it. See the dashboard widget-preview page's URL design below for the same principle applied to URLs, not just error text: prefer a `@me`-style sentinel over embedding a raw internal id in anything bookmarkable/shareable/loggable.
- **No `eval`, `new Function`, or dynamic `<script>` injection** anywhere in `src/` — keep it that way; there's no legitimate use case for it in this app.
- **Never carry data from a user-shared screenshot into a test file, doc comment, or any other committed content** — not the real names, case numbers, company/product names, or example text visible in it. A screenshot is shared to show a bug, not as source material to copy from; even a name or sentence that looks harmless can be a real customer's data. Write test fixtures and examples with clearly generic, made-up content instead (e.g. "Jane Doe", "Acme Corp", "First paragraph."/"Second paragraph.").
- **Never reference an issue tracker, ticket number, or repo name in code, comments, or this file** — a doc comment or `CLAUDE.md` entry should stand on its own ("reported live: ...", "fixed because ..."), not point at an external, mutable system that this codebase has no lasting connection to. Explain the *why* directly in the comment instead of citing where it was reported.
- **A raw base64-embedded `<img>` in comment/description HTML is now redacted server-side too, not just hidden on screen.** `useResolvedInlineImageHtml`'s `.iix`-referenced images were already correctly permission-gated (the browser never even requests one without `canDownloadAttachment`), but content authored before/without `SFTPGO_ATTACHMENT_STORAGE_ENABLED` never gets extracted into a real attachment at all — the image stays as `data:image/...;base64,...` directly inside the comment `content`/case `description` (found live: a `viewer`/`escalator` role, neither of which holds `canDownloadAttachment`, could see a pasted screenshot in a comment). `replaceInlineImageSrcs`'s `denyRawBase64` parameter (`inlineImages.ts`) still hides these behind the same "no permission" placeholder as a `.iix` denial — but the actual confidentiality fix is in `apps/csm-portal/backend` (`internal/handler/inline_image_redact.go`, see that repo's own `CLAUDE.md`): `redactRawBase64Images` strips the base64 payload out of the raw JSON response itself for a caller lacking `PermDownloadAttachment`, before it ever reaches this frontend, so `denyRawBase64` is now a display-consistency measure (the redacted placeholder src still starts with `data:image/`, so this hook still recognizes and hides it) rather than the only thing standing between a denied caller and the real bytes.

## The config-driven dashboard widget system

`AgentsLandingPagePilot` (rendered from `CsmDashboardPage.tsx`, alongside the older `AbtDashboardHeader` dashboard/team switcher) is a **fully backend-config-driven** widget grid — there is no frontend-side widget registry. The backend's `DASHBOARDS_CONFIG` env var (a JSON array, parsed into Go's `dashboard.Dashboard`/`dashboard.WidgetTemplate` — see `apps/csm-portal/backend/internal/dashboard/widgets.go`) is the single source of truth for which dashboards exist, which widgets each one has, and how each widget is filtered. The frontend never hardcodes a widget list; it only knows how to *render* whatever shape/resourceType combination the backend sends.

Other components in this same folder (`CaseCompositionCharts`, `CompositionDonut`, `CaseCountsMatrix`, `CustomerSummarySection`, `RecentActivitySection`, `MyAssignedCases`) are a separate, older composition-chart system that isn't currently wired into `CsmDashboardPage.tsx` — don't confuse them with the widget system below.

### The wire shape (`src/api/backend/types.ts`)

`GET /dashboards` returns `BeDashboardListItem[]` (id/displayName/isDefault/isTeamBased — enough for the dashboard switcher). `GET /dashboards/{id}` returns the full `BeDashboard`, whose `widgets: BeDashboardWidget[]` is the actual per-widget config:

```ts
interface BeDashboardWidget {
  widgetId: string;
  displayName: string;
  description?: string;        // subtitle shown under displayName; not shape-specific by design
  resourceType: BeWidgetResourceType;  // "case" | "incident" | "change_request" | "account" | "project"
                                        // | "user" | "time_card" | "problem" | "product_vulnerability"
  shape: BeWidgetShape;         // "count" | "list" | "pie" | "bar"
  gridWidth: number;            // 1-12, CSS grid columns this widget occupies
  filters: Record<string, unknown>;  // opaque; passed verbatim as the filters of that
                                      // resourceType's own POST /{resourceType}s/search
  groupBy?: string;             // present on the wire; unused today — `slices` (below) is what
                                 // actually drives pie/bar grouping
  listLimit?: number;           // shape "list" only: how many rows to show
  slices?: BeDashboardPieSlice[]; // shapes "pie"/"bar" only: see below
  section?: string;            // groups widgets under a titled sub-heading — see below
}

interface BeDashboardPieSlice {
  label: string;
  color?: BeWidgetPaletteColor;  // "primary" | "secondary" | "success" | "error" | "info" | "warning"
  filters: Record<string, unknown>;  // this slice's own criteria only — merge under the widget's
                                      // own base `filters` (slice keys win) to resolve its total
}
```

Every field beyond `widgetId`/`displayName`/`resourceType`/`shape`/`gridWidth`/`filters` is optional and `omitempty` on the wire — a widget/dashboard that doesn't set them behaves exactly as if the field didn't exist.

### How each `shape` resolves its data

All four shapes ultimately do the same thing — issue that `resourceType`'s own `POST /{resourceType}s/search` and read the response — they just differ in *how many* searches and what they do with the result(s):

- **`count`** (`useWidgetData`, shape `"count"`): one search, `pagination.limit: 1`, reads `total`. Renders a big number, the whole tile is a link to that resource's own tab (`WIDGET_RESOURCE_CONFIG[resourceType].buildHref(filters)`).
- **`list`** (`useWidgetData`, shape `"list"`): one search, `pagination.limit: listLimit ?? 4`, reads the item array. Renders through `WIDGET_LIST_RENDERERS[resourceType]` (`widgetListConfig.tsx`) — reuses each resource's **own real tab component** where one exists (e.g. `case` renders through the identical `CasesList` the Cases tab uses, via the same `mapCaseSearchViewToRow` mapper), falling back to the generic `DashboardMiniTable` otherwise. A "View more" link (shown only once `total > (listLimit ?? 4)`) goes to a dedicated, real, bookmarkable preview route (`DashboardWidgetPreviewPage`, `/dashboard/:previewSlug`) with pagination and search — not directly to the resource's own tab.
- **`pie`** / **`bar`** (`useWidgetPieData`): one search **per `slices` entry**, each with `pagination.limit: 1`, merging that slice's own `filters` under the widget's base `filters` (slice keys win). `useWidgetPieData` is shape-agnostic — it just resolves N labeled totals; `DashboardPieChart`/`DashboardBarChart` (both under `components/`) render the same resolved data as wedges or bars respectively. Each wedge/bar/legend row navigates to that slice's own filtered destination the same way a `count` tile does. A total of `0` across every slice renders an empty state (inbox icon + "Nothing to show here right now"), not an all-grey chart.

`DashboardWidgetTile.tsx` is the per-widget dispatcher: it reads `shape` and picks which of the above to render, plus the shared per-widget loading/error states.

**`count`/`pie`/`bar` only ever read `total` off these searches, never the rows — so for the case-family `resourceType`s they're sent with `countOnly: true` instead of plain `api.post`.** `postCountingOnly` (`api/backend/postCountingOnly.ts`, the mirror of the pre-existing `postSkippingTotal.ts`) sets the flag, retries without it on a 400, and latches it off for the rest of the session once that happens — so a portal built against an entity service that predates the field doesn't strand every count/pie widget. Reported live, with a real load test and a perf-database replay, as a meaningful chunk of the dashboard's own database time: the backend was always running a full page query (`ORDER BY ... LIMIT n`, then discarding the one row) purely so this hook could read `total` off the same response — see entity-service's own `CLAUDE.md` for the `countOnly` field and its database-side savings. Gated on `config.searchEndpoint === "/cases/search" && !config.buildSearchRequestBody` in both `useWidgetData`'s `shape !== "list"` branch and every slice query in `useWidgetPieData` — `countOnly` is a case-search-only field, and a `resourceType` with its own diverging request shape (`case_feedback`) was never designed against it. A `shape: "list"` widget still reads real rows, so it never sends the flag.

### `section` grouping

`AgentsLandingPagePilot.tsx`'s `groupWidgetsBySection` groups a dashboard's widgets by their `section` value, preserving the order each distinct value (including the untitled default, for widgets with no `section`) first appears among the widgets array. Widgets sharing a `section` render together under one bold heading, separate from the rest — e.g. a handful of SLA-violation `count` widgets can all set `"section": "SLA Violation"` to appear grouped under that heading without needing a separate dashboard. No `section` set anywhere (the common case) renders exactly as before this field existed: one untitled group, with `pie`/`bar` widgets still visually separated from `count`/`list` ones within that group.

### Per-resourceType config (`config/widgetResourceConfig.ts`, `config/widgetListConfig.tsx`)

`WIDGET_RESOURCE_CONFIG` is the one place that knows, per `resourceType`: its search endpoint, response items key, list-row label extractors, tile icon/color, `buildHref` (translates a widget's opaque filters into that resource's **own** tab's URL filter scheme — e.g. the dashboard's lowercase `catastrophic`/`critical`/... severity values get translated to the Cases tab's own `S0`/`S1`/... codes), and `previewSlug` (the URL segment for that resourceType's `/dashboard/:previewSlug` preview page). Adding a new `resourceType` the backend can send means adding an entry here and to `WIDGET_LIST_RENDERERS` — everything else (tile rendering, preview page, pagination) is generic over any entry in these two config objects.

### Current-user placeholder

The backend resolves a `"__current_user__"` filter placeholder into the caller's real platform user id **before** it reaches the frontend (see the backend's `ResolveFilters`/`ResolveSliceFilters`) — the frontend never sees or handles that placeholder for a widget's own data-fetching. Separately, the "View more" preview page's own **URL** masks the current user's id to a `@me` sentinel (`widgetPreviewUrl.ts`'s `buildWidgetPreviewHref`/`resolveCurrentUserSentinels`) purely so a bookmarked/shared link doesn't carry a bare internal user id — that's a frontend-only, URL-display concern, unrelated to the backend's own placeholder resolution.
