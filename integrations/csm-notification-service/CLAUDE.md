# CSM Notification Service

Go background worker (`net/http`, Go 1.26+) — a pure Kafka consumer, no inbound API beyond a health check. csm-portal-backend and customer-portal-backend publish domain events (case created, comment added, status changed, case assigned, incident created) directly to Azure Event Hub; this service's own consumers read them back and send the actual notification — email, a Google Chat alert, or a voice call. Extracted from `apps/csm-portal/backend/internal/notifications` — that backend no longer owns or calls any notification client.

This service used to also expose `POST /events` (an HTTP ingest endpoint the backends called, which this service then published to Event Hub itself) and, before that, an even earlier `POST /notifications` direct channel-command stub. Both were removed once it was decided the backends should own producing to Event Hub directly — one fewer network hop, and this service no longer needs any inbound HTTP surface for events at all. Don't re-add a producer-side HTTP endpoint here without confirming that decision has changed.

## Current scope — deliberately incomplete

The consume→dispatch path (event bus → `dispatch.Dispatcher`) **is real** — it sends actual emails, Google Chat alerts, and voice calls — but has one known, explicitly-flagged gap:

- **SMS is unused.** `TwilioClient.SendSMS` has no caller anywhere in this service. Voice has two: `dispatch.handleIncidentCreated`'s single immediate call (`MakeCall`), and the incident call-escalation engine (`MakeCall` or `MakeSSMLCall`, see "Incident call escalation" below), which places the many calls of a ladder.

A dead-letter topic **does** exist now (see "Event-driven notifications" below) — a record that exhausts the main consumer's retries is published there rather than dropped, and a separate DLQ consumer gets its own retry pass at it. There's still no third tier past that: a record that also exhausts the DLQ consumer's retries is logged and dropped for good.

Email *recipient* (audience) resolution is **not** a fixed env-configured list — every `case.*` payload carries its own `recipients` array, supplied by the caller (e.g. `csm-portal-backend`), since `dispatch.Dispatcher` has no way to resolve watchers/assignee/reporter itself. That's still short of "real" resolution (the caller has to already know the audience), but there's no `TEMP_*` env var or hardcoded test list to avoid pointing at real mailboxes anymore — `events.Validate` rejects any `case.*` event with an empty `recipients` list. This does **not** apply to `incident.created`'s call reaction, or `case.created`'s/`case.acknowledged`'s/`case.severity_changed`'s own Google Chat alerts — there's no "recipient" concept to resolve for either the way there is for email; a Chat post goes to one shared space, not per-recipient (these three always resolve to the fixed `chataudience.IncidentMonitor` audience — no team detection, no per-product routing, see `internal/dispatch` below), and a call goes to one phone number, not a mailbox. A publisher that knows the right on-call number can still supply `callTo` (`incident.created` only) directly in the payload; one that can't (e.g. entity-service, which has no on-call/paging system of its own) may omit it, and `dispatch.Dispatcher` substitutes its own configured `INCIDENT_DEFAULT_CALL_TO` — see `internal/dispatch` below.

*Link* resolution is a separate, smaller thing this service now does do: `internal/recipientlinks.Resolver` (backed by `internal/entity`, a minimal customer-entity-service client) looks up each recipient's role and picks the portal-appropriate case link for them — see "Event-driven notifications" below. Don't conflate the two: this service still doesn't decide *who* gets notified, only *which link* a given recipient gets.

## Why no `Auth` middleware

The only route this service exposes is `GET /health` (Choreo's liveness probe), with no end-user or caller identity to check at all — everything else is Kafka consumption, not an HTTP request. Don't add inbound JWT/Bearer validation, or a new HTTP endpoint that would need it, without confirming this service is meant to have an inbound API surface again.

## Middleware chain

`SecurityHeaders → CorrelationID → Logger → Mux`

- `SecurityHeaders` (`internal/middleware/security_headers.go`): sets `X-Content-Type-Options: nosniff`, `Content-Security-Policy: upgrade-insecure-requests`, and `Strict-Transport-Security: max-age=31536000; includeSubDomains` on every response
- `CorrelationID` (`internal/middleware/correlation.go`): reads `X-CSM-Correlation-ID` from the incoming request or generates a UUID v4; ensures the ID carries a `cns-` prefix (CSM Notification Service) either way, without double-prefixing an ID that already has it; stores the ID in context for the slog handler; echoes the ID in the response header
- `Logger` (`internal/middleware/logger.go`): logs every completed request (method, path, status, elapsed) via slog

`middleware.ConfigureLogger()` must be called at startup — it wraps the default slog handler so every `slog.*Context(r.Context(), …)` call automatically includes `correlationID=<id>` when the context carries one.

## Notification channels

`internal/notifications` — one config/client pair per channel in its own file, since channels differ in upstream auth scheme:

- `EmailConfig`/`EmailClient`/`SendEmail` (`email.go`) — OAuth2 client-credentials auth against an external email notification service (`POST /send-email`)
- `GoogleChatConfig`/`GoogleChatClient` (`googlechat.go`) — a plain incoming-webhook URL per Google Chat space, no OAuth2 involved. Every `Send*Alert` method's first argument is a Chat **audience** key (a team's own space, or a standing audience like `"Incident Monitor"`/`"Evaluation"` — see `internal/chataudience` under "SLA breach-alerting engine" below), routed via the shared private `sendCardToAudience(ctx, audience, msg)`/`HasAudienceSpace(audience) bool`, matched whitespace-insensitively but *case-sensitively* — an audience key is an exact team name or fixed constant, and case-folding two distinct real team names together would be a worse failure mode than requiring an exact match.

  **Two sources feed that routing table, not one.** `GoogleChatConfig.AudienceSpaces` (`[]GoogleChatAudienceSpace`, `{Audience, WebhookURL}`, from `GOOGLE_CHAT_SPACES`/`INCIDENT_CHAT_SPACES`) is the *static* source — meant now only for the standing, non-team audiences (`"Incident Monitor"`, `"Onboarding"`, `"Americas"`, `"Evaluation"`), set once at construction and immutable for the life of the process. A **real team's own space now comes from entity-service's `team` table instead** (`team.chat_webhook_url`, that repo's own migration `0240`) — hand-listing a team in `GOOGLE_CHAT_SPACES` is the thing this replaces, so a team shouldn't need an entry there any more once its row has a webhook URL. `GoogleChatClient.SetTeamAudienceSpaces(map[string]string)` atomically swaps in the current team→URL set (guarded by its own `sync.RWMutex`, since it's read by request-handling goroutines while a background goroutine refreshes it); `webhookURLFor` checks the static map first (so a team still listed there during the migration window keeps working, rather than silently losing its space) and falls back to the team-sourced one. `cmd/server/main.go` fetches the full set via `entity.CustomerEntityClient.GetTeamChatWebhooks` (`GET /teams/chat-webhooks`, internal-caller-only on entity-service — this service's own OAuth2 client id must be in entity-service's `M2M_CLIENT_IDS`), gated on `CUSTOMER_ENTITY_BASE_URL` like every other optional entity-service feature. **The very first fetch is retried with backoff, before any Kafka consumer starts** — up to 5 attempts, 5s doubling to a 30s cap — rather than one shot: `sendCardToAudience` acknowledges (never retries) a record whose audience resolves to "no space configured" (see that function's own doc comment), which is indistinguishable at that point from "this team genuinely has no Chat space." Without the retry, a single transient entity-service failure at the exact moment this process started could leave `teamAudienceSpaces` empty well past the point consumers began processing real records — every team-routed alert (SLA breach, frustration detection, `sr.*` customer comments) in that window would silently resolve to "no space" and be dropped for good, since this was never a Kafka-level failure for `eventbus.Consumer`'s own retry/DLQ machinery to see. Bounded, not indefinite: a persistently-unreachable entity-service must still let this service start (team-routed Chat is a best-effort enhancement over the static audiences, not core delivery) — after the last retry fails, it's logged and the process moves on with only the static audiences until the next scheduled refresh. Past that first call, refreshes run on a plain ticker (`TEAM_CHAT_SPACES_REFRESH_INTERVAL`, default 5m); a failed refresh there is logged and keeps whatever the client already had, never crash-loops. Unlike the SLA duration policy fetch (fetched once, since that data essentially never changes), this really does need periodic refresh: an operator can add or change a team's webhook URL in the database at any time without redeploying this service. `SendCaseCreatedAlert`, `SendCaseAcknowledgedAlert`, `SendSeverityChangedAlert`, and `SendSecurityReportAnalysisAlert` (and the three `sr.*` cards in `googlechat_sr.go` — see "`sr.*` service-request Chat alerts" below) each just build their own `chatCard` and hand it to `sendCardToAudience`, which itself calls the shared private `postCard(ctx, webhookURL, msg)` for the actual HTTP mechanics. `chatCard.Header` is a pointer (`*chatCardHeader`, `omitempty`): the `sr.*`, frustration and incident cards set one; none of the four `case.*` cards (`SendCaseCreatedAlert`/`SendSeverityChangedAlert`/`SendSecurityReportAnalysisAlert`/`SendCaseAcknowledgedAlert`) does (see "case.* Chat cards" below for why). An audience with no configured space is simply skipped (logged), not an error — see `sendCardToAudience`'s own doc comment; there is no unmatched-key fallback the way an earlier product-routed design had, since an audience key is either a real team name or one of a small set of fixed constants this service itself controls, not an arbitrary display string a publisher could send unconfigured. `incident.created`/`incident.assigned` post to the incident's assignment-group space — see "Incident Chat cards" below. `sendCardToAudience` is also the single choke point that logs every real send attempt's own outcome — `"notifications: google chat alert sent"` (info, with `audience`) or `"notifications: google chat alert failed to send"` (error, with `audience` and, when the failure is a `*apierror.Error`, `statusCode` — never the error's own message/body) — added specifically so "did a Chat alert actually go out, and to which audience's space" is answerable directly from this service's own logs, rather than only inferring it from `internal/dispatch`'s generic retry/dead-letter logging further up the call stack, which doesn't say which channel failed or why. The failure log deliberately omits the raw error: a Google Chat error response can echo back part of the submitted card (title/text) verbatim, and this service's own logging convention is ids and sanitised summaries only, never a raw upstream body that might carry case content — same reasoning as `entity-service`'s `publishCaseCreatedEvent`.
- `TwilioConfig`/`TwilioClient`/`SendSMS`+`MakeCall` (`twilio.go`) — HTTP Basic Auth (Twilio Account SID/Auth Token; Twilio has no OAuth2 flow). One client, two methods, since sms and call are the same Twilio account/auth, just different REST resources (`Messages.json` vs `Calls.json`) via a shared private `do()`:
  - `SendSMS(ctx, to, body)` sends via the client's configured `MessagingServiceSid` if set (our account's real setup — a sender pool with opt-out/compliance handling), else its fixed `FromNumber`. If both are set, `MessagingServiceSid` wins
  - `MakeCall(ctx, to, message)` places a voice call that reads `message` aloud via a `<Say>` TwiML document built locally (`sayTwiML`, no external TwiML hosting needed) — always requires `FromNumber` as caller ID, since Voice has no `MessagingServiceSid` equivalent, regardless of whether `MessagingServiceSid` is set for sms. `<Say voice="..." language="...">` come from `TwilioConfig.Voice`/`Language` (`TWILIO_VOICE`/`TWILIO_LANGUAGE`, both optional — empty omits the attribute and uses Twilio's account default)
  - `TwilioConfig.APIBaseURL` overrides Twilio's REST API base (`TWILIO_API_BASE_URL`, defaults to `defaultTwilioAPIBaseURL` when empty — resolved once in `NewTwilioClient`, not read per-request). Not just a test seam: tests set it to an `httptest.Server` URL the same way a real deployment could point it at a regional Twilio edge endpoint

All three clients are constructed in `cmd/server/main.go` with `os.Getenv` (never `mustEnv`) for their config, since none is required for every deployment — a missing/invalid config only surfaces as an error the first time that channel is actually used. All three are handed to `dispatch.NewDispatcher`, which is the only thing that calls them (see "Current scope" above for `SendSMS`/`MakeCall`'s current usage gap).

A new channel gets its own `<Name>Config`/`<Name>Client` file in `internal/notifications` following the same pattern (or a new method on an existing client, if it shares that client's auth — as `MakeCall` does with `SendSMS`), then gets wired into `Dispatcher` for whichever event type(s) should trigger it — see "Adding a new event type" below.

`internal/entity` (the customer-entity-service client backing `internal/recipientlinks`, and recording onboarding-step outcomes) is **not** a notification channel and deliberately doesn't follow the pattern above — it's an upstream data client used to decide *which link* to put in an email (and to write a step's outcome back), not something that sends a notification itself. Don't move it into `internal/notifications` or give it a `Send*` method. The same goes for **`internal/scim`** (`client.go`), the SCIM operations service client `dispatch.handleProjectContactInvited` uses to create an invitee's Asgardeo user: it provisions an account, it doesn't notify anyone, so it has its own package (mirroring `apps/csm-portal/backend/internal/scim`'s OAuth2 client-credentials shape, narrowed to `EnsureExternalUser` — `POST /organizations/external/users`, 201 = created / 200 = already existed, anything else an `*apierror.Error` with the status only — the body is deliberately not retained, since a SCIM validation error echoes the invitee's email and the error is persisted as an onboarding step's `lastError`; deliberately sends no `password`/`askPassword`, the SCIM service generates one the user never sees and Asgardeo sends no email of its own). Not imported from the csm-portal-backend package: this module is its own deployable, and that client carries end-user identity/tracing headers a Kafka consumer has nothing to fill. Its OAuth2 client-credentials `*http.Client` comes from **`internal/oauthhttp`**, the one shared copy every upstream client here (`internal/entity`, `internal/notifications/email.go`, `internal/slaengine`, `internal/scim`) builds on — token-fetch and request timeouts live there, not per client. A 200/201 from the SCIM service without a body or without the user's `id` is an error, not a provisioned identity.

## Event-driven notifications

This service is a pure consumer: csm-portal-backend and customer-portal-backend publish directly to Event Hub themselves (see `internal/events`'s package doc) — there is no HTTP ingest endpoint and no `internal/outbox` package here anymore. There *is* now an `internal/entity` package — don't confuse it with the removed `internal/entityservice` (that was an event-ingest thing, gone for good); `internal/entity` is new, unrelated, and exists only to back `internal/recipientlinks`'s link resolution (see below). Two packages implement the bus→consumer pipeline; `internal/notifications` (templates + channel clients) is the last-mile sender it calls.

- **`internal/events`** (`events.go`/`validate.go`) — the schema and its only remaining validation boundary. `Type` is one of `case.created`/`case.comment_added`/`case.status_changed`/`case.assigned`/`case.acknowledged`/`case.severity_changed`/`incident.created` (`KnownTypes`), plus `change_request.approval_requested`/`change_request.plan_date_notice` (csm-flow-service's, on their own topic), `sr.created`/`sr.acknowledged`/`sr.comment_added` (entity-service's service-request events, `service_request.go`, on `sre-events` — see "`sr.*` service-request Chat alerts" below) and `project_contact.invited` (entity-service's customer-onboarding event, also on its own topic — see "`project_contact.invited`" below). `Envelope{Type, EntityID, Payload}` is the Kafka record value — `EntityID` is a case ID for the `case.*` types, an incident ID for `incident.created`, or the Salesforce membership Id for `project_contact.invited` (whatever the event is about, generically — it was named `CaseID` originally, renamed once `incident.created` made that name misleading), and is the Kafka partition key (see `internal/eventbus` below). `Payload` is `json.RawMessage`, decoded into the `Type`-matching payload struct (`CaseCreatedPayload`, etc.) by `Validate` and, again, by `dispatch.Dispatcher.Handle` for rendering. `Validate(entityID, t, raw)` — moved here from a since-removed HTTP handler — decodes strictly (`DisallowUnknownFields`) and checks required fields, plus (for every `case.*` type) that the payload's own `CaseID` matches `entityID`; a mismatch would mean the payload was published keyed under the wrong case's partition. `case.acknowledged` is Chat-only — its own `CaseAcknowledgedPayload` has no `Recipients` at all, so `Validate`'s case for it skips `validRecipients` entirely, unlike every other `case.*` type. `case.severity_changed` is the one exception to that exception: it has both an email reaction and a Chat alert (see below), so its own `SeverityChangedPayload` carries `Recipients` and `Validate`'s case for it requires `validRecipients` same as `case.created`/`case.status_changed`/`case.assigned`. `Dispatcher.Handle` calls `Validate` before rendering/sending anything, since there's no handler upstream doing it before publish anymore — a caller that publishes a structurally invalid event now gets it retried, dead-lettered, and eventually dropped, rather than rejected synchronously at publish time. Payloads still carry denormalized display values (names, titles, a phone number) this service has no other way to obtain — that part hasn't changed. But case/comment **links** are no longer one of those denormalized values: five of the six `case.*` payloads — every one except `CaseAcknowledgedPayload`, which is Chat-only — carry `ProjectID`/`CaseID` (and `CommentID`, on `CommentAddedPayload` only — the others have no comment to link to at publish time) instead of pre-built `CaseLink`/`CommentLink` strings, and `dispatch` resolves each recipient's own portal-appropriate link itself (see `internal/recipientlinks` below) rather than trusting a caller-supplied link. `Recipients []string` (audience) is unchanged — still caller-supplied, still not resolved here; see "Current scope" above for why that's a distinct thing from link resolution.
- **`internal/entity`** (`customer.go`, `onboarding.go`) — a minimal entity-service client implementing exactly two endpoints: `POST /users/search` (`customer.go`, backing `internal/recipientlinks`'s role lookup) and `PUT /onboarding-steps/{membershipSfId}/{step}` (`onboarding.go`, `RecordOnboardingStep` — the one write this service makes, from `dispatch.handleProjectContactInvited`, see below) — unlike `apps/csm-portal/backend`'s own entity client (~60 passthrough methods for that backend's handlers). It was read-only and single-endpoint until the onboarding flow needed somewhere to record step outcomes; don't grow it further without the same kind of concrete consumer. Its `do()`/OAuth2 setup mirrors `internal/notifications/email.go`'s shape, and — like that email client — its *credentials* don't follow a per-channel-independent pattern: `cmd/server/main.go` fills both `CustomerEntityConfig.TokenURL`/`ClientID`/`ClientSecret` and `EmailConfig.TokenURL`/`ClientID`/`ClientSecret` from the shared `OAUTH2_TOKEN_URL`/`OAUTH2_CLIENT_ID`/`OAUTH2_CLIENT_SECRET` env vars, not client-specific ones (`EMAIL_TOKEN_URL`/`EMAIL_CLIENT_ID`/`EMAIL_CLIENT_SECRET` used to exist and were removed) — mirroring csm-portal-backend's shared-OAuth2-app convention for *its* entity client. The real email-service and entity-service deployments this points at both authenticate every caller through the same shared gateway app (scoped via each client's own `*_SCOPES` var), which is why this isn't optional stylistic reuse — a dedicated `EMAIL_TOKEN_URL`/etc. genuinely doesn't exist for this deployment. Only `CUSTOMER_ENTITY_BASE_URL`/`CUSTOMER_ENTITY_SCOPES` (respectively `EMAIL_BASE_URL`/`EMAIL_SCOPES`/`EMAIL_FROM_ADDRESS`) are specific to each client. Google Chat and Twilio remain genuinely unrelated external providers with their own independent credentials — don't extend the shared-app treatment to them without the same kind of real-world reason. Deliberately carries no `x-user-id-token`/correlation-ID header forwarding — csm-portal-backend's version has both, to propagate a real end-user's identity/tracing through an HTTP request, neither of which exists in a Kafka consumer.
- **`internal/recipientlinks`** (`resolver.go`) — `Resolver.ResolveLinks(ctx, emails, projectID, caseID) ([]RecipientLink, error)` resolves each recipient's own portal-appropriate case link via `internal/entity`'s role lookup: a role in `CUSTOMER_ROLES` → the customer portal link, a role in `CSM_ROLES` → the CSM portal link, else a fallback chain — see `linkFor`'s doc comment for the full reasoning. When roles don't resolve it (including when entity-service has no record for the recipient at all), the recipient's own email domain decides instead: `wso2EmailDomain` (`"wso2.com"`, a hardcoded constant — mirrors `apps/csm-portal/backend`'s own `wso2EmailDomain` in `user_external_account.go`, not a new env var) → CSM, anything else → customer — a domain is always present, unlike roles, which incomplete/test entity-service data frequently leaves empty; this was a real reported issue (staging recipients with no role data were misclassified, producing spurious extra `groupByLink` groups and what looked like duplicate emails during `EMAIL_DEBUG_MODE` testing). Returns the *bare* case link only; `dispatch.commentLinkFor` appends a comment-specific `#<commentId>` fragment on top for `case.comment_added` (matching the CSM portal frontend's own comment-permalink format — the customer portal has no such fragment handling today, so the same suffix is simply inert there). A per-*recipient* decision, not per-event — the same notification can go to both a customer watcher and a CSM watcher at once, each needing a different link, which is why `dispatch.groupByLink` exists (see below) rather than rendering one shared email. `CSMLink(caseID) string` is the exception: no recipient, no role lookup, just `<CSMBaseURL>/cases/{caseID}` directly — for `dispatch.handleCaseCreated`'s/`handleCaseAcknowledged`'s/`handleSeverityChanged`'s Google Chat alerts, each of which posts once to a shared Chat space rather than per-recipient, so there's no audience to resolve a role for in the first place. Doesn't take a caller-supplied link — this service builds it itself, the same way it resolves every other portal link. `IncidentLink(incidentID)` builds `<CSMBaseURL>/operations/incidents/{id}` for the incident Chat card the same way.
- **`internal/eventbus`** (`config.go`/`producer.go`/`consumer.go`/`logger.go`) — a thin wrapper around `github.com/segmentio/kafka-go` for Azure Event Hub's Kafka-compatible endpoint. This service used `github.com/twmb/franz-go` first, then switched to `kafka-go` specifically for its MIT license (franz-go is BSD-3-Clause) — both are pure Go (no cgo), keeping this service on Choreo's buildpack deploy with no Dockerfile either way; the swap is otherwise a wash technically (see the two known trade-offs below). `dispatch` and any other caller never import `kafka-go` directly — this package exposes its own `Record{Topic, Partition, Offset, Key, Value, IsFinalAttempt, NoMoreRetries}` and `Handle func(context.Context, Record) error` instead — `NoMoreRetries` is true only on a Handle call where there is truly no further attempt coming for this record's content anywhere, main topic or DLQ — either on `IsFinalAttempt` when `onExhausted` is nil, or on an extra cleanup call `processRecord` makes if `onExhausted` itself fails (nothing will ever redeliver this content then either, so `dispatch` still needs the chance to release its tracking); `dispatch` depends on this being distinct from `IsFinalAttempt`, see its own notes below, so `github.com/segmentio/kafka-go` is fully contained here. Auth is SASL/PLAIN with the literal username `"$ConnectionString"` and the Event Hub namespace's Shared Access Policy connection string as the password — this is Event Hub's own convention, not a real username. `Producer.Publish` keys every record by `EntityID` (`kafka.Hash` balancer) so all events about one case/incident land on the same partition and are processed in order — this service's own use of `Producer` today is only for publishing to the dead-letter topic (see below), since the case-events producer side now lives in the backends. `Consumer.Run` uses `FetchMessage`/`CommitMessages` (not the auto-committing `ReadMessage`) and only commits a record's offset after `Handle` succeeds (or its retries are exhausted and `OnExhausted` has run) — never before — so a crash mid-processing redelivers on restart instead of silently skipping. `Compression` is left unset (no codec) on the `Writer` — Event Hub's Kafka-compat layer rejected both idempotent producing and compressed batches with `UNSUPPORTED_FOR_MESSAGE_FORMAT` under the previous client (confirmed against the real namespace); `kafka-go`'s `Writer` has no idempotent-write feature to disable in the first place, and leaving `Compression` unset avoids the same rejection. `StartOffset: kafka.FirstOffset` is set explicitly for the same reason `kgo.ConsumeResetOffset(...AtStart())` was needed before — a partition with no committed offset should be read from the beginning, not the tail — though this happens to already be `kafka-go`'s own default. `logger.go` bridges kafka-go's `Logger` (routine, non-error chatter — protocol join/sync/commit messages, "N messages written" on every produce) to `slog.Debug`, and `ErrorLogger` (where kafka-go actually reports problems) to `slog.Error` — matching kafka-go's own severity split. Confirmed against the real namespace: routing `Logger` to `slog.Warn` instead (as this package originally did, to compensate for the previous Kafka client only having one log level) produced thousands of WARN lines a day for entirely normal operation. Don't reach for per-message-string filtering here again — bridging at the right level per kafka-go's own Logger/ErrorLogger split makes that unnecessary.
  - **`PartitionCount(ctx, cfg)`** dials the broker and calls `conn.ReadPartitions(cfg.Topic)`, returning how many partitions the topic actually has. Used only once, at startup (see `startConsumers` in `main.go`), to sanity-check a configured consumer count against reality — not read again afterward.
  - **`Consumer.Run(ctx, handle, onExhausted)`** — `onExhausted` (type `OnExhausted`) is called once a record has failed every one of `handleAttempts` (3) calls to `handle`; `Run` commits the record's offset right after regardless of `onExhausted`'s own outcome, since nothing will retry this record on this topic again either way. Passing `nil` (the DLQ consumer's own `Run` call — see below) falls back to logging at ERROR and dropping the record. The retry loop itself (`handleAttempts` calls, `handleRetryDelay` between them) is factored into the package-level `processRecord` function specifically so it's unit-testable without a real Kafka broker — `consumer_test.go` exercises it directly, injecting a short retry delay.
  - **Known trade-offs from the franz-go → kafka-go swap** (confirmed live against the real Event Hub namespace, not theoretical): (1) `kafka-go`'s consumer-group rebalancing only offers `Range`/`RoundRobin` balancers, no cooperative/incremental strategy like franz-go's `CooperativeStickyBalancer` — matters once more than one consumer instance shares a group (now the normal case, via `MAIN_CONSUMER_COUNT`/`DLQ_CONSUMER_COUNT` — see below), where a rebalance briefly pauses every partition instead of just the ones moving. (2) A graceful `Consumer.Close()` can take up to ~30s, matching `kafka.ReaderConfig.SessionTimeout`'s default — noticeably slower than before. If this service is ever deployed somewhere with a shorter termination grace period than server-shutdown-timeout + ~30s, that's worth revisiting (e.g. lowering `SessionTimeout` explicitly).
- **`internal/dispatch`** (`dispatch.go`) — `Dispatcher.Handle` implements `eventbus.Handle`: unmarshal the record as an `events.Envelope`, reject an unknown `Type` or a payload that fails `events.Validate` (see above), then switch on `Type` and unmarshal `Payload` into the matching struct. `NewDispatcher(email, googleChat, call, links, emailSendingEnabled, emailDebugMode, emailDebugRecipients, callSendingEnabled, defaultOnCallNumber, defaultCSMEmailCC)` takes a fourth `linkResolver` param (satisfied by `*recipientlinks.Resolver`) alongside the three channel senders, then three email-specific controls checked in this order (`sendPerGroup`, below): `emailSendingEnabled` (`EMAIL_SENDING_ENABLED`, the disable-entirely `!= "false"` convention, same as `apps/csm-portal/backend`'s `AUTH_TOKEN_VALIDATOR_ENABLED`) is checked first — when false, every group is logged and skipped, `SendEmail` is never called at all, regardless of `emailDebugMode`; a re-added killswitch (an earlier version of this had one, replaced for a while by debug mode alone, until a live incident needed a way to silence email entirely without also stopping Chat/Twilio/link-resolution from being exercised). `emailDebugMode`/`emailDebugRecipients` (`EMAIL_DEBUG_MODE`/`EMAIL_DEBUG_RECIPIENTS`, only consulted when sending is enabled; `os.Getenv(...) == "true"`, so unset means real sending — inverted from this service's usual `!= "false"` convention, deliberately, since "debug" reads as an opt-in) redirects the four `case.*` types' actual `SendEmail` calls to `emailDebugRecipients` instead of each event's real resolved recipients; unlike the killswitch, the email still actually sends, just to a safe test list, so a dev/staging deployment can be exercised end-to-end without risking a real mailbox. A seventh bool, `callSendingEnabled` (`CALL_SENDING_ENABLED`, still the disable-entirely `!= "false"` convention), is the killswitch for `incident.created`'s Twilio call specifically; calls have no debug-recipient equivalent, so they kept the simpler shape. The trailing `defaultOnCallNumber` string (`INCIDENT_DEFAULT_CALL_TO`) is `handleIncidentCreated`'s fallback value for its payload's own `CallTo` when a publisher's payload omits it — added so entity-service, which has no on-call/paging system of its own, can publish the event without knowing it; a publisher that does supply its own value still takes precedence. `case.created`/`case.acknowledged`/`case.severity_changed`'s Google Chat alerts have no equivalent fallback to configure — they always resolve to the fixed `chataudience.IncidentMonitor` audience (see below), not a publisher-suppliable value. `events.Validate`'s `TypeIncidentCreated` case reflects the `CallTo` fallback: it's optional (empty is fine), but a non-empty value must still match `e164Pattern` — this only relaxes "absent," not "malformed." `CaseCreatedPayload.Product` remains optional (`omitempty`) — it's a purely-display value in the case-created email template and Chat card, unrelated to Chat routing. Four types (`case.*`) now go through `groupByLink(ctx, recipients, projectID, caseID)` — calls `links.ResolveLinks`, buckets recipients into `map[string][]string` keyed by the link they resolved to (recipients sharing a link still batch into one email, at most two buckets today: customer vs CSM portal) — then `sendPerGroup(ctx, baseKey, groups, subject, render)` renders (via the matching `notifications.Render*` function, unchanged signatures — they already took `caseLink`/`commentLink` as separate params, so no template changes were needed) and sends once per distinct link, in sorted-key order for determinism, joining any per-group errors with `errors.Join`. `baseKey` (from `recordBaseKey(record)`, a SHA-256 hash of `record.Value` — the raw envelope bytes, not `topic/partition/offset` — shared by every idempotency-tracked channel in this file) plus each group's own `caseLink` key that group's own `claim`/`forget` entry: a real-world failure (a persistently-misconfigured email OAuth2 client) showed that without this, a retry caused by one still-failing group would resend every group that had already succeeded, and — for `case.created`, which also has a Chat alert — resend that too. `recordBaseKey` hashes content rather than Kafka coordinates specifically because a record dead-lettered to the DLQ topic is republished with the exact same `Value` but a brand-new `topic/partition/offset` (`cmd/server/main.go`'s `OnExhausted` calls `dlqProducer.Publish(ctx, record.Key, record.Value)`) — coordinate-based keys would make the DLQ's first attempt see an unclaimed key and resend an already-succeeded channel, which is exactly what a live incident surfaced (see `TestDispatcher_Handle_CaseCreated_RetryDoesNotResendSucceededChatAlert`). `sendPerGroup` returns `owned []string` — the caseLinks THIS call actually claimed (won the race for) and is keeping — alongside its joined error; every caller (`handleCaseCreated`/`handleCommentAdded`/`handleStatusChanged`/`handleCaseAssigned`) uses this two different ways depending on which release condition fired: on `record.NoMoreRetries` (no further retry coming at all, ever, on any topic), it forgets every caseLink in the original `groups` map directly (`slices.Collect(maps.Keys(groups))`) — safe regardless of who currently holds a given key, since nothing will ever look at it again; on the whole call succeeding this round instead (a retry IS still coming), it forgets only `owned`. That distinction matters: two `Handle` calls can genuinely race on the same record (a Kafka consumer-group rebalance transition isn't guaranteed to be exclusive down to the microsecond — the same reasoning `claim`'s own doc comment gives), and a call that loses the claim race on some group attempts nothing for it, so its own error is nil either way — releasing anything wider than `owned` on the non-final branch let a losing call release a key a different, still in-flight call actively relies on staying claimed, letting a later retry reclaim and resend an email that hadn't even finished sending yet. This was a real, live-observed duplicate-email bug (see `TestDispatcher_Handle_LosingConcurrentCallDoesNotReleaseWinnersClaim`) before `sendPerGroup` returned `owned` at all. When `emailDebugMode` is true, `sendPerGroup` still runs `groupByLink` against the event's real recipients (so a broken resolver/entity-service still surfaces as an error) but calls `SendEmail` with `emailDebugRecipients` in place of each group's real recipients — still a real send, just redirected; the per-group tracking key is still based on the real resolved `caseLink`, unaffected by the redirect. If `emailDebugMode` is true and `emailDebugRecipients` is empty (misconfigured), that group is marked done and skipped (logged) rather than calling `SendEmail` with zero recipients — retrying wouldn't fix a missing debug-recipient config. `commentLinkFor(caseLink, commentID)` appends the `#<commentId>` suffix (empty `commentID` → bare link, used by the three non-comment types). `groupByLink` also returns `groupUserIDs map[string][]string` (caseLink → each group's recipients' entity-service user ids, from `recipientlinks.RecipientLink.UserID` — populated from the same `/users/search` response `internal/entity.UserRoleInfo` already decodes, just a field it wasn't reading before), which `sendPerGroup` logs (`"dispatch: email sent"`, `recipientUserIds`) once a send actually happens — never the recipient email addresses themselves, per this repo's own "no recipient emails in logs" convention (see `internal/entity`'s `do()` doc comment) — so a delivery is still traceable to a specific recipient. `displayCaseRef(caseNumber, caseID)` picks `CaseNumber` (the case's human-readable ServiceNow reference, e.g. `"CS0023001"`) over the UUID `CaseID` for every template display slot across all four `case.*` handlers, falling back to `CaseID` only if a publisher hasn't been updated to send `CaseNumber` yet — a raw UUID showing up in a case-created/comment-added/status-changed/case-assigned subject or body was a real, reported bug; `CaseID` itself is unchanged for link-building (`groupByLink`/`CSMLink`), which still needs the real id. `subjectLine(wso2CaseID, caseNumber, caseID, title)` builds every `case.*` email's subject in one explicitly-required standard format, `"[WSO2 Support] (<wso2 case id>/<case number>) <title>"` (first slot via `displayInternalRef(wso2CaseID, caseID)`, second via `displayCaseRef(caseNumber, caseID)`) — all four handlers use it now; `handleStatusChanged`/`handleCaseAssigned` fall back to a synthesized title (`"Status changed to <newStatus>"`/`"Case assigned"`) when `CaseTitle` is empty, since neither payload originally carried one (added alongside `CaseNumber` — see `events.StatusChangedPayload`/`CaseAssignedPayload`). `WSO2CaseID` (`wso2CaseId` on the wire) is ServiceNow's `u_wso2_case_id` custom field (`domain.CaseView.InternalID` in entity-service) — the CSM portal's own case identifier (e.g. `"WSO2-1000"`), distinct from `CaseNumber` (ServiceNow's own `"CS..."` number) and from `CaseID` (the raw UUID); matches the CSM portal frontend's own `wso2CaseId / caseNumber` pairing (`caseIdentity.ts`'s `caseIdLabel`). `displayInternalRef` falls back to the raw `CaseID` only if a publisher hasn't sent `WSO2CaseID` yet, same reasoning as `displayCaseRef`. `CaseAssignedPayload.AssigneeName`/`AssigneeEmail` identify who the case is now assigned *to* — not who performed the assignment (an earlier version was named `AssignerName`/`AssignerEmail`, but no publisher has ever had a way to resolve who performed an assignment; entity-service's own `AssigneeEmail` on its update request — the new assignee — is directly available with no extra identity resolution, so the payload was renamed to match what's actually resolvable). `RenderCaseAssignedEmail`'s template still reads "&lt;name&gt; (&lt;email&gt;) assigned to &lt;number&gt;" — the wording is unchanged from before the rename (matches an existing WSO2-support email format the product owner wants parity with); only which person's name/email fills the slot changed, from nobody (never resolvable) to the new assignee. `handleCommentAdded` branches on `events.CommentAddedPayload.IsInternalNote` (set by entity-service when the comment is a work note — never customer-visible; entity-service's own `publishCommentAddedEvent` already restricts `Recipients` to active internal users before publishing — see that service's own `CLAUDE.md`). **This dispatcher does not simply trust that, by explicit product decision, after a real reported leak**: `IsInternalNote` also re-filters `groups` down to the CSM-portal audience only, right after `groupByLink` resolves it — `groupByLink` has already classified every recipient into its own portal-audience group via `recipientlinks.Resolver`'s role-first/domain-fallback check (the identical "roles with internal" classification entity-service's own filter is built on), so keeping only the group whose key equals `links.CSMLink(caseID)` (deterministic — see that method's own doc comment: "no customer-facing equivalent") needs no further per-recipient lookup of its own. This closes the gap regardless of how it would have opened — a stale entity-service build, a future publisher that forgets the filter — without this dispatcher needing a database of its own. A work note whose only recipients are customer-portal-linked simply sends nothing (`sendPerGroup` over an empty map is a no-op, not an error). `true` renders via `notifications.RenderInternalNoteEmail` instead of `RenderCommentAddedEmail`, using `displayInternalRef(p.WSO2CaseID, p.CaseID)` (the internal case reference, e.g. `"WSO2-1000"`) rather than `displayCaseRef(p.CaseNumber, p.CaseID)` as the case reference — this audience is always internal staff, who recognize that reference, not ServiceNow's own case number. `internal_note.html` (`RenderInternalNoteEmail`) matches an existing internal WSO2-support email format: "&lt;name&gt; added work note on &lt;reference&gt;" instead of "&lt;name&gt; commented on case &lt;number&gt;", and no "Re: &lt;title&gt;" strap at all (an internal note isn't "about" the case title the way a reply is) — otherwise the same card/CTA layout as `comment_added.html`.

**`NewDispatcher`'s trailing `defaultCSMEmailCC []string` (`DEFAULT_CSM_EMAIL_CC`, comma-separated)** is CC'd on every `case.*` email's CSM-portal-link group only — `sendPerGroup` takes a `csmLink` argument (every caller passes `d.links.CSMLink(p.CaseID)`) and only the group whose `caseLink == csmLink` gets `d.defaultCSMEmailCC` on its `cc` list; the customer-portal group (or any other resolved link) never does, under any circumstances. Checked and applied strictly after `emailSendingEnabled`/`emailDebugMode`'s own gates: when `emailDebugMode` is true, `cc` is forced back to `nil` even for the CSM group — a debug run redirects `to` to `emailDebugRecipients` specifically so nothing reaches a real mailbox, and CC'ing this real, shared default inbox regardless would defeat that (see `TestDispatcher_Handle_DefaultCSMEmailCC_SuppressedInDebugMode`). Empty/unset `DEFAULT_CSM_EMAIL_CC` means no default CC at all, same as every other optional config here.

**Every email template (all `case.*`/CR/onboarding templates, plus both SLA breach templates above) carries an "Expected sent to: `<!-- [INTENDED_FOR] -->`" row, shown only on a debug-redirected send.** The row sits behind `applyOptionalBlock(tmpl, "INTENDED_FOR", intendedFor)` like every other optional field in this package — an empty `intendedFor` (the normal, non-debug case) drops the row entirely rather than rendering it blank, so a real recipient never sees it at all. `sendPerGroup` computes it once per group, right where it redirects `to` to `emailDebugRecipients`: `intendedFor = strings.Join(to, ", ")` (the group's real, pre-redirect recipients) when `emailDebugMode` is true, `""` otherwise — then passes it as a second argument to its `render(caseLink, intendedFor)` callback, which every `case.*` handler's closure threads straight into its `Render*` call (a new trailing `intendedFor string` param on the five plain-signature functions, a new `IntendedFor` field on every `*EmailData` struct otherwise). The three non-`sendPerGroup` paths (CR approval/plan-date-notice, both onboarding invitation/welcome emails) do the same thing inline, at their own `emailDebugMode` branch, before building their own `*EmailData`/`RenderProjectContact*` call. (`Engine.sendBreachEmails`, which used to follow this identical rule, no longer exists — see "SLA breach-alerting engine" below for why it was removed rather than ported.) The point is purely operational — so someone testing against `EMAIL_DEBUG_MODE=true` can tell, from the debug inbox alone, which real recipient a given redirected copy was actually meant for — and must never leak into a production send.

A case with recipients spanning both portal roles (customer-role + CSM-role) resolves to two `groupByLink` groups, which is correct: in production that's two separate emails to two different real audiences. When `emailDebugMode` is true, both groups still each send their own separate `SendEmail` call, just redirected to the same configured `emailDebugRecipients` — so a tester watching that inbox legitimately sees one email per real group. (An earlier version of this tried merging every group's already-rendered HTML document into one email in debug mode; that concatenated multiple complete `<html>` documents into one body, which is invalid markup — reverted. If a case's recipients genuinely span two portal roles, seeing two emails during debug testing is expected, not a bug — see `recipientlinks.Resolver.linkFor`'s email-domain fallback below for reducing *misclassification*-driven splits, which is a separate concern from this.) A comment/description's rich-text HTML (as ServiceNow/the portal editors produce it, e.g. `<p><span style="white-space: pre-wrap;">...</span></p>`) goes through `internal/notifications.sanitizeRichText` before it reaches any `Render*` template — a real HTML-tokenizer-based (`golang.org/x/net/html`, not regex) allow-list sanitizer, not a blunt strip-everything pass: structure (paragraphs/line breaks/lists/tables/headings/quotes/code blocks, plus a center/right/justify `text-align`), basic formatting (bold/italic/underline/strikethrough/inline code), safe hyperlinks (`http`/`https`/`mailto`/`tel` schemes only), and inline images are preserved; everything else drops to its own inner (escaped) text. This list is exactly what the announcement/comment editor's toolbar can produce (checked against the HTML Lexical itself exports for each format) — so a customer sees what the author composed; font size via the editor's Body/Caption block types is the one deliberate exception, since `rem`/`px` text sizing is unreliable across mail clients. Tables (`table`/`tr`/`th`/`td`), headings, quotes, `pre`/`code` and an aligned paragraph are re-emitted as fixed, hardcoded tags with inline styling — never the source's own attributes or styles (a `text-align` is reduced to one of three keywords) — and each cell's own leading/trailing paragraph breaks are trimmed; this exists because an announcement's product/version matrix used to arrive as one value per line. HTML void elements (`<col>`, `<hr>`, ...) never touch the sanitizer's tag stack, and any tag still open when the input ends is closed in reverse order, so a malformed unclosed `<table>` can't swallow the template's footer links. An inline image is never re-embedded as a `data:` URI in the output HTML — see "The WSO2 logo showed as a broken image in Gmail" below for why that gets stripped on render — instead `sanitizeRichText` decodes it, returns it separately as a `notifications.InlineImage{ContentID, ContentType, Data}`, and rewrites the tag to a short `<img src="cid:<contentId>">` reference. Every caller (`RenderCommentAddedEmail`/`RenderInternalNoteEmail`/`RenderCaseCreatedEmail`/`RenderCRPlanDateNoticeEmail`) returns `(string, []InlineImage)` instead of a plain string for this reason; `dispatch.sendPerGroup`'s own `render` callback returns the same pair, and converts the images to `[]notifications.EmailAttachment` (via `dispatch.inlineAttachments`, each marked `Inline: true` with its matching `ContentID`) passed straight into `EmailClient.SendEmail`'s `attachments` parameter — this is what actually makes the `cid:` reference resolve to a real, displayed image rather than a broken one.

**Two more real, reported email-rendering bugs, both fixed in `internal/notifications`:**

- **The WSO2 logo showed as a broken image in Gmail.** The templates used to bake the logo PNG in as an inline `data:image/png;base64,...` URI (`bakeLogo`, embedded via `go:embed`) specifically to avoid any external dependency — but Gmail (and most major webmail clients) strip `data:` URI images from received HTML mail as a security measure, regardless of how correctly they're encoded. At the time, a `cid:`-referenced inline MIME attachment would have avoided the external fetch too, but the internal email-sending service this client's API calls only supported `Content-Disposition: attachment`, not inline/`Content-ID` — so `cid:` wasn't an option for this yet either. The fix: `bakeLogo` substitutes `wso2LogoURL`, a real fetchable URL (`https://wso2.cachefly.net/wso2/sites/all/image_resources/logos/WSO2-Logo-Black.png` — WSO2's own CDN, not third-party hosting), instead of a data URI. Explicitly *not* self-hosted from this service's own endpoint (that was considered — it would need a new public route, and this service's own endpoint isn't reachable from outside WSO2's network, unlike Gmail's external fetcher) — the CDN URL was the simpler, already-available choice at the time. `templates/wso2-logo.png` and its `go:embed` were removed since nothing references the bytes anymore; the `<img>` tags in all four templates now declare `width="113" height="28"` (the real asset is 1277×317, not the old 300×119 — a mismatched `width`/`height` would stretch it in clients that don't recompute it themselves).

  **The `cid:` limitation this hit no longer applies.** The email-sending service (`infra-operations/operations/email-service`) now accepts an `inline`/`contentId` pair on its `EmailAttachment` schema (`POST /send-email`), and `EmailClient.EmailAttachment` here mirrors it — see `sanitizeRichText`'s own `InlineImage` extraction above, which is what actually uses this for a comment/description's own embedded images. The logo itself was deliberately left on the CDN URL rather than converted to a `cid:` attachment: it's one fixed, static asset shared by every email, and a hardcoded CDN link costs nothing per send, unlike an inline attachment (base64-encoded into every outgoing MIME message) — there's no reason to pay that cost for something that never changes.
- **A display name with a non-ASCII trailing marker (e.g. entity-service returning `"Jane Doe Ⓦ"`) rendered as a literal "?"** in the recipient's inbox. A browser renders raw UTF-8 fine, but `email.go`'s `EmailClient.SendEmail` reaches an external service over HTTP whose own send path doesn't reliably preserve non-ASCII bytes. Fix: `escapeHTML` (replacing every direct `html.EscapeString` call in `Render*`, and used inside `escapeMultiline`) HTML-escapes as before *and* additionally converts every rune above U+007F to a numeric HTML character reference (e.g. `Ⓦ` → `&#9420;`) — pure ASCII on the wire, decoded back to the original character by any HTML-capable mail client on display, regardless of what happens to raw multi-byte bytes in transit.

The "Add Comment" CTA in all four templates changed from a solid-background button to a plain colored text link (matching "View Case"'s existing style) — the email itself can't submit a comment, only deep-link into the portal, so a button implying an in-place action was misleading. The accent color used throughout every template (links, the CTA, the case-title strap line) changed from `#3b5bdb` to `rgb(71,96,146)`.

`handleCaseCreated` additionally posts a Google Chat alert via `GoogleChatClient.SendCaseCreatedAlert` — independent of the email step above (a failure in one is joined with, but doesn't suppress, the other). It always routes to the fixed `chataudience.IncidentMonitor` audience (see "case.* Chat cards" below for the card's own layout) — no team detection, no per-product routing, no publisher-suppliable override; this service has no real per-product Chat space need, so the earlier product-routed design (`GoogleChatConfig.Spaces`, `Dispatcher.defaultChatProduct`, `DEFAULT_CHAT_PRODUCT`) was removed entirely once that became clear. Its `caseLink` is `links.CSMLink(caseID)` (a `linkResolver` method, `recipientlinks.Resolver.CSMLink`) rather than a `groupByLink`-resolved link — a Chat post has no per-recipient audience to resolve against, so it always targets the CSM portal's case link, with no customer-portal equivalent. The Chat alert has its own idempotency-tracked `chatKey` (`baseKey+"/chat"`) — `handleCaseCreated` releases `chatKey` and every email group's key together, in one place, once `record.NoMoreRetries` or `beginRecord`/`endRecord` (`Dispatcher.records`) reports it's safe to (see `beginRecord`'s own doc comment) — never on any single channel's own success alone. `beginRecord`/`endRecord` replaced an earlier `chatOwned && len(errs) == 0` check: that read "my own attempt saw zero errors" as "the whole record is done," which a call that lost the email claim race (and so attempted nothing for email) could satisfy trivially — letting it release `chatKey` while a different, still in-flight call was genuinely mid-`SendEmail` for the same record, which could then reclaim and resend the Chat alert. `beginRecord`/`endRecord` tracks how many concurrent `Handle` calls are in flight for a given `baseKey` and whether any of them hit an error, so the release only fires for whichever call is provably the last one still working on it — see `TestDispatcher_Handle_CaseCreated_ConcurrentBlockedEmailDoesNotDuplicateChat` for the regression this closed (three separate real bugs total have now been caught by regression tests in this area before landing: releasing on a single channel's success, releasing on the main topic's own final attempt when a DLQ tier is still coming, and this concurrent cross-channel release). `handleSeverityChanged` (below) uses the same `beginRecord`/`endRecord` mechanism for its own two channels (email + chat), for the same reason: a losing call for one channel must not release the other while a different, still in-flight call genuinely owns it.

`incident.created` skips the email/link-resolution path entirely and has two independent reactions: `TwilioClient.MakeCall` from the payload's own `CallTo` field (substituting `defaultOnCallNumber` when it's empty; skipped and treated as succeeded when the resolved number is empty or `callSendingEnabled` is false), and the "Incident Reported" Chat card (see "Incident Chat cards" below). Two channels, so `handleIncidentCreated` uses `handleCaseCreated`'s `beginRecord`/`endRecord` shape with `callKey`/`chatKey` (`baseKey+"/call"`/`"/chat"`): a channel that succeeded keeps its claim until the whole record succeeds or `record.NoMoreRetries`, so a retry caused by a failing Chat post never places the call again (`TestDispatcher_Handle_IncidentCreated_ChatRetryDoesNotRepeatTheCall`). `record.IsFinalAttempt` is deliberately NOT used for the release, for the same DLQ-rekeying reason as every other handler here. `IncidentCreatedPayload.Product` is still accepted on the wire (decode compatibility) but not read.

**The Alert Settings mapping decides an incident's room, ahead of `INCIDENT_CHAT_SPACES`** (`paging/incident_routes.go`, `notifications/googlechat_incident.go`, `applyIncidentRoutes` in `cmd/server/main.go`). **`case.*` Chat cards — `POST /cases` only, never `POST /incidents`.** `SendCaseCreatedAlert`/`SendCaseAcknowledgedAlert`/`SendSeverityChangedAlert` (redesigned together, many times over, in direct response to live screenshots from a real deployment — see each function's own doc comment for the exact, current shape) share several conventions but differ in structure. Shared: no buttons at all — every navigation target is a real, visible `<a href>` inside a plain-text widget, never a `ButtonList` (on the case-created, security-report-analysis and severity-changed cards it is the case reference itself; `SendCaseAcknowledgedAlert` and `SendFrustrationAlert` still end on a "View case" link), since opening the case is navigation, not a genuine one-click action from Chat today. No leading icon or emoji on any body line either — Chat's native `decoratedText` icon has a fixed, non-configurable gap from its text, and an inline emoji glyph was tried and dropped too — both cost width a narrow (mobile) screen needs for the text itself, without adding information. `dispatch.severityLabelAndColor(severity)` maps the raw uppercase severity string entity-service sends (e.g. `"CRITICAL"`) to the label/color pair every card uses — `S0`-catastrophic/`S1`-critical/`S2`-high/`S3`-medium, `S4`-low is this service's own extrapolation to keep the map total, falling back to the raw value in neutral gray for anything unrecognized. `HIGH`'s color (`#F97316`, a distinctly orange hue) was corrected from an earlier red-leaning orange (`#EA580C`) that read too close to `CRITICAL`'s red in a real card — a live-testing catch, not a made-up value. `caseAlertLine` (in `googlechat.go`) HTML-escapes each dynamic value before formatting it into a widget's surrounding markup — the same reasoning as `internal/notifications`' own `escapeHTML` for email templates: Chat's card text interprets a limited HTML subset, so an unescaped value containing `<`/`&` could break out of its tag. `teamPart(team)` renders team **bold, in one color for every team** (`teamTextColor`, the muted gray `#5F6368` team names have always had here) and returns `""`, not a styled empty string, when team is blank, so callers just skip appending it (no blank line), rather than joining it onto another line. Two color schemes were built and dropped on request: a per-ABT palette (Sirius blue, Atlas green, Castor teal, ...), as more upkeep than it was worth since every new team would need a color, and then a single green, in favor of the established gray. The team line stands out by being bold and first, not by hue.

**The `case.*` cards have no header, so the team can be the first line.** A Chat card header is always drawn above every widget, and its fields are plain text (no color, no bold, fixed size) — so with a header the team could never lead the card or carry its color. A version that put team in the header subtitle was tried and reverted for the same reason; a later one kept the header and put team first in the body, directly under the ticket, in muted gray, which read as an afterthought next to the ticket. The cards are now headerless, matching ServiceNow's own alert, and laid out as two blocks with a divider between them (`caseCardWidgets(top, ref)` → `[top text, divider, case reference]` in one section). **Top:** team (`teamPart`, omitted when empty), then severity (or the severity-change transition, or SRA's fixed label), then product (bold, omitted when empty). **Bottom:** the case reference `"<caseNumber> · <wso2CaseID>"` (`caseRefWidget`; `chatHeaderCaseRef`, falling back to caseNumber alone), with no "new" marker (a `🆕` on the created cards' reference was tried and removed on request), with the reference as the **link to the case** (`<a href>`, plain link text, not also bold — nesting `<a>` in `<b>` is not documented Chat markup; there is no separate "View case" line on these cards any more, by request; a missing link falls back to the bold reference), and beneath it the case subject — a `decoratedText` widget (`chatDecoratedText`) whose `text` is the linked reference and whose `bottomLabel` is the subject. That is deliberate: card text markup (`b`, `i`, `u`, `s`, `font color`, `a`, `br`, `code`, lists) has no font size, and a label is the one place Chat draws smaller, muted text, so the description reads a little smaller than the rest. A label is a plain string, so the subject goes through verbatim, not HTML-escaped (escaping would print a literal `&amp;`), with no bold or color; Chat's reference says `bottomLabel` always wraps, and `wrapText` is set on the main text too. How a webhook-posted label actually renders is not documented — check it on dev. The divider (cardsV2's `divider` widget, `chatCardWidget.Divider`, which must marshal as `{}`) is the line the header used to draw; it is dropped when either block is empty rather than left dangling, so an empty text widget is never sent. `cardParts` in `googlechat_test.go` asserts that shape for every team-showing card. The ticket loses the header's larger monospace styling and becomes a bold body line; that is the price of putting team first. `SendCaseAcknowledgedAlert` was already headerless and still never shows team.

**`project_contact.invited` (`handleProjectContactInvited`) — the consumer side of the customer onboarding flow** (Salesforce membership → entity-service's Postgres → Asgardeo identity → invitation email → first-access registration; see entity-service's own `CLAUDE.md`, "Salesforce membership ingest and onboarding steps", and the onboarding-step API it documents). Published by entity-service's membership ingest (since PR #1902) once a `Project_Contact__c` in state INVITED / RE-INVITED is in Postgres, keyed by the Salesforce membership Id (`EntityID` — `events.Validate` requires it to match the payload's own `membershipSfId`, like the `case.*` types' `caseId`; only `membershipSfId` and a well-formed `email` are required, `givenName`/`familyName` may be empty). `events.ProjectContactInvitedPayload` mirrors entity-service's struct by hand. **Two sequential steps, not two independent reactions**: IDENTITY (`internal/scim.Client.EnsureExternalUser`) then EMAIL (`notifications.RenderProjectContactInvitedNewEmail`/`RenderProjectContactInvitedExistingEmail`/`RenderProjectContactInvitedReminderEmail`, three templates differing in wording only — the "new" one welcomes a just-created account and explains the first-sign-in email code, the "existing" one says the project was added to an account the reader already has, the "reminder" one just repeats the invitation, for a resend — see "Resending an invitation" below). Sequential because the email's wording depends on the identity step's `existed` answer, and a failed identity step must return before any email — the invitee must not be told to sign in to an account that doesn't exist. Rules: an `isIntegrationUser` contact records IDENTITY=SKIPPED and EMAIL=SKIPPED and does nothing else (machine accounts never sign in); each step is behind its own opt-in flag, `CSM_MIGRATION_ONBOARD_IDENTITY_ENABLED`/`CSM_MIGRATION_ONBOARD_EMAIL_ENABLED` (read through `envBool(name, false)` in `cmd/server/main.go` — the one helper every boolean env var goes through, with the default spelled out at the call site: killswitches like `EMAIL_SENDING_ENABLED` pass `true`, every `CSM_MIGRATION_*` flag passes `false`; default off — a disabled step is recorded SKIPPED); a failed step records FAILED with the error text and **returns the error**, so the usual retry/DLQ path applies; the "existing" wording is used only when identity actually ran this record and said `existed=true` — with identity off nothing can know, so the "new" wording is used (welcoming someone who already has an account is the cheaper mistake). The invitation goes to the invitee alone (no CC/BCC, no `groupByLink` — one configured sign-in URL, `ONBOARD_PORTAL_URL`, not a per-recipient case link), from `ONBOARD_EMAIL_FROM` (falls back to `EMAIL_FROM_ADDRESS`) through the shared `notifications.EmailClient` via `SendEmailFrom` (one client, one token cache; only the sender differs), with the sender resolved in `cmd/server/main.go`'s `loadOnboardingConfig`. It still honours the service-wide `EMAIL_SENDING_ENABLED` killswitch (recorded SKIPPED, not FAILED) and `EMAIL_DEBUG_MODE`'s redirect, the same as every other email here. Wired via `Dispatcher.WithOnboarding(dispatch.OnboardingConfig)` rather than more positional `NewDispatcher` params, since the whole feature is optional and orthogonal to every other type. **Step recording is deliberately best-effort** (`recordOnboardingStep` → `entity.RecordOnboardingStep`, `PUT /onboarding-steps/{membershipSfId}/{step}` with `{status, lastError?, eventType: "project_contact.invited", eventModifiedOn, email, contactSfId}`): a failure to record is logged at ERROR and otherwise ignored — it must never mask the step's own error, and must never turn a succeeded step (especially a sent email) into a retried one. `eventModifiedOn` is the payload's `eventModifiedOn` — the membership's Salesforce `LastModifiedDate`, which entity-service puts on the event: entity-service only applies a step write whose `eventModifiedOn` is not older than the stored one, so a delayed delivery of an older invitation cannot overwrite a newer one's outcome, while retries of the same version (equal timestamps) still land. Only a payload with no timestamp falls back to the processing time. **Retry safety**: `EnsureExternalUser` is idempotent upstream, but re-running it on a retry caused by the *email* failing would answer `existed=true` for a user the previous attempt itself created — and the retry would send the "you already have an account" wording to someone never told they have one. `Dispatcher.identityExisted` (guarded by `doneMu`, keyed `recordBaseKey+"/identity"`) remembers the first successful answer per record, and the whole attempt is guarded by a per-record `claim()` (released when `Handle` returns) so two racing Handle calls cannot both provision or both send and skips the SCIM call on the retry; released on full success or `record.NoMoreRetries` (never `IsFinalAttempt` — same DLQ-rekeying reasoning as every other release here) — see `TestDispatcher_Handle_ProjectContactInvited_EmailFailureThenRetry`. No `claim`/`forget` on the email itself: nothing after `SendEmail` can fail in a way that triggers a retry (recording is best-effort), so this handler's own retries never re-send a sent invitation. Logs `membershipSfId`/`contactSfId`/`projectKey` and the Asgardeo user id, **never the invitee's email** — this repo's own "no recipient emails in logs" convention. Ops prerequisites: this service's OAuth2 client id must be in entity-service's `AUTH_INTERNAL_CLIENT_IDS` (the onboarding-steps endpoints are internal-caller-only, a 403 there means exactly that), and `SCIM_BASE_URL`/`SCIM_SCOPES` must point at the SCIM operations service (digiops-infra#345's `POST /organizations/external/users`). `cmd/preview` renders the "new" variant for this type. **Duplicate invitations are checked against the ledger, not against memory.** Immediately before sending, the handler calls `SucceededEmailStep` (`GET /onboarding-steps/{membershipSfId}`, `internal/entity`) and skips when a SUCCEEDED EMAIL step already exists **for this membership version** (`Dispatcher.invitationAlreadySent`): the row's `eventModifiedOn` is not before the event's. The ledger keeps one EMAIL row per membership, so without the version check the first invitation blocked every later one — a contact deactivated and then re-invited (a newer Salesforce `LastModifiedDate`) never got an email. Salesforce's several UPDATED events per save and redeliveries carry the same or an older version and are still skipped; a re-invitation carries a newer one and sends. When either timestamp is missing, zero or unparseable the versions cannot be compared and any SUCCEEDED row still means sent (logged at WARN) — a lost re-invitation can be recovered with a resend, a duplicate e-mail cannot be taken back. It is the only one of the three guards that sees state from outside this process: the in-process claim lives for one process and the ingest's duplicate check only recognises an unchanged Salesforce version, so neither covers a redelivery after a restart, a replay from the dead-letter topic, or the case this exists for — the customer portal onboarding a contact synchronously, with the Salesforce event for the same contact reaching the ingest afterwards as a new version. It is a **read of shared state, not a lock**: two replicas can both read "not sent" before either sends, and a send whose SUCCEEDED write then fails leaves nothing for the next delivery to find. Both windows need a coincidence (concurrent delivery of one record across a consumer-group rebalance; the ledger write and the offset commit failing together) and cost one repeated welcome e-mail; closing them properly needs an atomic reservation in entity-service, which is deliberately not built yet. A ledger read that fails is an error, never a quiet "nothing has been sent": the record is retried rather than risking a second invitation, and a missing recorder (`OnboardingConfig.Steps == nil`) is the same kind of error rather than a silent skip — *recording* a step outcome tolerates a nil ledger, sending with nothing to check against does not (a resend, which never reads the ledger, is unaffected). The write that records the send is issued on `context.WithoutCancel` for the same reason — a shutdown that cancelled it would lose the SUCCEEDED row for an e-mail that had already gone out, and the same shutdown would likely lose the offset commit too, turning one invitation into two on restart. Only EMAIL is guarded this way — a repeated identity call is harmless, since the SCIM endpoint is create-if-absent.

**`project_contact.registered` (`handleProjectContactRegistered`)** sends the Welcome email once per membership after first sign-in. Same flags as the invitation; the `WELCOME_EMAIL` step is its duplicate guard.

**Resending an invitation deliberately bypasses that guard.** `ProjectContactInvitedPayload.IsResend` (`isResend` on the wire, `omitempty` — an absent value is a normal, first invitation) is set by entity-service when it republishes the same `project_contact.invited` event because an admin pressed "Resend invitation" in the portal. When it is set, `handleProjectContactInvited` skips the `SucceededEmailStep` read entirely and sends. The guard exists to stop an *accidental* second invitation — the entity service writes Salesforce as well as its own database now, so every portal invitation produces a Salesforce event that comes back through the ingest, and without the guard one invite would send two emails — and a requested resend is by definition not that. Nothing else changes: the EMAIL step is still recorded, so the ledger's `attemptCount` keeps showing how many invitations actually went out, and the identity step is untouched (the SCIM endpoint is create-if-absent, so a resend simply finds the account the first invitation created). A resend also always uses the **reminder** template, whatever the identity step answered: by then the account exists, so the unguarded template choice would reach for the "you already have a WSO2 account" wording, which reads as nonsense to someone who never received the first email — and the "new" wording would welcome them a second time. Choosing on the marker rather than on `existed` also sidesteps having to remember whether *we* created the account the first time. The reminder is short and deliberately claims neither ("Here is your invitation … again. Sign in with your email address …"), sharing `project_contact_invited_new.html`'s card layout, project name/key, sign-in link and optional roles block, with no `ACCOUNT_*` blocks at all. Its subject is `"[WSO2 Support] Reminder: your invitation to <project>"`. Validation is unchanged — `isResend` is valid present or absent and nothing depends on it being there.

**Its own topic pair.** `project_contact.invited` does not arrive on `EVENT_HUB_TOPIC` (in practice `case-events`): it has `PROJECT_EVENT_HUB_TOPIC` (default `project-events`) and `PROJECT_EVENT_HUB_DLQ_TOPIC` (default `project-events-dlq`), wired in `cmd/server/main.go` exactly like the change-request pair — `envOrDefault` config off the same broker/connection string, `PROJECT_CONSUMER_GROUP`/`PROJECT_DLQ_CONSUMER_GROUP` (defaults `csm-notification-service-project`/`-project-dlq`), `PROJECT_CONSUMER_COUNT`/`PROJECT_DLQ_CONSUMER_COUNT`, its own `eventbus.Producer` and `projectToDeadLetter`, and two `startConsumers` calls (`"project"`, `"project-dlq"`) both dispatching through the same `dispatcher.Handle`. Same reasoning as the change-request split: a separate consumer group isolates processing, only a separate topic isolates volume — an invitation backlog must never sit behind a flood of case events, and this dead-letter queue is watched on its own. Only this event type moved; `case.*` and the rest stay on the main topic.

- **Dead-letter queue** — a record whose `Handle` call fails on all `handleAttempts` attempts is published to `EVENT_HUB_DLQ_TOPIC` (see `cmd/server/main.go`'s `toDeadLetter` func, `eventbus.OnExhausted`) instead of being dropped. This service also runs a second, independent consumer group against that DLQ topic, using the *same* `dispatcher.Handle` — so a dead-lettered record gets its own fresh `handleAttempts` retry pass — but with `onExhausted=nil`, so a record that fails there too is logged at ERROR and dropped for good; there is deliberately no third tier. If `EVENT_HUB_DLQ_TOPIC`'s Event Hub doesn't exist yet in Azure, provision it before deploying — this service does not create topics itself.
- **`cmd/server/main.go`** — constructs `eventBusCfg`/`dlqCfg` from `mustEnv` (not `os.Getenv`): unlike the notification channels, broken event bus config should fail startup loudly since consuming (and dead-lettering) events is this service's core job. `startConsumers(ctx, name, cfg, group, count, handle, onExhausted)` first calls `eventbus.PartitionCount` and logs a warning (never fails startup) if `count` exceeds the topic's real partition count — Kafka just leaves the excess consumers idle rather than erroring, so a warning is the right severity — then starts `count` independent `eventbus.Consumer` instances, each in its own goroutine, all joining the same consumer group; Kafka's own rebalancing splits the topic's partitions across however many are actually running. Called once per topic: the main topic (`MAIN_CONSUMER_COUNT`, `toDeadLetter` as `onExhausted`), its DLQ (`DLQ_CONSUMER_COUNT`, `onExhausted=nil`), and the same main/DLQ pairing again for the change-request topics (`CR_EVENT_HUB_TOPIC`/`CR_EVENT_HUB_DLQ_TOPIC`) and the onboarding topics (`PROJECT_EVENT_HUB_TOPIC`/`PROJECT_EVENT_HUB_DLQ_TOPIC`) — each pair with its own consumer groups, counts, dead-letter producer and `onExhausted`, all handled by the one `dispatcher.Handle`. Both sets of consumers are closed explicitly on shutdown (after `ctx` is canceled, before the HTTP server's own `Shutdown`) so each instance leaves its consumer group gracefully rather than waiting out the session timeout.

## SLA breach-alerting engine

**Updated for entity-service's condition-driven SLA engine (internal/slacondition) — three things below are now stale and superseded, kept only as history:**

1. **The static `sla_duration_policy` table is dropped, but `GET /sla-duration-policy` itself is still live** — entity-service now computes that endpoint's response from the real `sla`/`sla_policy` tables instead (resolved per severity/clock-type by real conditions, not a flat lookup; see that repo's own `CLAUDE.md`). `EntityClient.GetDurationPolicy` here is unchanged and still works: `internal/paging`'s own rung-email feature (`cmd/server/main.go`'s `slaDurations`/`RungEmailSending.SLADurations`) is a real, live consumer of it (a "response SLA remaining time" display) — this was briefly, mistakenly assumed dead and the endpoint deleted entirely, then restored once that was caught. `slaengine.Engine` itself still doesn't call `GetDurationPolicy` or hold a `durations` map: `RegisterClocks` fetches each clock type's real duration live, per clock, via `GetClockState`; `reconcileClock` reads it straight off the bulk `GetActiveCSMSLAClocks` response (`activeSLAClock.DurationSeconds`, entity-service's `domain.SLAStatus.DurationSeconds`) with no extra round trip. `NewEngine` has no `durations` parameter, and its construction in `main.go` does not wait on the (unrelated) rung-email duration fetch succeeding — a failure there must not also disable SLA breach tracking.
2. **Every `GET /sla-status`/`GET /sla-status/clock-state` call this engine makes passes `source=csm`** (`slaEngineSourceFilter` in `client.go`) — entity-service's in-process SLA engine tags its own clocks `source='CSM'`: `'CSM'` = this engine's own rows, `'SERVICENOW'` = a real, independent, continuously-running external sync job's rows. `'SERVICENOW'` must never be used for an engine-managed clock — doing so would let this engine's reads collide with that sync job's own rows for the same case. Both `GetActiveCSMSLAClocks` (bulk reconciliation) and `GetClockState` (the single-clock pre-alert check) share the one `slaEngineSourceFilter` constant, so this scoping applies equally to both, not just the bulk listing.
3. **`ApplyStateEffects` no longer matches `newStatus` against a hardcoded pause-state list** (`"Awaiting Info"`/`"Solution Proposed"` used to always mean pause). That list disagreed with the real, per-policy `pause_condition`/`resume_condition` the condition-driven engine evaluates — not every policy pauses on the identical set of states. `entityPauseStatus(ctx, caseID, clockType)` asks entity-service's own `GetClockState` (now also returning `IsPaused`) instead, per clock type, for every status except the still-hardcoded `"Closed"` (a genuine lifecycle terminus, not a pause-state guess). `e.entity == nil` or a lookup failure both default to "not paused" (fail-open toward sending, same posture `sendBreachAlert`'s own entity-service check already has).
4. **A Redis failure defers rather than degrading.** `Tick`/`processDueMember`'s own Redis calls (`DueMembers`, `GetClock`, `ClaimTier`) are wrapped in a bounded retry (`withRedisRetry`, 3 attempts, 150ms apart). If `GetClock` still fails after retrying, `processDueMemberFallback` logs the member and leaves its wake entry exactly where it is — it does **not** send a degraded alert from entity-service's own live state. An earlier version did, but recording that a degraded send happened needs the same Redis commands that just failed, so an outage spanning more than one tick could resend the same degraded alert on every tick it stayed down, and a recovered normal tick could then claim the tier fresh and send again — a real duplicate-alert risk. Leaving the member untouched means the next successful tick's normal, `ClaimTier`-guarded path sends exactly once, as soon as Redis recovers: an outage delays a breach alert rather than ever risking a duplicate.
5. **`RegisterClocks`/`reconcileClock`/`resumeShift` schedule and recompute tier/breach wake-ups with the same business-day-aware math entity-service's own engine uses, for any policy whose `schedule` is `'WSO2 Business days'`** — flat `startedAt.Add(duration)` math is wrong for one: a 240h business-day RESOLUTION clock starting on a Friday needs the real business-day-adjusted due instant (which skips weekends), not Friday+240h calendar time. `GetClockState`/`GetActiveCSMSLAClocks` carry each clock's own `Schedule` (mirroring entity-service's `domain.SLAClockState.Schedule`/`SLAStatus.Schedule`); `internal/businessdays` (ported by hand from entity-service's own package of the same name, the same cross-repo convention `internal/events`/`internal/eventbus` already follow) provides `AddBusinessDuration(start, d)`, the inverse of entity-service's `Elapsed`: the instant reached after adding `d` of business-day time to `start`, skipping weekends, decided in `America/New_York` exactly like entity-service's own calendar. `dueInstant`/`tierTime`/`dueAtAndTierDuration` (`engine.go`) pick `AddBusinessDuration` over flat `Add` based on the clock's own `Schedule`; every other schedule value (`""`/`'24 x 7'`/unsupported) behaves as flat wall-clock time. `resumeShift`'s own business-day branch (`resumeShiftBusinessDays`) recomputes each not-yet-alerted tier's absolute wake time from `AddBusinessDuration(startedAt, tierFraction(duration, tier) + businessPause)` rather than incrementing by a flat pause delta — `GetClockState` carries `BusinessPauseDurationSeconds` (entity-service's `business_pause_duration` column) for exactly this. **Known, accepted, bounded limitation**: `reconcileClock`'s own pause-offset folding still uses the flat `PauseDurationSeconds`/`PausedOn` fields, since `activeSLAClock` (the bulk `GET /sla-status` response) doesn't carry a business-pause total the way the single-clock `GetClockState` now does — so a paused-and-resumed business-day clock's *reconciled* (startup-recovery) wake times, as opposed to its normally-resumed ones, can still be off by however much of that pause fell on a weekend. Revisit by adding a business-pause-total field to the bulk response if this proves to matter in practice.
6. **`RegisterClocks`/`entityPauseStatus` retry a short, bounded number of times (`getClockStateWithRetry`, 2 attempts, 300ms apart) before accepting entity-service's `GetClockState` answer of "not found yet."** entity-service publishes `case.created`/`case.status_changed` BEFORE it registers/applies the case's real SLA clocks, not after (confirmed: this ordering in that repo's own `sn_case_service.go` predates and is untouched by any of this engine's own work) — so this Kafka consumer, reacting to the very same event, can race ahead of entity-service's own write and see "not found" on its first read even though entity-service is a moment away from writing the row. A short retry closes that race without reordering entity-service's publish (which could have other side effects). Kept short on purpose: "not found" is also the ordinary, permanent answer for a clock type a case's policy genuinely never registers (e.g. a LOW/S4 case with no workaround/resolution policy at all) — the overwhelmingly more common case on every status change after the first — so a long or many-attempt retry would pay that cost needlessly on every one of those.

---

`internal/slaengine` is **not a Kafka consumer of its own** — `internal/dispatch.Dispatcher` is the one and only Kafka consumer in this service; `slaengine.Engine`'s four triggers (`RegisterClocks`/`ApplyStateEffects`/`CompleteResponseClock`/`CompleteWorkaroundClock`) are called directly from four of `Dispatcher`'s existing handlers (`handleCaseCreated`/`handleStatusChanged`/`handleCommentAdded`/`handleWorkaroundProvided`), the same way `dispatch.checkFrustration` is. Only `RunTicker` runs as its own goroutine, scanning a Redis wake-index on a plain ticker (`SLA_TICK_INTERVAL`, default `5m`) for a newly-due 50%/75%/100% checkpoint.

**Division of responsibility**: entity-service's job is to *trigger* — it already publishes `case.created`/`case.status_changed`/`case.comment_added` for its own reasons, and adds a couple of things this engine needs that it's uniquely positioned to compute: `events.CommentAddedPayload.IsSupportEngineerResponse` (it owns the role data; this service has no identity/role lookup of its own), and a standalone `case.workaround_provided` event (see `CompleteWorkaroundClock`'s own doc comment below — unlike the other two signals, there's no existing event a workaround-provided fact could ride on, so it gets a minimal one of its own). This engine owns the actual SLA *policy interpretation and tracking* — durations, due dates, pause/resume, tier detection, alerting — driven entirely by those events plus one small, static reference table fetched once at startup (`GET /sla-duration-policy`).

**Replaces a design that polled entity-service's `GET /sla-status` in bulk, every tick** — that endpoint (backed by the ServiceNow-synced `sla`/`sla_policy` tables) turned out to be genuinely too slow at real data volumes: its `OFFSET`-paginated query re-ran a full `DISTINCT ON`/sort/join from scratch on every single page (measured live: 6-34+ seconds per page), reliably tripping the gateway timeout between this service and entity-service — the `"slaengine: tick failed" ... upstream returned 503`/connection-reset errors this redesign exists to fix. Before that, an even earlier design hand-registered a clock per case on a now-removed entity-service `sla_clocks` table (a stand-in built before entity-service had real SLA data) and scheduled a Redis wake-index off a locally-computed due date — this design revives that mechanism (the wake-index itself was always sound) without reviving its entity-service dependency: every clock's state lives in Redis now, nowhere else. `events.TypeSLATierReached`/`SLATierReachedPayload` survive unchanged across all three designs.

- **`client.go`** — `EntityClient.GetDurationPolicy(ctx)` and `GetActiveCSMSLAClocks(ctx)` are the two entity-service calls this engine makes at `cmd/server/main.go` startup. `GetDurationPolicy`: `GET /sla-duration-policy` (a small, static reference table — at most 15 rows, severity × clock type, seeded directly from WSO2's own published Enterprise Support Policy, independent of `sla`/`sla_policy`) is parsed into `map[severity]map[clockType]time.Duration`, keyed by the same uppercase English word (`"CATASTROPHIC"`) a `case.created` payload's own `Priority` field carries — no translation needed to look a case's durations up by its own severity. A fetch failure here is loud (`slog.Error`) but not fatal: `main.go` simply never constructs the engine or starts `RunTicker` for this run (SLA tracking disabled, not a crash loop) — this is a nice-to-have layered on top of the notification channels this service exists for, not core delivery. `GetActiveCSMSLAClocks` pages through `GET /sla-status?source=csm` (`activeSLAStatusPageSize` = 200 rows per page) and backs `Engine.Reconcile` — see that method's own doc comment and the bullet below. A third, narrower method, `GetClockState(ctx, caseID, clockType)`, calls entity-service's own `GET /sla-status/clock-state?workItemId=<caseId>&target=<clockType>&source=csm` — a **separate, dedicated endpoint** from `GET /sla-status`, not a filter on it (see that repo's own `CLAUDE.md`, "SLA status", for why a CodeRabbit review specifically rejected the filter approach an earlier version of this tried) — returning that one clock's full current state (`Found`/`IsActive`/`Stage`/`HasBreached`/`StartedOn`) regardless of whether it's active. See `sendBreachAlert`'s own bullet below for what it's for and when it's called; unlike the two startup-only calls, this one runs on the hot alerting path, once per tier about to be sent.
- **`redis.go`** — `Store` holds everything in Redis, nothing durable anywhere else:
  - **`sla:wake`**, one ZSET for the whole engine — member `"<caseId>|<clockType>|<tier>"`, score = that tier's due-at Unix timestamp. Ported from the pre-poll design's own `WakeIndex`.
  - **`sla:clock:<caseId>|<clockType>`**, one HASH per clock — the Chat card's own display fields (`caseNumber`/`wso2CaseId`/`caseTitle`/`caseType`/`product`/`team`/`priority`/`startedAt`, written once by `RegisterClocks` and never refreshed, except `state`, which `ApplyStateEffects` keeps current on every `case.status_changed`), a `paused` flag, and an `alertedTier` cursor (0/50/75/100 — the highest tier already alerted *or force-completed*, same semantics a plain poll-engine cursor would have, just stored alongside the clock's own metadata instead of as a separate key). All refreshed with a generous `clockTTL` (90 days) on every write, so a clock with no further write ever touching it (a long-closed case) expires on its own.
  - **`sla:tier-claimed:<caseId>|<clockType>|<tier>|<startedAt>`**, a plain SETNX claim per tier — unchanged in spirit from the poll-engine's own `TierStore.ClaimTier`: if this service is ever deployed with more than one replica, only the replica that wins the claim alerts. `startedAt` (the clock's own Unix start timestamp) is part of the key — see the `setClockScript`/"incarnation" note just below for why.
  - `AdvanceAlertedTier` is a Lua script (ported from the poll-engine's own `advanceTierScript`, just against a hash field instead of a plain key) that only ever moves the cursor *forward* — the same compare-and-set two independent callers (a `Tick` claim, and `CompleteResponseClock`/`ApplyStateEffects`' `CLOSED` branch) need to never race each other backward.
  - **`setClockScript` is incarnation-aware, not just replay-safe.** It already protected against a redelivered `case.created` silently resetting `alertedTier`/`paused` back to zero (via `HSETNX`, never overwriting an existing value) — but a CodeRabbit review on the `Reconcile` addition below caught the matching failure mode the *other* direction: entity-service's `ReviseCaseClocks` cancels a case's existing clocks and registers entirely fresh ones (a new `start_on`, no relation to the old elapsed time) on a severity change, and `Reconcile` reads whichever row is currently active — so it can observe a case's clock jump to a new `startedAt` with no event telling this engine so in between. Without a fix, a tier already alerted under the OLD `startedAt` (`alertedTier` already at, say, 100) would make `processDueMember`'s own `"AlertedTier >= tier"` check permanently swallow every one of the NEW incarnation's own tier crossings — a silent, total loss of alerting for that clock, with no error anywhere. The script now compares the hash's stored `startedAt` to the incoming one before writing: unchanged (a genuine replay) preserves `alertedTier` exactly as before; changed (a new incarnation) resets it to `0`. `ClaimTier`/`ReleaseTier`/`tierClaimKey` take the matching half of this fix — `startedAt` is part of the claim key, so a stale, unexpired claim from the OLD incarnation can't suppress the NEW one's genuine first alert either; `processDueMember` passes `meta.StartedAt` (from its own `GetClock` call) into both, never a value it computes itself. Verified against a real Redis instance (`internal/slaengine/redis_test.go`, gated the same way `internal/paging/store_test.go` is) — this class of bug lives entirely in the Lua script's own logic, which the package's Go-level fake-backed tests can't exercise.
  - **`AdvanceAlertedTier`/`RemoveWake` needed the identical incarnation guard one call further down, caught on a second CodeRabbit pass.** `ClaimTier` alone isn't enough: a tick that already won its (incarnation-scoped) claim under the OLD clock can still race a replacement registration landing *after* the claim but *before* this same tick's own later `AdvanceAlertedTier`/`RemoveWake` calls — both of which previously had no incarnation awareness at all, since they act on whatever the hash/wake-index currently hold, not on what this tick originally observed. `AdvanceAlertedTier` now takes the clock's `incarnation time.Time` too (`processDueMember` passes `meta.StartedAt`, the same value it already used for `ClaimTier`) and its own Lua script returns `applied=false`, touching nothing, when the hash's current `startedAt` no longer matches — `processDueMember` then skips `RemoveWake` entirely on that branch: the wake-index member for that `(caseID, clockType, tier)` may by then already be the NEW incarnation's own, independently-scheduled entry (`AddWake` overwrites the same ZSET member), and deleting it would silently cancel a still-pending future alert that has nothing to do with the stale tick. `CompleteResponseClock`/`ApplyStateEffects`' `CLOSED` branch pass the zero `time.Time{}` — they're reacting to a live event about the case right now, not working from a possibly-stale snapshot, so there's no incarnation to compare against and the update always applies, same as before this guard existed. `reconcileClock`'s own pre-claim call now passes the incarnation it just wrote via `SetClock` too, for the same reasoning. See `TestEngine_ProcessDueMember_IncarnationChangedMidFlight_DoesNotClobberNewClock` for the regression test (a wrapped fake store that injects the exact race window between `ClaimTier` succeeding and the later calls).
  - **`startedAt` is stored as `UnixNano`, not `Unix` (whole seconds) — a third CodeRabbit finding on the same feature.** Two genuinely different incarnations of the same `(caseID, clockType)` pair can land within the same wall-clock second (a fast severity re-revision, or simply two clock types of one case revised back-to-back) — a whole-seconds timestamp can't tell them apart, so the incarnation check above would wrongly treat the second as a replay of the first, preserving its stale `alertedTier`/tier claim exactly like the bug the check exists to prevent. `SetClock`/`GetClock`/`tierClaimKey` all use `UnixNano`/`time.Unix(0, v)` consistently now. See `TestStore_SetClock_DistinguishesIncarnationsWithinTheSameSecond`.
- **`engine.go`** — the four triggers, then the ticker:
  - **`RegisterClocks(ctx, caseID, priority, createdAt, caseNumber, wso2CaseID, caseTitle, caseType, product, team)`** (called from `dispatch.handleCaseCreated`) looks up `priority` in the duration-policy map, and for each clock type the policy actually has an entry for at that severity (LOW/S4 has `response` only — see migration `0192`'s own seed data; nothing is registered for a type the policy has no row for) computes `dueAt = createdAt.Add(duration)`, applies `avoidWeekend` (rolls a Saturday/Sunday due date to the next Monday) only for `resolution` at `MEDIUM`/S3 — the one duration published as "1 Business Week" rather than a flat interval — writes the clock's metadata hash, and schedules its three (50/75/100%) wake entries via `tierTime(createdAt, actualDuration, tier)`. Both `avoidWeekend`/`tierTime` are ported verbatim from the pre-poll design.
  - **`ApplyStateEffects(ctx, caseID, newStatus)`** (called from `dispatch.handleStatusChanged`, unconditionally — every effect here is idempotent, so a resent status change is harmless) matches `newStatus` case-insensitively against entity-service's own human display labels (`"Awaiting Info"`/`"Solution Proposed"` → pause `workaround`+`resolution`; `"Closed"` → force-complete **both** `resolution` and `response` (`AdvanceAlertedTier` to 100, the latter via `CompleteResponseClock` itself) and pause `workaround`; anything else → resume both) and refreshes all three clocks' own `state` field for the next breach card, regardless of which branch fires. **Response used to be left completely untouched on close** ("it's only ever completed by `CompleteResponseClock`, on a qualifying comment") — reported live: a case that closes with no qualifying support-engineer reply ever recorded (a work note doesn't qualify, and neither does a comment whose author didn't resolve as a recognized CS-engineer role) left the response clock neither paused nor completed, so its Redis wake entries stayed live and a breach alert fired into Chat well after the case had already closed. Workaround is only ever *paused* here on close, never completed by this function — see `CompleteWorkaroundClock` just below for the one real completion trigger (a real "workaround provided" signal now exists, `case.workaround_provided`) — but pausing alone remains safe on its own terms regardless: `processDueMember` drops a *paused* clock's due wake entry without alerting regardless of tier, so pausing suppresses alerts exactly as completing would — confirmed directly, not just read off the code: disabling only the response fix and closing a case left every fired alert tagged `clockType=response`, none for `workaround`/`resolution`.
  - **`CompleteResponseClock(ctx, caseID)`** (called from `dispatch.handleCommentAdded`, only when `events.CommentAddedPayload.IsSupportEngineerResponse` is true) force-completes the response clock the same way — `AdvanceAlertedTier` to 100, idempotent under a redelivered comment-added event.
  - **`CompleteWorkaroundClock(ctx, caseID) error`** (called from `dispatch.handleWorkaroundProvided`, the consumer of entity-service's new `case.workaround_provided` event) force-completes the workaround clock the same way. Reported live, a real gap this closes: entity-service's own Postgres-side `SLAEngineService` already had a `CompleteWorkaroundClock` of its own, called whenever a case PATCH sets `workaroundProvided:true` — but that's a different tracker in a different process (see that repo's own `CLAUDE.md`, "CSM-native SLA clock engine"), and nothing published this fact to Kafka at all before `case.workaround_provided` existed, so this engine's own workaround clock could still fire a breach alert well after a workaround had genuinely been provided. `false` (a recall) is deliberately never published by entity-service either — same "no uncomplete operation" posture its own `CompleteWorkaroundClock` already has — so there's no equivalent "un-complete" case here. No `Recipients`, no Chat alert on the *event* itself (`events.WorkaroundProvidedPayload` carries only the case id) — this is a pure tracking signal, consumed exactly once by this one call. **Unlike every other trigger here, this one is NOT best-effort** (a CodeRabbit-caught gap): `RegisterClocks`/`ApplyStateEffects`/`CompleteResponseClock` all react to events whose effect either repeats (a resent status change) or gets re-established later in the same case's lifecycle, and `Reconcile`'s own startup sweep can rebuild a clock's state from entity-service's durable row regardless — but a workaround-provided signal lost to a transient Redis failure has no such second chance, since nothing else ever calls this again for the same PATCH. So its store error is returned (wrapped) all the way up through `handleWorkaroundProvided` and `Handle`, failing the record so `eventbus.Consumer` retries it instead of silently acknowledging a clock that was never actually completed — `slaEngineService`'s own doc comment spells out why this one signature differs from its three siblings.
  - **`Reconcile(ctx, client)`** — the one thing this design still lacked relative to every earlier one: Redis itself has no durability, and before this there was no way to recover any of it if the instance was ever flushed or replaced — every in-flight clock's pause flag, alerted-tier cursor and display metadata would simply be gone, silently, with no error anywhere. Called once, at `cmd/server/main.go` startup, right after the engine is constructed and *before* `RunTicker`/any consumer starts: pages through `EntityClient.GetActiveCSMSLAClocks` (`GET /sla-status?source=csm` — entity-service's own CSM-native engine already writes this same durable record synchronously on every lifecycle event; see that repo's own `CLAUDE.md`, "CSM-native SLA clock engine") and rebuilds each clock's Redis state via `reconcileClock`, the same due-date math `RegisterClocks` uses (`tierTime`/`avoidWeekend`), anchored on that row's own `startOn`. The one thing it does differently from a fresh `RegisterClocks` call: a tier whose due time has already passed is pre-claimed via `AdvanceAlertedTier` (never moves the cursor backward, so this can't un-complete anything Redis already has right) **instead of** getting a wake entry — scheduling one for an already-overdue tier would have the very next `Tick` immediately alert on stale history, flooding Chat with breach alerts for tiers almost certainly already alerted on before whatever wiped Redis. Only a genuinely still-future tier gets a real wake entry, so normal ticking resumes seamlessly. The durable row's own paused flag is always applied as-is (`setPaused(ctx, ..., c.IsPaused)`, not only when `true`) — a CodeRabbit-caught bug in an earlier version only ever set `paused=true` and never cleared it back to `false`, which would have left a clock Redis thought was paused stuck that way forever once reconciled, even after the real row resumed. Not gated on "only run if Redis looks empty" — every write here is already idempotent, so running it against an already-correct Redis is a safe, cheap no-op in effect. A fetch failure is logged, not fatal (`main.go` just starts the ticker with whatever Redis already has); a single clock's write failure is logged and reconciliation continues with the rest. As a side effect (not its purpose), this also closes `RegisterClocks`' own "no backfill" gap below for any case whose entity-service row predates this engine's Redis ever seeing it.
  - **`Tick`/`RunTicker`** scan `sla:wake` for everything due at or before now and process each (`processDueMember`): remove the wake entry and drop it if the clock is unregistered or already covered by `alertedTier`; otherwise claim the tier (`ClaimTier`), and on a win, `alertTier` — publish `events.TypeSLATierReached`, then `sendBreachAlert`. A Kafka publish failure is a real, retried error (the claim is released, the wake entry stays for the next tick); a Chat-send failure is logged only and never retried — same explicit, carried-forward product decision the poll-engine made, for the same reason: retrying would mean re-claiming the tier, and one persistently broken Chat space would otherwise turn into an unbounded stream of duplicate alerts to every *other*, perfectly healthy space, repeating every tick forever.
  - **A `Paused` clock's due member is left in the wake index, not removed** — this replaces an earlier, carried-forward design flaw (every prior engine this one succeeded had it too) where a tier due while paused was dropped outright, permanently losing that tier's alert even once the clock resumed. Leaving it is cheap (one `GetClock` round trip per tick until resumed) and is exactly what `Engine.setPaused`'s resume-time wake shift (below) needs to act on.
  - **Pause/resume duration is entity-service's, not Redis's, source of truth — this engine keeps no pause-start timestamp of its own.** `ClockMeta.Paused` is still just a boolean flag in the Redis clock hash; entity-service's own CSM-native engine (`SLAEngineRepository.SetPaused`) is what now actually accumulates the real elapsed pause time into its `sla` table's `pause_duration` column, synchronously, during the very same request that publishes the `case.status_changed` event this engine reacts to (see that repo's own CLAUDE.md, "CSM-native SLA clock engine") — so by the time this Kafka consumer processes a resume, entity-service's own row already reflects the just-completed segment. `Engine.resumeShift` (called from `ApplyStateEffects`'s resume branch, right after `setPaused(..., false)`) reads that fresh total via `EntityClient.GetClockState` (now also returning `PausedOn`/`PauseDurationSeconds`) and diffs it against `ClockMeta.ShiftedPauseSeconds` — the cumulative amount this clock's own wake schedule has already been shifted by, as of the last resume or reconciliation — to get exactly the newly-completed segment's length. `Store.ShiftWake` then `ZINCRBY`s every one of the clock's tier members **still present** in `sla:wake` forward by that delta (a Lua script checks `ZSCORE` first, since a bare `ZINCRBY` on an absent member would wrongly *create* it, resurrecting a tier `processDueMember` already alerted on and removed), and `Store.SetShiftedPauseSeconds` records the new baseline. A clock paused and resumed several times is shifted only by each new increment, never the whole running total again. `e.entity == nil` (every existing test's own bare `Engine{}`) or a failed/empty lookup both skip the shift and log — fails safe (no shift, same as before this feature existed) rather than risk an incorrect one.
  - **`Engine.Reconcile`/`reconcileClock` are also pause-aware now**, closing the "if Redis goes down, recompute everything from entity-service" half of the same feature: `activeSLAClock` (the `GET /sla-status?source=csm` response shape) carries the same `PausedOn`/`PauseDurationSeconds` fields, and `reconcileClock` folds the clock's total pause time — every already-completed segment (`PauseDurationSeconds`) plus, if the clock is *still* paused at the exact moment reconciliation runs, the open segment since `PausedOn` — into each tier's own due-time calculation before deciding whether to schedule a real wake entry or pre-claim it as already past. The shifted-pause baseline this writes is the **completed** total only, never the still-open segment (which has no durable total of its own until the clock actually resumes) — recording it early would make the real, eventual resume compute a short, wrong delta. This is also what makes "breach messages are sent off Redis and entity-service together" true end to end: Redis still drives the tick/alert loop exactly as before, but every due-date it works from — freshly registered, resumed, or rebuilt from a Redis wipe — is now anchored on entity-service's own durable pause bookkeeping, not a value this engine invents or loses on restart.
  - **Deliberately not done: no durable record of which 50/75/100% tiers have already been alerted on.** `AlertedTier` stays exactly what it always was — a plain cursor in the Redis clock hash, nothing in entity-service's `sla` table tracks it. The pause-duration fix above only needed somewhere durable for *pause timing*, not for *alert history*: a Redis wipe re-derives which tiers are already past (and pre-claims them via `AdvanceAlertedTier`, never re-alerting) from the clock's own due-date math, exactly as `Reconcile` already did before this change — there was no gap here to close, and adding one would be unrequested persistence for state this engine's own startup reconciliation already recomputes correctly from first principles.
  - `sendBreachAlert` builds the Chat card straight from the clock's own stored metadata and posts once per resolved Chat **audience** — see `internal/chataudience` below. **Known, accepted reduction from the poll-engine's own version**: `isEvaluationAccount`/`onboardingStatus` are always `false`/`""` here (no event this engine consumes carries them any more — `case.created`'s own copies of those two fields are themselves long-deprecated and unused, see `events.CaseCreatedPayload`'s own doc comment), and `teamLeadName` is always `""` (no event carries that either, and there is no live lookup left to resolve it from). Both are purely routing/display niceties that degrade gracefully to `chataudience.Resolve`'s own team-then-"Incident Monitor" fallback and a bare team name on the card — not a crash, not silently wrong data, just less routing/display richness than a live bulk lookup could offer.
  - **`sendBreachAlert` now re-verifies the clock against entity-service, right before building or sending anything** (`entityClockStatusClient.GetClockState`, `e.entity`) — a real, reproduced incident, not a hypothetical: `ApplyStateEffects`'/`CompleteResponseClock`'s own `AdvanceAlertedTier` write (see those methods' own bullets above) is a separate, non-atomic Redis write from whatever Kafka event triggered it, and can be silently lost with no retry, same as any other best-effort trigger here — leaving a wake entry scheduled at `RegisterClocks` time to fire a false breach alert for a clock that had, in truth, already completed cleanly (closed with a qualifying reply, or sooner). `e.entity.GetClockState(ctx, caseID, clockType)` calls entity-service's own `GET /sla-status/clock-state?workItemId=<caseId>&target=<clockType>&source=csm` (see that repo's own `CLAUDE.md`, "SLA status") and returns that clock's full, current `clockState{Found, IsActive, Stage, HasBreached, StartedOn}`. The alert is suppressed — logged and dropped with **no Chat send** — only when ALL of: the lookup succeeded; `Found` is true (entity-service's own CSM registration is itself best-effort, on a different trigger than this engine's Redis registration, so "no row" is unconfirmed, not evidence of resolution); `StartedOn` is within `clockIncarnationTolerance` (5 minutes) of this wake entry's own `meta.StartedAt` (`isSameClockIncarnation`) — a severity revision cancels the old clock and registers a fresh one for the same `(case, clockType)` pair, and that NEW incarnation being active must not be read as confirming the OLD, Redis-tracked one (the one this wake entry is actually about) is resolved; `Stage` is genuinely terminal (`isTerminalSLAStage`: `ACHIEVED`/`CANCELLED`/`COMPLETED`, deliberately not `BREACHED` — mirrors entity-service's own `slaEngineOpenStageFilter`); and `!HasBreached` — a clock that genuinely DID breach before it was later completed is a real violation worth reporting, not the false-alarm case this feature exists to catch. Every one of those five conditions is a fix for a specific gap a CodeRabbit review caught in the first, simpler version of this check (a bare "is any row of this clock type still active" boolean) — see `GetClockState`'s own doc comment in `client.go` for the two structural gaps (unconfirmed absence, incarnation confusion) that version had. The `sla.tier_reached` Kafka publish and every bit of `processDueMember`'s own bookkeeping (the tier claim, `AdvanceAlertedTier`, `RemoveWake`) still run exactly as if a real alert had gone out when suppressed — the point is to stop a known-stale signal from reaching a human, not to pretend the tier was never crossed, and marking it done here is what stops the SAME stale clock from being re-checked (and re-suppressed) on its next tier too. **Fails open on anything inconclusive**: a lookup error, no row found, or a mismatched incarnation all log and send anyway, since silently losing a genuine breach alert over an inconclusive double-check is worse than the occasional false positive this whole feature exists to reduce; `e.entity` is nil for any caller that hasn't wired one up (every pre-existing test), which fails open the same way and leaves this function's behavior completely unchanged for them. One check, inside the one function every clock type's alert already funnels through — `response`/`workaround`/`resolution` are all covered by this single call site, not three separate ones.
- **The poll-engine's own SLA breach-alert EMAIL reaction (`sendBreachEmails`) is gone, not ported — a deliberate scope decision, not an oversight.** That feature needed `AssigneeEmail`/`TeamEmail`/`AssigneeName`, all resolved from entity-service's own live, bulk `/sla-status` join — none of which exist on any event this engine now consumes (`case.created`/`case.status_changed`/`case.comment_added`), and adding them would mean a further entity-service payload change, out of scope for this pass. The Chat alert (this service's primary alerting channel for every other event type too — `case.created`/`case.acknowledged`/`case.severity_changed`/frustration-detection all alert via Chat, with email as at most a secondary channel for ordinary `case.*` notifications, never for SLA breaches before this gap) is unaffected. Revisit by extending `case.created`'s payload with these fields if email parity is ever wanted back. `internal/notifications/sla_breach_email.go` and its two templates (`templates/sla_breach_assignee.html`/`sla_breach_team.html`) had no caller left once this feature was removed and were deleted outright, not left dangling.
- **`SLA_EMAIL_SENDING_ENABLED` (default `true`) gates ALL SLA-related notifications: the SLA breach Google Chat card and any SLA email.** Same disable-entirely convention as `EMAIL_SENDING_ENABLED`/`CALL_SENDING_ENABLED` (`cmd/server/main.go`; only the literal `"false"` disables). The name is kept for config compatibility. Threaded to `slaengine.Engine` as `slaEmailSendingEnabled`; checked at the top of `sendBreachAlert`, the only SLA-triggered Chat send in the service (`sla.tier_reached` has a no-op dispatch case, and the paging engine is driven by case events, not SLA events). When `false`, only the send is skipped (logged at info): `processDueMember` has already claimed the tier and published `sla.tier_reached`, and still advances the alerted-tier cursor and removes the wake entry, so a tier crossed while disabled counts as alerted and re-enabling does not flood Chat with stale cards. Non-SLA Chat alerts (frustration, `sr.*`, outage, incident) are unaffected. There is no SLA breach email today.
- **`internal/chataudience`** (`resolve.go`) — unchanged: `Resolve(team, isEvaluationAccount, onboardingStatus, now, hasAudience) []string` decides which Chat audience(s) an alert should post to, shared by `slaengine.Engine.sendBreachAlert` and `dispatch.checkFrustration`.
- **`googlechat_sla.go`** — `GoogleChatClient.SendSLABreachAlert`'s call signature is unchanged by this redesign (`teamLeadName` is simply always passed `""` now — see `sendBreachAlert`'s own doc comment above).
- **`dispatch.go`'s `Handle` switch still has an explicit no-op case for `events.TypeSLATierReached`** — unchanged: still in `KnownTypes`, still has a `Validate` case, but no reaction of its own; nothing in this service consumes that event.
- **No new consumer group, no new topic — `case.workaround_provided` is the one new Kafka event type this engine's triggers needed, and it rides the existing main consumer like every other `case.*` type.** `RegisterClocks`/`ApplyStateEffects`/`CompleteResponseClock`/`CompleteWorkaroundClock` are all plain function calls from within `Dispatcher`'s own existing/new handlers, on the existing main consumer — only `RunTicker` is a separate goroutine, same as before. The other three triggers piggyback on events entity-service already publishes for its own reasons (`case.created`/`case.status_changed`/`case.comment_added`); workaround had no such event to piggyback on (see `CompleteWorkaroundClock`'s own doc comment above), hence the one new, minimal type.
- **A case created before this engine's first deployment has no registered clock — mostly still true, with one partial mitigation.** `RegisterClocks` only ever runs from `handleCaseCreated` — there is still no dedicated backfill job. `Engine.Reconcile` (above) incidentally closes this for any case entity-service's own CSM-native engine already has a durable `source='CSM'` row for (i.e. any case created after *that* engine started working correctly — see that repo's own `CLAUDE.md` on the policy-resolution bug it had until recently), since reconciliation rebuilds from the exact same record a dedicated backfill script would read from. A case from before entity-service's own engine existed, or one whose severity never resolved a policy, still has nothing to reconcile from.
- **`internal/timecardengine`/`events.TypeCaseBillableStatusChanged` no longer exist, on either side.** This used to be a dedicated consumer group here reacting to a case's severity crossing the LOW/S4 boundary (bulk-flipping every time card's `isBillable` for the case), with entity-service's own `Publish` call for it left commented out pending a Postgres `time_cards` table there. By the time that table existed (`time_card`/`time_card_approver`, already fully wired up — see entity-service's own CLAUDE.md), it became clear the event hop itself was never justified: entity-service already owns this data directly (a single `UPDATE time_card SET is_billable = ... WHERE case_id = ...`), so the reaction now happens there, synchronously, in-process — no Kafka round trip, no separate consumer group, no cross-service failure mode for what both ends recognized was never actually a notification to an external system. Removed entirely rather than left wired-but-dormant.

## Cases and incidents are different entities

A **case** is entity-service's `POST /cases` and `domain.CaseView`, carried by
the `case.*` events. An **incident** is `POST /incidents` and
`domain.IncidentView`, carried by the `incident.*` events. Both families exist
here and they are not interchangeable: `case.comment_added` and
`incident.comment_added` are different payloads about different entities.
`dispatch` reacts to the case events; `internal/paging` reacts to both: CRE
paging starts from customer cases, SRE paging from SRE incidents and from a
case at S0 (see "Case Paging from customer cases" below).

**"SRE incident" is not a third thing.** `integrations/sre-alert-ingestion-service`
turns a vendor alert (Azure, Grafana, Site24x7, OpenSearch) into a platform
incident through that same `POST /incidents`, so an alert-born incident is
exactly what the `incident.*` events describe, and the call-escalation ladder
below escalates it like any other. There is no separate SRE entity.

## Incident call escalation

The ladder lives in `internal/paging`, not `internal/escalation`: that
package is the customer-frustration detector's client (next section), and
"escalation" is the customer-initiated feature's word. The two share no
code, types or configuration.

`internal/paging` runs the incident call-escalation ladder from the
"Synchronizing Twilio Alerts for New Incoming Incidents Based on ABT Model"
specification: an unattended incident climbs five rungs (LEVEL_0 rotation
lead/members — rotations only — then ABT leads, ABT team leads, Head of BU,
Head of CRE), each rung placing several calls spaced apart before escalating,
on a clock set entirely by the incident's priority (section 7.0's table, in
`policy.go`'s `DefaultPolicy`, verbatim — with two documented divergences
where the document's own rows don't sum to its stated totals; the formula
wins and tests pin both). Like `internal/slaengine`, it is its own consumer
group on the shared topic (`INCIDENT_ESCALATION_CONSUMER_GROUP`) plus a
ticker, with Redis as its only durable state — the same `REDIS_URL`/
`REDIS_ADDR` client, its own keys. Structure:

- **`policy.go` / `plan.go` — pure.** `Lookup` resolves a priority (P-notation
  or a label: both the case-severity vocabulary and ServiceNow's incident
  priority enum, whose `MODERATE` is the spelling `MEDIUM` — `PLANNING` is
  deliberately absent, section 7.0 has no row below P4). `BuildPlan` expands a
  `Trigger` into every `PlannedCall`, resolving recipients **once per rung**
  (a live roster could otherwise answer two attempts of one rung
  differently). `ExecutionSummary`/`WorkNote` render section 11.0's work note
  from the engine's *placed flags*, not from scheduled times — a cancellation
  and a call due at the same instant race, the cancellation wins, and
  reporting by time alone claimed calls that never happened.
- **`resolver.go` — the seam.** `RoutingContext.HasNotificationLevel` decides
  whether LEVEL_0 exists: rotation shifts only, **and on USA_WEEKEND only when
  not ABT-eligible** (rule R10 has no notification level, R12/R14 do — the one
  input that changes the ladder's shape rather than who answers).
  `ABTEligible` is a `*bool` in both the payload and the routing context,
  because there are three states: eligibility splits the rule table in half,
  so "nobody told us" is genuinely different from "told no" — and it is the
  common case, since no publisher sets it. Unknown reports the rule as
  `UNKNOWN_ABT` rather than a confident wrong row, and keeps LEVEL_0 on a
  USA_WEEKEND rotation (waking one extra person is the recoverable error;
  dropping the fastest rung on a weekend night is not).
  `RoutingContext.Rule` names which of section 5.0's fourteen rows an incident
  routes by; nothing branches on it, it exists so the path is *reportable* —
  it's in the schedule log line, every placed call, both endings, and the work
  note. `Resolver` is the interface the rule table's data plugs into.
  **`RosterResolver` is a stopgap**: the specification resolves recipients
  from ServiceNow (`sys_user_group_type`, `u_team_member_role`, the On-Call
  Scheduling module), none of which is reachable here, so an operator roster
  (`INCIDENT_ESCALATION_ROSTER`, JSON) implements the table's specificity
  order — team, then shift pool, then default — against hand-maintained data.
  Section 8.0's LEVEL_0 availability filtering is not implemented (no
  schedule to read). `StaticResolver` is for tests.
- **`shift.go`.** `ShiftAt` derives the effective shift from the trigger
  time in IST (section 6.0's boundaries); the night shift straddles midnight,
  so pre-06:00 hours belong to the shift-day that opened the night before.
  This assumes ServiceNow's `openedOn`/`createdOn` are UTC — the whole repo's
  existing `parseSNDateTime` assumption, but a 5.5-hour error here puts an
  incident in the wrong shift entirely, so confirm it against a real record.
- **`engine.go` / `store.go` — the two halves.** `Handle` reacts to four
  events: `incident.created` claims the incident **create-if-absent** (a
  redelivered trigger must not restart a ladder from LEVEL_0);
  `incident.priority_elevated` deliberately **replaces** a running ladder,
  retiring its outstanding calls; `incident.acknowledged` (leaving NEW) and a
  public `incident.comment_added` are the two halves of an acknowledgement and
  **both are required**: each is recorded on the ladder's own state as it
  arrives, in either order, and the ladder keeps climbing until the second one
  does. A status move on its own is what a dispatcher does while triaging a
  queue, and treating it as an answer silenced the pager for incidents nobody
  had picked up. `acknowledgement.requireBoth: false` restores the old
  either-gesture rule. A work note
  (`isPublic: false`) is ignored. `Tick` (every `INCIDENT_ESCALATION_TICK_INTERVAL`,
  default 5s — finer than the SLA engine's, since P0's calls are a minute
  apart) scans the wake ZSET, and for each due call: **place, then record,
  then drop the wake entry** — a crash between the first two repeats the call
  next tick, which is the direction to fail in for a paging system.
  Before dialling, the replica **claims** the call (`Store.ClaimCall`, a SETNX
  keyed by call and chain, one-minute TTL): two replicas -- a rolling restart
  always has two for a moment -- cannot both dial it, and a replica that dies
  mid-call delays it by at most the TTL instead of losing it. A transient
  failure releases the claim so the next tick retries.
  **A trigger whose last call is already in the past is dropped**: this
  group reads the topic from its first offset the first time it exists, so
  the first deployment replays retention, and without that guard the next
  tick burst-dials every rung of every stale incident. A short backlog still
  catches up correctly (offsets are from the report time on purpose).
- **`client.go`.** A narrow entity-service client whose one job is PATCHing
  the execution summary onto the incident as a work note. **Optional**
  (`CUSTOMER_ENTITY_BASE_URL` unset → summary logged instead), unlike the SLA
  engine's — this engine's job is placing calls; the summary is a record.
  Loop-safe: a work-notes-only PATCH publishes no escalation signal, and
  `incident.comment_added` comes from a different endpoint this never calls.
- **`config.go` — what a deployment may spend.** `INCIDENT_ESCALATION_CONFIG`
  points at a YAML file governing **both** ladders (`cre:`/`sre:` sections):
  an `enabled` master switch, a per-ladder `channel`, `trigger` conditions
  (`priorities`/`teams`/`excludeTeams`/`shifts`/`requireKnownTeam`) deciding
  which incidents get a ladder at all, and `safety` caps
  (`maxCallsPerLadder`/`maxLevel`/`allowedNumbers`) capping what one ladder may
  spend. It is a file rather than more environment variables because every
  knob in it changes how many calls get placed, and therefore the bill — and
  because the answer to "what will this deployment dial" should be one
  readable thing, not eight variables assembled by hand from a container spec.
  Rules worth keeping: an **unreadable or invalid file disables both ladders**
  and logs it, never a silent fall back to defaults nobody chose; an
  **unknown key is an error** (`KnownFields(true)`), because a misspelled
  `maxCallsPerLadder` that is quietly dropped leaves an operator certain they
  have capped the spend when they have not; `safety.maxLevel` is a **`*int`**
  so absent and `0` are different — LEVEL_0 is a legitimate cap and the zero
  value of the struct (what a deployment with no file, and every hand-built
  `EngineConfig` in tests, gets) must mean *no* cap, not "truncate every ladder
  to one rung". With **no `INCIDENT_ESCALATION_CONFIG` set at all** the service
  behaves exactly as it did before the file existed, so adopting it is opt-in;
  `INCIDENT_ESCALATION_ENABLED` overrides the file's master switch in both
  directions, so a ladder can be stopped without editing and shipping a file
  mid-incident. `Engine.applySafety` trims a freshly built plan to the caps
  **before it is stored**, recording a `PlanIssue` (`LEVEL_CAPPED`,
  `NUMBER_NOT_ALLOWED`, `CALL_CAP_REACHED`) for each, so a ladder reaching
  fewer people than the rules say lands on the work note rather than being a
  quiet saving.
- **`case_alert_settings.go`, `case_alert_values.go` + `cmd/server/case_alert_settings.go`
  — settings saved on the Team Schedule.** `PAGING_CONFIG_SOURCE` (an env var, not a
  file key: the file is decoded strictly, so a new key would turn paging off on
  older builds) is `db` when unset: everything saved, for CRE, SRE and SME
  (rooms, routes, ladder values; SME values via `smeCaseAlertKeys`), each key
  in place of the file's; nothing saved is the file. A saved SME room replaces
  or adds that team's `sme.teamChats` entry; an SME team with no room of its own
  uses `sme.chat` (`smeNotifiersFor`), never no card. `off` never asks
  entity-service.
  `shadow` reads `GET /team-schedule/case-alerts/settings/runtime` once at start,
  logs what `MergeCaseAlertSettings` would change, and runs on the file; `db`
  runs on the merge. The merge only replaces what was saved -- a ladder's shared
  room, an SRE team's room (and its teamless flag), an alias or a default group
  -- and puts each saved URL in a `CASE_ALERTS_ROOM_*` variable so the engine
  reads it like any webhook (`Chat.WebhookURLEnv`) and nothing in it changes.
  The result must pass `Config.validate`; entity-service down, a refused merge
  or a failed setenv all keep the file, never `DefaultConfig`. Group names are
  matched case-insensitively, as the resolver does. The equivalence test
  (`SavedLikeTheFileChangesNothing`) pins that settings saved to match the file
  page exactly as the file does.
  **Ladder values** (`case_alert_values.go`) are the rest of `cre:`/`sre:`:
  one key each (`teams.abts`, `heads.cre`, `trigger.priorities`,
  `timing.interval`, ...), in the file's shape, applied before rooms and routes
  by a setter per key in `caseAlertKeys` (which must match entity-service's
  `caseAlertValueSpecs`; `TestCaseAlertKeysMatchTheTab` lists them). An unknown
  key or one for the other ladder is skipped and logged; a value in the wrong
  shape refuses the merge. Each ladder's own switches are keys too:
  `enabled`, `channel` (CRE, SRE, SME), `safety.maxCallsPerLadder`,
  `safety.callWithoutVerifiedLeads` and `safety.callHeadsWithoutLowerTiers`
  (CRE, SRE), so a ladder can be turned on, put on chat only or have its
  holds changed from the tab (a file with no `sme:` section still gets the SME
  page from a saved `enabled`). The file's top-level `enabled`, the
  `INCIDENT_ESCALATION_ENABLED` kill switch, `safety.maxLevel`,
  `safety.allowedNumbers`, `phones`, `testCall` and `rules` are not keys: they
  stay in the file. The applied report also carries `channels`
  (`EffectiveChannels`): per ladder whether it runs, its channel, and each SRE
  and SME team's channel in use (the ladder's narrowed by the team's own) and
  whether it has a room. Saved values still apply only at start-up.
  It also carries `groups` (`CaseAlertGroupRouting`): per ladder the
  assignment-group aliases (lower-cased group to team key), and for SRE the
  default groups and the teams with a room but no rota, so the tab can say
  where each group goes and stop warning about groups the file routes.
  The applied report carries `running` (`RunningCaseAlertValues`): every
  ladder value the process runs with and whether it came from the file or the
  tab -- in shadow the file's, so the tab can copy them. Heads go with a name
  and email, never a phone. It also carries `fileOnly`: what only the file
  sets (on/off, channel, safety caps, phones.source, `ackChat`), shown read-only on the
  tab; allowed numbers are counted, never listed. CRE's also carries the rung emails
  (`email.enabled`, `email.teamLists` counted, `email.creTeamList`/`email.csTeamList`
  as set or not, never an address; the tab hides that row now that the four are
  tab values, which `running` reports with their addresses, like a head's), `rules.custom` and `timing` (`creChainTiming`:
  severity to the minutes each step L0-L4 is called, from `DefaultPolicy`, so the
  tab cannot drift from the code), so every CRE setting shows on the tab. `SmallFilePlusSavedIsTheFullFile` pins that
  `paging-alert.minimal.yaml` plus everything copied from the full file pages
  exactly as the full file.
  **Team channels** (`team_channel.go`): a saved SRE team row may carry a
  channel; it becomes `LadderConfig.TeamChannels` (`yaml:"-"`, never from the
  file). `channelFor` reads the incident's own SRE team (through aliases) and
  `narrowChannel` keeps only what both the team and the ladder's file channel
  allow -- a team can drop calls, drop chat or go to log, never add a channel.
  It is used where the plan is built, in `applySafety` and in `place`
  (`withChannel` filters the notifiers). An incident with no SRE team of its
  own uses the ladder's channel.
  A **db start** retries entity-service for `PAGING_CONFIG_WAIT` (default 2m;
  network errors, 5xx and 429 only), then falls back to the last settings a db
  start loaded, kept in Redis under `incident:escalation:case-alerts:last-loaded`
  without webhook URLs (so rooms come from the file), and only then to the
  file. A fallback start does not report.
- **`notifier.go` - which channel a rung reaches people on.** The ladder's
  timing, routing and cancellation are channel-agnostic; only the last hop
  differs. `INCIDENT_ESCALATION_CHANNEL` picks `call` (the specification's
  own, and the default), `chat` (a card in the incident's Google Chat space
  via `SendEscalationAlert`), `both`, or **`log`** — which runs the entire
  ladder and writes a line per rung naming who it *would* have reached,
  reaching nobody. `log` exists because the two channels that reach people
  both need an account: calls cost money per rung, chat needs a webhook for a
  room real colleagues sit in, and neither is something to point at a test.
  It is a channel rather than a global dry-run flag so it appears where every
  other delivery decision does, and it is **exclusive** — `Channel.Uses`
  reports false for `log` against `both`, so a log ladder wires that notifier
  and nothing else; a live ladder that also emitted "would notify" lines would
  read like a dry run mid-page. It logs the recipient's `recipientId`
  (`Recipient.LogID`), never a name, address or number. **A chat card does not wake anyone**
  - the initial Chat alert already exists and the ladder exists because it
  was not enough overnight - so `chat` alone is a real reduction in what the
  feature does. Where it earns its place is alongside the calls, giving the
  room sight of an escalation climbing, and as the only channel exercisable
  end to end without a telephony account. Chat posts **once per rung**, not
  per attempt: a rung's repeats exist because a phone went unanswered, a
  question a posted card cannot ask, and a P1 ladder's fourteen attempts
  would bury the room. With `both`, each channel is attempted even if the
  other fails.
- **`internal/notifications/ssml.go`.** `MakeSSMLCall` speaks a typed
  `Speech` tree as real nested SSML inside `<Say>`. It exists because
  `MakeCall`'s chardata escaping — correct, and what stops TwiML injection —
  read an SSML *string*'s tags aloud. The tree keeps both properties: markup
  on the wire, text that can never become markup (caller text only ever
  reaches the document through `xml.CharData`). Opt-in via
  `INCIDENT_ESCALATION_SSML=true`. No `<speak>` root: in TwiML, `<Say>` is
  the root.

### The SRE ladder (`sre.go`, `teamschedule_sre.go`)

There are two ladders, and **one engine per ladder**: `cmd/server/main.go`
starts a CRE engine and an SRE engine (`EngineConfig.Kind`), each with its own
channel, its own consumer group (`INCIDENT_ESCALATION_CONSUMER_GROUP`,
`INCIDENT_ESCALATION_SRE_CONSUMER_GROUP`) and its own Redis namespace
(`Store.ForLadder` -- the CRE ladder keeps the original keys, so ladders stored
before this existed are still found). One engine per ladder because **a P0 CRE
incident climbs both at once**: sharing one namespace would make the second
SETNX look like a redelivery, and sharing one wake index would let each tick
place the other ladder's calls over its own channel.

**Which ladders a record climbs is code, not configuration**: `DefaultRouting`
in `routing.go`. It used to be the file's `routing:` section; on 2026-10-07 it
was taken out of the file on purpose -- these rules are the Case Paging design,
and changing them should be a reviewed code change, not a file edit on a running
deployment. A file that still has a `routing:` section is refused (unknown key).
`EngineConfig.Routing` remains for tests only. `Engine.claims` matches the
record kind (`case`/`incident`), the team family (`sre` / `cre` / `none`, from
`TeamScheduleResolver.TeamFamily`), `contactType` and priority against the
rules, and an engine claims the record when a matching rule names its ladder --
so one record can climb both. A rule with **no** `team` condition takes
team-less records and overrides that ladder's `trigger.requireKnownTeam`
(`excludeTeam` does not count as a team condition). The rules:

    cre-case      record [case]                                        -> cre
    cre-p0        record [case], priority [S0]                         -> sre   (S1 Critical: CRE only)
    sre-abt-team  record [incident], team [sre]                        -> sre   (sheet "Yes" rows)
    monitoring    record [incident], contactType [AZURE, SITE_247,
                  SENTINEL], excludeTeam [cre]                         -> sre   (sheet "No" rows)

An incident on a CRE team matches nothing: CRE work arrives as a case. The
ladder-mechanics tests drive the CRE ladder with incidents through an explicit
`incidentRouting` (engine_test.go), not the default.

`contactType` comes from entity-service's `incident.created`
(`IncidentCreatedPayload.ContactType`, the incident view's label, falling back
to the create request's); it is compared ignoring punctuation, so `SITE_247`
matches the database's `SITE_24_7`. The one rule kept in code is a property of
the SRE ladder, not of routing: its clock ignores priority, so an elevation
starts an SRE ladder only through a rule that conditions on priority.
`crePriorities` (the earlier SRE-only setting) is gone -- an unknown key, so a
file still carrying it fails to load rather than being silently ignored.

An incident is an SRE team's when its assignment group (after
`sre.teams.aliases`) is in `sre.teams.abts`; with no list configured, the Team
Schedule catalogue's team `family` answers.

    LEVEL_0  L1 support   at once
    LEVEL_1  L2 support   +interval (5m)
    LEVEL_2  L3 support   +interval
    LEVEL_3  L4 support   +interval, only with sre.timing.includeL4 (NOT CONFIRMED)

**One call, one person per rung**, the same clock for every priority, and **no
priority gate** -- `PolicyFor` gates only the CRE ladder on priority; an SRE
incident at PLANNING still gets its clock. The clock is `sre.timing`
(`SRETiming.Policy`); without a file, `INCIDENT_ESCALATION_SRE_L4` still turns
L4 on. A rung is whoever holds that **tier** on an SRE window at the instant
**that rung opens** (on-duty `tier`, else the window's own) -- not the report
instant: a ladder reported at 13:25 opens L2 at 13:30, inside TZ2, and asked
at 13:25 it called TZ1's L2 after they had gone home, or nobody when TZ1 had
no holder for the tier. `BuildPlan` sets `RoutingContext.At` to the rung's
opening time for the SRE ladder only; the CRE ladder keeps the report instant,
its rungs being fixed by the shift the incident arrived in. **An SRE team's
incident reaches only its own team** (`tierPicks`): by day another team's
holder never answers, so an Apollo L1 on leave or off the rota leaves the L1
rung empty and the ladder goes on to Apollo's L2 (it used to borrow Artemis's
L1). The exception is the shared night crew, `sharedCrewZone` (TZ3, 21:00-06:00
IST, weekends included), whose holders answer either SaaS team. **When nobody
holds L1, L2 or L3, the L3 rung calls the team lead** (one of them), at the L3
slot; an incident with no SRE team of its own (a default group, a CRE P0 with
no SRE team) calls one lead of every team on its rota instead (both SaaS
teams). A missing tier with somebody on another one is just an empty rung. An
incident with no SRE team of its own still takes whoever holds the tier.
Picked in this order: on-leave holders only when nobody else in the team holds
the tier; then the zone whose L1 block is live -- weekdays
12:00-15:00 IST the TZ1 and TZ2 escalation windows are both live, and the SRE
team confirmed only one person is called; then `sre.teams.abts` order; then
email. The rota has no L4 tier, so L4 is the lead of the answering team -- the
incident's own, or for an incident with no SRE team of its own (a CRE P0) the
team of the first tier somebody holds, L1, then L2, then L3 -- and it calls
nobody when the leads were already called on the L3 rung. An assumption.

**"Default" group** (`sre.teams.defaultGroups`, opt-in): an incident whose
assignment group is listed (the alert flow's "Default") is an SRE incident
with no team of its own: it climbs the SRE ladder on `defaultRota`, each rung
reaching whoever holds that tier on the live window, as a team-less monitoring
alert does -- whatever its contact type. A group may not also be in
`teams.abts`.

**An incident's paging follows its card** (no configuration): when the
incident's assignment group has an `INCIDENT_CHAT_SPACES` space (after
`INCIDENT_CHAT_FANOUT`, through the shared `notifications.IncidentGroups` the
dispatcher's card also uses), every rung, the closing message and the
escalated-to-SME message are posted there as short replies in the
"Incident Reported" card's thread (`notifications.IncidentThreadKey`), whatever
`sre.chat`/`sre.teamChats` say (`Engine.incidentRooms`). Chat threads a reply
under a card only through the same webhook, which is why this is the incident
space and not the ladder's own. A customer case, or an incident whose group has
no incident space, keeps the rules below and the full card.

**Each team's own space** (`sre.teamChats`, opt-in): team key -> a `chat`
section. A listed team's rung cards go to its own space; an incident of an
unlisted team, or with none, uses `sre.chat`. `Engine.notifiersFor` picks by
the incident's team through `sre.teams.aliases`. Startup logs the teams that
have a space, and warns (never refuses: that would stop both ladders) about a
key that is not in `sre.teams.abts`, an alias target or `defaultGroups`
(`unknownSRETeamChats`; skipped when `abts` is empty). SaaS Apollo, SaaS
Artemis and IaaS each in their own space, through `NewEngine` and the webhook
variables: `team_chat_spaces_test.go` (SME teams too).

**An incident with no SRE team of its own** (`sre.teamlessChats`, opt-in):
a default group (a service mapped to no SRE team), a customer case at S0 whose account has no known SRE team, a
monitoring alert with no team. `teamlessChats: [apollo, artemis]` posts its
cards and closing message to every space named (`Engine.chatTeams`); each
entry must be a `teamChats` key (refused at load otherwise). Empty, such an
incident uses `sre.chat`, as before. An SRE team of its own without a space
stays in `sre.chat`; with `teams.abts` empty any named group counts as an SRE
team. The call (and log) notifiers are always the ladder's own: a team's
space contributes only its Chat notifier, so routing never decides whether a
rung rings. Two or more spaces share that ONE call notifier (the rung rings its
engineer once) and one `fanoutChat`: a failed card is retried to every space
at once, so a space that fails while another took the card counts as
delivered (logged), and only a card no space took is retried. With
`channel: both` the call alone decides whether a rung is retried; a card that
fails transiently after the call went out is retried on its own
(`LadderState.CardPending`), never re-dialling, for up to 15 minutes after the
rung was due (`cardRetryWindow`); a rejected card is logged and dropped. The SME handoff
message still goes by the group it left: a default group is never a SaaS SRE
team, so it is never handed to SME.

**Closing message** (`sre.unansweredChat`, opt-in): when every rung has been
called and nobody acknowledged, `postUnanswered` posts "Unanswered: <chain>
paging ended" with who each rung reached. For an incident whose group has an
`INCIDENT_CHAT_SPACES` space it replies under the "Incident Reported" card, once
per space the card went to (`Engine.incidentRooms`); otherwise it goes to the
team's own space, else `sre.chat` -- whatever `sre.channel` is, so a call-only
ladder still tells the room. Best effort (logged, never retried). An SME ladder has its own,
`sme.unansweredChat`: the SME team's own space (`sme.teamChats`), else
`sme.chat`.

**Escalated-to-SME message** (`sre.smeHandoffChat`, opt-in): when a SaaS SRE
incident's escalation starts an SME page, `postSMEHandoff` posts who escalated
it, SRE paging stopped, and whether the SMEs are being paged. When the group it
left has an `INCIDENT_CHAT_SPACES` space it replies under the incident card, one
message per space the card went to (after `INCIDENT_CHAT_FANOUT`); otherwise one
message to the SRE team space (through `sre.teamChats`, else `sre.chat`). Once
per SME page (the page's dedup), best effort.

**Stopped reply** (`cre.ackChat` / `sre.ackChat`, on unless set false):
when a ladder stops, `postStopped` replies in its thread, in the rooms its
rung cards went to (`Engine.cardRooms`, the same choice `place` makes, so an
incident's replies sit under the incident card): "Acknowledged" with who (a
case's assignee) and how, "Case closed", "Severity changed to S4", or --
when a severity or priority change replaces the chain -- "Severity changed to
X: paging restarts". It lists who was paged and how many calls were
cancelled. Posted only from the first stop (a retried stop finds `Cancelled`
set) and only once a rung has gone out with sending on, so a room never hears
about a chain it did not see; before any rung, a room the incident card
reached (`IncidentCards`, e.g. an SME ladder whose L1 was empty) counts as
having seen it. A hand-off to the SMEs posts nothing here; its
own message says it. The SRE setting covers the SME ladders. Best effort.

**Stops on** (an SRE incident): `incident.assigned` (an engineer set as the
assignee, published by entity-service) or `incident.acknowledged` (leaving NEW,
whatever the new state -- confirmed 2026-10-07). A public comment
does **not** stop an SRE ladder -- it may be a third party triaging -- and an
assignee does not stop a CRE one (the engine's `Kind` decides; there is no
per-plan check). An elevation never restarts an SRE team's ladder: its clock
does not depend on priority. The voice message and card say "assign the
incident to yourself", and the rule is reported as `SRE_TIERS`.

**SaaS and IaaS SRE are separate chains.** SRE has three sub-teams, each with
its own L1 -> L2 -> L3: SaaS SRE (apollo, artemis; rota `SRE_SAAS`; zones
TZ1-TZ3), IaaS SRE (`iaas`, type `sre-iaas`, assignment group "SRE IaaS";
rota `SRE_IAAS`; Day/Night zones) and PaaS (none yet). The catalogue carries
`rotaCode` on teams and zones; the engine stamps the incident's rota on the
routing context (`RoutingContext.Rota`, from `TeamScheduleResolver.SRERota`):
its own SRE team's rota, or `sre.teams.defaultRota` (default `SRE_SAAS`) for an
incident with no SRE team (a case S0 whose account has none, a team-less monitoring alert). Only SRE
windows whose zone is on that rota are read, so a SaaS incident never reaches
an IaaS engineer or the other way round. A catalogue with no rota codes at all
(an entity-service from before rotas) reads every SRE window, as before. The
card's rung, the voice message and the work note name the chain ("SaaS SRE",
"IaaS SRE"); with no rota they read exactly as before.

### The Special Ops (SME) page (`sme.go`)

entity-service publishes `incident.special_ops_alert` on the operations topic
(`sre-events`) whenever an incident's assignment group changes **into** a
Special Ops group, however it changed -- the "Escalate to Special Ops Team"
button today -- and only when it has `SRE_EVENT_HUB_TOPIC` set. Here it arrives
through the dispatcher's sre-events consumer (`HandleShared`), which hands it
to the SRE engine (`Dispatcher.WithSpecialOpsPage` -> `Engine.HandleSpecialOpsAlert`);
the paging engines' own consumers ignore the type, even when
`INCIDENT_EVENT_HUB_TOPIC` is the same topic, so one alert pages once. The
engine is built after the consumers start, so `main.go` calls
`DeferSpecialOpsPage` first and an early alert waits for it. Off unless the
file's `sme.enabled`:

- **Gate**: the group the incident left (`previousAssignmentGroupName`, else
  its id, through `sre.teams.aliases`) must be a SaaS SRE team (`SaaSSRETeam`:
  its rota is `SRE_SAAS`; without rota codes, an SRE team not typed
  `sre-iaas`). IaaS, CRE and unknown groups are logged and ignored.
- The running SRE chain is stopped (`Escalated to SME`, the usual summary).
- The SME team is the payload's `smeTeam`, else `sme.teams[teamKey]`; neither
  is `NO_SME_TEAM` on the work note.
- **The SME ladder** (since 2026-10-09; it was one call before): L1 of the
  SME team's current Day/Night window at once, L2 after `sme.timing.interval`,
  L3 after two (five minutes each by default; `sme.timing` has the shape of
  `sre.timing`, `includeL4` ignored). Each rung asks for its tier at the moment
  it opens (`resolveSME`): the holder of that tier on an SME-family window of
  the team, longest since last called, then email; someone rostered there with
  no tier counts as L1. It runs on the SRE engine's ticker under its own key,
  `smeLadderKey` (`<incidentId>:sme:<team>`), so several SME teams can climb on
  one incident; its work notes and summary still go to the incident. Calls go
  over `sme.channel` (log/chat/call/both, `sme.chat`, `sme.safety.allowedNumbers`)
  -- `Engine.place` picks the SME notifiers for an SME plan -- and the card
  names the rung ("Special Ops L2 on duty").
- **Each team's own Chat space** (`sme.teamChats`, opt-in): SME team key ->
  a `chat` section (`webhookUrlEnv`, `audience`). Only the SME team an
  incident is escalated to is notified. With `audience` alone the space is that
  audience's `GOOGLE_CHAT_SPACES` entry, so the nine teams need no variable of
  their own (the committed example does this; `team_chat_spaces_test.go`
  uncomments it and checks each team gets its own space). Unset, every team's
  cards go to `sme.chat`, as before. Set, a listed team's cards go to its own space and
  a team not listed uses `sme.chat`, never no card (a room saved on the Alert
  Settings tab counts as listed). `Engine.smeNotifiersFor` picks by `Routing.SMETeam`.
- **The "Incident Escalated" card is the escalation's, not L1's** (since
  2026-10-23): `postSMEIncidentCard` posts it to the SME team's spaces when the
  alert is handled, with chat in `sme.channel` and sending on, whoever is on
  call. Nobody rostered on any tier: the card still goes out ("Nobody
  rostered") and no ladder starts. L1 empty: the card goes out at once rather
  than with L2, and names the first rostered tier and when it is called
  ("Nobody rostered before L2", then the L2 and the time). The rooms it reached are saved on the ladder (`IncidentCards`)
  before any rung is scheduled, so the first rung posts only its reply; a room
  the card missed gets it from the first rung, as before. At the start a work note says who
  L1 is, or why nobody can be paged (`NO_RECIPIENTS`, `NO_NUMBER`,
  `NUMBER_NOT_ALLOWED`, `NO_CHANNEL`); a rung with nobody is logged ("SME rung
  cannot be called") and skipped; the usual execution summary is written when
  the ladder finishes or is stopped.
- **Dedup**: a SETNX key per (incident, SME team), 24 h: the same team alerted
  again while open is ignored, another team gets its own ladder. A page that
  reaches nobody is released.
- **Answered by an assignment, compared by time**: `incident.assigned`
  (incident topic, SRE engine) carries `assignedOn` (entity-service stamps it;
  the handling time stands in when absent). It closes the pages raised at or
  before it (`changedOn`) and stops their ladders ("Assignee set"), keeps any
  raised after it, and records the time (`Store.CloseSMEPages`). An alert raised at or before that time pages nobody,
  so it does not matter which topic is read first; the alert reads the time
  again after opening its page, so the two cannot cross. A later escalation
  pages again. `assignedOn` is a new field and this service decodes strictly:
  deploy it before the entity-service that sends it.
- **Needs an assignee**: entity-service refuses a handoff on an unassigned
  incident (409 `incident_handoff_needs_assignee`) and the CSM portal disables
  the button with the reason: the assignee answers for the page.
- **Try it locally**: `scripts/csm-compose/sre-e2e.sh create`, then
  `sre-e2e.sh sme -s choreo-runtime -k choreo-runtime-team` (rosters L1-L3 on
  the live SME window, publishes the alert on `sre-events`, follows the ladder;
  mount a copy of the config with a shorter `sme.timing.interval` through
  `ESCALATION_CONFIG_FILE` to watch it climb in minutes).
- **Known edge**: the escalation and `incident.created` come on different
  topics. If the alert is handled first (a restart or backlog), the SRE chain
  starts after the escalation and runs until an assignment stops it.

### Case Paging from customer cases (`cases.go`)

The rules are `task-call-alert-flow/Case Paging Rules.xlsx` (agreed 2026-10-07),
which is the source of truth; change a rule there first. Both engines read the
case events from the shared topic (`case.created`, `case.severity_changed`,
`case.assigned`, `case.comment_added`, `case.status_changed`); the ladder state
is keyed by the case id, and `Trigger.Record` is `case`.

- **Start**: `case.created` for a support case (`caseType` CASE; other types are
  never paged). S0 pages CRE and SRE, S1-S4 CRE only; which severities CRE pages
  is `cre.trigger.priorities` (the local file leaves S4 out: paging S4 is
  optional).
- **Severity change**: any change stops the running chain and starts a new one
  for the new severity, from the first tier, even after acknowledgement. A
  severity a ladder does not page stops its chain (SRE below S0; S4 while it is
  off). The event has no timestamp, so the chain runs from now, and a
  redelivery is recognised by the chain already running at that severity.
- **Stop**: CRE needs an engineer assigned AND that engineer's public comment
  (`acknowledgement.requireBoth`). SRE on an S0 case stops when any engineer is
  assigned, or -- on a case already assigned when it became S0 -- on the
  assignee's public comment. Only gestures after the chain started count. A
  customer's comment and a work note never stop paging. A support engineer's
  comment before they are assigned is remembered and counts once they are. A
  closed case (`case.status_changed` "Closed", or a resolved/cancelled label)
  stops both.
- **SRE team**: an S0 case's SRE ladder pages its account's SRE team
  (`sreTeamName` on `case.created`/`case.severity_changed`, entity-service's
  `account.sre_team_id`), carried as `RoutingContext.SRETeam`; `Trigger.Team`
  stays the CRE team. Who is called (`ownSRETeam`, the rota), the card spaces
  (`chatTeams`), the team's channel (`channelFor`) and the closing replies all
  follow it. The name must resolve, through `sre.teams.aliases`, to a team in
  `sre.teams.abts` (and to a `sre.teamChats` key for its own space); one that
  does not, or a case with none, pages every team on `defaultRota` and posts
  to `teamlessChats`, as before. Until 2026-10-26 every S0 case was paged that
  way. Both fields are new and this service decodes strictly: deploy it before
  the entity-service that sends them.
- **Assignee**: the starting events carry none, so the current assignee is kept
  in Redis from `case.assigned` (`incident:escalation:case:assignee:<caseId>`,
  shared by both ladders).
- **Summary**: written onto the case as a work note, `POST /cases/{id}/comments`
  `{type: work_note, actorEmail}`. The actor is `INCIDENT_ESCALATION_NOTE_ACTOR`
  (default `system-m2m@wso2.com`), and this service's client id must be in
  entity-service's `M2M_CLIENT_IDS`. A failure is logged, never retried.
- The voice message and card say "Assign the case to yourself and add a public
  comment to stop further calls"; the card links to `/cases/<id>`.

**Configuration** is the file's `sre:` section, the same shape as `cre:` plus
`timing` and `teams.abts`/`teams.aliases`; who climbs it is `DefaultRouting`, in code. Each
ladder's own keys are refused on the other (a `timing:` under `cre:` is an
error, not ignored), and a team in both `cre.teams.abts` and `sre.teams.abts` is
an error -- its lead would still be called on every CRE ladder's
`all_team_leads` rung.

**Numbers**: the rota holds none. `INCIDENT_ESCALATION_PHONES` (JSON, e-mail ->
E.164) or `INCIDENT_ESCALATION_TEST_CALL_TO` (every call to one number) fill
them through `TeamScheduleResolver.WithPhoneBook`. A chat-only ladder needs
neither. The phone book is a fallback: a valid CSM profile number replaces its
entry (`ProfilePhoneResolver`); `TEST_CALL_TO` is never replaced, and the
roster resolver applies it too (`RosterResolver.WithTestCallTo`).

**Where alert-born incidents come from.** `sre-alert-core-service` creates the
CSM incident (`engine.deliverAndPersist` -> `notify.NotifyCSM` -> `POST
/incidents` on csm-integration-service, which passes the body through to
entity-service). entity-service publishes `incident.created` through
`publishIncidentCreatedEvent` on every data source, plain `postgres` included,
once the insert commits; the event is enriched from the stored incident, so it
carries the team, priority and contact type routing reads. The create request
sends `contactType` when the alert's source has one (AZURE, SITE_247,
SENTINEL), which the `monitoring` rule matches. It sends no assignment group:
entity-service assigns the incident to its service's support group (#2353), and
that group's family is what the `sre-abt-team` rule matches. The local
end-to-end tools (`sre-e2e.sh`, `trigger-escalation.sh`) still publish the
event themselves, through `entity-service/internal/tools/publishincident`, to
drive a ladder without creating an incident.

**Incident topic.** With `INCIDENT_EVENT_HUB_TOPIC` set (e.g. `sre-events`), entity-service publishes every `incident.*` event there instead of the shared topic, and the SRE ladder adds a consumer on it (group `PAGING_SRE_INCIDENT_CONSUMER_GROUP`, default `csm-notification-service-paging-sre-incidents`; a new group, so it takes the Case Paging name, while the existing groups keep theirs because renaming a group drops its offsets) while keeping its shared-topic consumer for customer cases (a case S0 pages SRE). The CRE ladder never reads it. All of an incident's events move together, so its stop signals arrive where its trigger did. Roll out here first, then on entity-service; reading both topics through the switch is harmless (create-if-absent). The dispatcher must keep seeing `incident.created` (its default on-call call): when `SRE_EVENT_HUB_TOPIC` is the same topic the `sre-events` consumer (`HandleShared`) already reads it, otherwise `incidentDispatchConsumer` starts a dispatcher consumer on it (group `INCIDENT_CONSUMER_GROUP`, default `<EVENT_HUB_CONSUMER_GROUP>-incidents`, dead-lettering to the case DLQ where these records went before).

**Wiring** (`cmd/server/main.go`): inside the Redis block, started only when
the ladder has somebody to resolve rungs from (`escalationStartProblem`): the
Team Schedule, with `INCIDENT_ESCALATION_RESOLVER=team-schedule` and
`CUSTOMER_ENTITY_BASE_URL` set, or else a non-empty
`INCIDENT_ESCALATION_ROSTER` — a ladder that can never call anyone is worse

only when it is what the ladder reads (it used to be required in both modes);
one that is set but does not parse stops the engine either way. Shares `CALL_SENDING_ENABLED` with the dispatcher's call. Startup
warns when `INCIDENT_DEFAULT_CALL_TO` is also set: the dispatcher's single
immediate call predates the ladder and is **not** in the specification (its
initial reaction is the Chat alert and an email); unset it once the ladder
covers an environment, or an incident gets both.

**On leave** (`cre.onLeave`, `sre.onLeave`, `sme.onLeave`: `skip`, the
default, or `call`). Someone who holds a rung but is on leave that day is left
out under `skip` -- the rung goes to whoever else holds it, or the ladder
climbs past -- and rung under `call`, after anyone available on the same tier
(`preferAvailable`). The rota rungs (CRE rota pairs, SRE tiers, SME tiers) ask
`GET /team-schedule/on-duty` for people on leave only under `call`
(`includeOnLeave=true`; they come back marked `onLeave`). The CRE responder,
lead and head rungs come from membership, which knows nothing of leave, so
under `skip` they are filtered by `POST /team-schedule/absences/search` for the
incident's date in IST (`withoutAway`; a span that moves someone to another
team is work, not leave); if that read fails the rung is rung as it is. The
engine stamps the ladder's setting on `RoutingContext.CallOnLeave`. Before
2026-10-09 the CRE membership rungs rang people on leave regardless.

**Phone numbers** come from each person's own CSM Portal profile. The Team
Schedule names who to call but holds no numbers, and a call plan drops anyone
without one (`NO_NUMBER`). `ProfilePhoneResolver` wraps whichever resolver is
in use and fills a missing number. **CSM answers first**: one batched
`GET /team-schedule/paging-contacts?emails=` per rung (3 s) returns, per person,
`dialPhone` -- the number on their profile (`"user".phone`, which the portals
write since the "store the user's phone" change) when it is E.164, else the
paging-only number a lead or admin stored (`paging_contact`) -- and `dialSource`
(`profile` / `paging`). **Asgardeo is the fallback** for people CSM has no
callable number for (`scim.Client.MobileNumber` reads the `mobile` phone the
portal's profile dialog writes there), once per person per two minutes, 3 s per
lookup; it exists until `"user".phone` has been filled from Asgardeo, and
`PAGING_PHONE_SCIM_FALLBACK=false` turns it off (paging then never calls
Asgardeo; the onboarding flow keeps its own use of `SCIM_BASE_URL`). The CSM
portal backend reads the same variable for the Case Paging readiness strip. A CSM lookup that fails falls back to Asgardeo for
everyone. An older entity-service sends only the paging-only number (no
`dialSource`); it is then used after the Asgardeo profile, as before. Order
(first match wins): `INCIDENT_ESCALATION_TEST_CALL_TO` (`Recipient.PhoneFixed`,
never replaced), then the person's **CSM profile number**, then a number they
already carry (the phone book, `paging-alert.yaml`, the roster), then their
alert-only number in CSM, then Asgardeo's. Until 2026-10-18 the configured
number came first and an old phone-book entry beat a corrected profile. A lookup that fails, times out or is not E.164 leaves that one
person `NO_NUMBER` and never fails the tier. `phones.source: none` turns it all
off. Applies to the CRE and SRE ladders and the SME page alike. Nothing is
persisted outside the plan, and the number is never logged.

**Test calls** (`testcall.go`): `paging.test_call_requested` (entity-service,
on the main topic, `entityId` = userId) reaches `dispatch` and is handed to
`paging.TestCaller` (wired in `main.go` when Redis and `CUSTOMER_ENTITY_BASE_URL`
are set). One request per person per 2 minutes (Redis SETNX); the file's
`testCall` section (`enabled`, default on; `allowedNumbers`, empty = any) and
`CALL_SENDING_ENABLED` gate it, and a refusal is reported `failed`. One short
call is placed and the event acknowledged; a goroutine on the server context
asks Twilio for the call's status (`TwilioClient.GetCall`) after 60 s, then
every 20 s up to 3 min (still in progress at the end is `completed`, anything
else `no-answer`), and PUTs `completed`/`no-answer`/`busy`/`failed` to
`/team-schedule/paging-contacts/{userId}/test-result` (three attempts). A
restart during the wait leaves the status `pending` (accepted for phase 1).

**Call outcomes** (`call_outcome.go`, `ALERTING_CALL_OUTCOME_CHECK`, default
on, `false` turns it off): a rung's call is logged `ALERT TRIGGERED ...
status=queued`, which only says Twilio took it. Unless the flag is `false`,
`Engine.WithCallOutcomeWatcher` gives
both engines one `CallOutcomeWatcher`, and every call `placeVia` places (a
`ChannelCall` delivery with a sid) is asked of Twilio the same way a test call
is -- after 60 s, every 20 s, up to 3 min -- then logged once as
`escalation: call outcome` with `callSid`, `result`
(`completed`/`no-answer`/`busy`/`failed`/`canceled`, or `unresolved` with the
last `twilioStatus`), at info when answered and warn otherwise. Logging only:
the ladder never reads it. Not a `StatusCallback` on purpose -- that needs a
public route this service does not have. `completed` means Twilio connected
the call; a voicemail pickup is `completed` too. A restart during the wait
loses that line.

**People in logs are ids.** Every paging log line names a person as
`recipientId` = `Recipient.LogID()`: the CSM user id the Team Schedule gave
(`Recipient.UserID`, filled from on-duty assignments and team members), else
`e:` + 12 hex of the SHA-256 of the lower-cased email (heads and leads named in
configuration have no user id), never a name, email or number. Chat cards and
the execution summary still name people; they are for people to read.

**Calls switch on when the ABT lead pool is verified.** Before any call is
placed, `applySafety` asks the resolver for its whole lead pool
(`LeadPoolResolver`; every `lead` on the ABT teams, numbers filled from
profiles) and, if any lead has no E.164 number, holds the plan's calls
(`safety.callWithoutVerifiedLeads: true` overrides). Without this, a lead tier
with no numbers is skipped as `NO_NUMBER` and an unanswered incident of any
priority climbs from LEVEL_0 straight to the heads. Separately, the heads
(LEVEL_3/LEVEL_4) are held when no call on LEVEL_0..LEVEL_2 has a number
(`safety.callHeadsWithoutLowerTiers: true` overrides).

Both holds are setup, not incident outcomes, so they are **logged only, never
written to the work note**: a call-only ladder held by the gate schedules
nothing and writes no note (`Plan.CallsHeld`); with `both`, entries keep their
chat cards and only the call is skipped (`PlannedCall.HoldCall`). A resolver
without a lead pool (the hand-maintained roster, whose entries carry numbers)
is not checked. To keep calls off entirely regardless, use `channel: chat` or
`log`.

## Frustration detection (`case.comment_added`)

`dispatch.checkFrustration`, called from the top of `handleCommentAdded` for every `case.comment_added` event, sends a new comment to the existing `ai-escalate-comment-detector` service (a separate deployable, not part of this repo) for an OpenAI-backed frustration analysis, and posts a Chat alert when that service's own configured threshold is crossed. Entirely optional and best-effort: unset `ESCALATION_DETECTOR_BASE_URL` means the step is a no-op (no detector configured, so `d.frustrationDetector` stays `nil`), and any failure along the way (the role lookup, the detector call, the Chat post) is logged and swallowed, never propagated as the record's own error — the comment's own email reaction, driven entirely by the code below this call, is the primary thing this handler exists for.

- **`internal/escalation`** (`client.go`) is a minimal client for the detector's single-comment `POST /escalations` endpoint — not `/contexts` (the multi-comment endpoint that service's own code uses to post its own, unrelated Google Chat alert to its own configured space; this client never calls it, so that code path and that space are never involved here). `DetectEscalation(ctx, caseID, caseNumber, product, comment)` fills `commentPostedTimestampInSN`/`snCustomerServiceCaseSysId` with best-effort placeholder values (the current time, an empty string) — required fields on the detector's own `EscalationRequest` type that this client has no real source for and that service only uses for echoing back in its response/its own debug logging, never for the analysis itself. Authenticated via OAuth2 client credentials (`internal/oauthhttp`), sharing the same `OAUTH2_CLIENT_ID`/`OAUTH2_CLIENT_SECRET`/`OAUTH2_TOKEN_URL` credentials the email and customer entity clients already use — only `ESCALATION_DETECTOR_BASE_URL`/`ESCALATION_DETECTOR_SCOPES` are specific to this client. The response read is bounded (`io.LimitReader`, 1 MiB) so a misbehaving/misconfigured detector can't have this buffer an unbounded body in memory on the Kafka consumer path. `Result.ShouldAlert` is the detector's own `isEmailTrigger` (crossed *that* service's configured threshold) — callers gate an actual Chat alert on this, not `IsFrustrated` alone, which is just the model's raw judgment call before being measured against a bar.
- **Author classification (`recipientlinks.Resolver.IsCustomer`)** — `checkFrustration` only ever sends a comment to the detector when its author resolves to a customer: `events.CommentAddedPayload.AuthorEmail` (the comment author's own resolved email, added alongside `Product`/`Team`/`IsEvaluationAccount`/`ProjectOnboardingStatus` specifically for this feature) is classified the same role-then-domain-fallback way `linkFor` already classifies a *recipient's* email for portal-link routing (see "Event-driven notifications" above) — reusing that exact mechanism rather than inventing a second one. An internal/CSM-authored comment, or a payload with no resolved author email at all, skips the detector call entirely — no API cost, no Chat alert.
- **Chat routing (`SendFrustrationAlert`, `chataudience.Resolve`)** — once `ShouldAlert` is true, the alert routes exactly like an SLA breach alert: team-first (the payload's own `Team`), falling back to `"Incident Monitor"`, plus the `Evaluation`/`Onboarding`/`Americas`/weekend overlays — not the fixed-`"Incident Monitor"`-only posture `case.created`/`case.acknowledged`/`case.severity_changed` use. `IsEvaluationAccount`/`ProjectOnboardingStatus` are Postgres-only facts on the publisher's side (entity-service's `CaseRepository.ProjectOnboardingInfo`) and are simply their zero value on a pure-ServiceNow deployment with no Postgres pool — `chataudience.Resolve` treats that the same as "not an evaluation account, no onboarding status," not an error. A failure sending to one resolved audience doesn't stop the others (`errors.Join`), each logged individually with its own `audience` attribute.
- **Idempotency (`checkFrustration`'s own `recordBaseKey(record)+"/frustration"` claim)** — this call sits *before* the email-sending code in `handleCommentAdded`, whose own return value (driven by the email path) is what `eventbus.Consumer` retries on. Without its own tracking, a record retried solely because the email send kept failing would redo frustration detection (a second OpenAI call) and repost the Chat alert on every attempt — the exact repeated-Chat-alert-on-retry-and-DLQ-hand-off failure mode this file's own `sendPerGroup`/`forgetEmailGroups`/chatKey mechanisms elsewhere already exist to prevent. Unlike the single-channel `chatKey` shape `handleCaseAcknowledged`/`handleIncidentCreated` use (forget on success *or* failure, safe there only because their own success/failure directly determines whether the whole function gets retried at all), this claim is deliberately **not** released on success — only on `record.NoMoreRetries` (no further attempt coming, ever, on any topic), registered as a `defer` *before* the `claim` call itself: on the genuinely final retry, `claim` can return `false` (an earlier attempt still holds the key) and return early, and without the `defer` already registered by that point, the key would leak in `d.done` forever — a real bug caught by this feature's own regression test (`TestDispatcher_Handle_CommentAdded_FrustrationDetection_NotRepeatedWhenEmailRetries`) before the ordering was fixed.

## Commands

```bash
go vet ./...              # vet
go test -race ./...       # vet + race-detector tests
go build -o server ./cmd/server   # compile
govulncheck ./...         # checks dependencies against Go's official vulnerability database
```

`govulncheck` does call-graph analysis, not just "is a vulnerable package present" — it only flags a vulnerability if your code's own call graph actually reaches the vulnerable function, so a clean result means more than a plain dependency-list scan would. If it errors with `package requires newer Go version go1.26 (application built with go1.25)`, the installed `govulncheck` binary itself was built with an older Go than this module's `go 1.26.0` directive — reinstall it with a toolchain that matches or exceeds that, e.g. from a directory using that toolchain, or `GOTOOLCHAIN=go1.26.5 go install golang.org/x/vuln/cmd/govulncheck@latest` (adjust the patch version to whatever's cached under `$(go env GOPATH)/pkg/mod/golang.org/toolchain@v0.0.1-go1.26.*`), then invoke it the same way if it still misdetects its own Go version.

## Adding a new channel

1. **Client** (`internal/notifications/<channel>.go`) — add `<Name>Config`/`<Name>Client`/`Send<Thing>` following `email.go`'s or `googlechat.go`'s shape, whichever auth scheme is closer
2. **`cmd/server/main.go`** — construct the new client from env vars (use `os.Getenv`, not `mustEnv`, unless the channel truly must be configured for the service to start), and pass it into `dispatch.NewDispatcher`
3. **`dispatch.Dispatcher`** — add a field for the new client, and call it from whichever `handle<Type>` method(s) should trigger it (a new field on an existing event's payload if it needs new caller-supplied data, or a new event type entirely — see "Adding a new event type")
4. **Payload fields**, if the new channel needs new ones on an existing event — add them to the relevant `*Payload` struct in `internal/events/events.go`; there's no `openapi.yaml` schema for these anymore (it only documents `/health` now — see "Event-driven notifications"), so that struct's own doc comments are the source of truth for the wire shape
5. **Tests** — add dispatch tests for the new channel's send path, following the existing per-type cases in `dispatch_test.go`

## Security

- **Never commit secrets** — client IDs/secrets, webhook URLs, service URLs with credentials, and the Event Hub connection string must not appear in source code or config files; use environment variables
- **No sensitive data in logs** — log only IDs and error summaries; this includes not logging the Event Hub connection string or full record values that might carry PII — every `case.*` payload's `recipients` array is real email addresses now (not a fixed test list), so this applies more directly than before, and `project_contact.invited`'s payload is one real customer contact's email and name (`handleProjectContactInvited` logs `membershipSfId`/`contactSfId`/`projectKey`, never the email). `internal/recipientlinks`'s role-lookup warnings are deliberately keyed on `caseID`/`roles`/`userType`, never the recipient's email — this was a real CodeRabbit-caught PII finding when the code lived in csm-portal-backend (fixed in `ea84cdf2e`); it must not be reintroduced now that the code has moved
- **No app-level inbound auth** — this is intentional (see above), not an oversight; don't "fix" it by bolting on JWT validation without confirming this service is meant to have an inbound API surface again
- **Input validation** — `events.Validate`, called from `dispatch.Dispatcher.Handle`, is now the only validation boundary this service has (no HTTP handler upstream anymore) — keep rejecting unexpected input there (JSON structure, required fields) rather than letting a malformed record reach a notification client
- **TwiML injection** — `MakeCall`'s spoken message is caller-supplied text, not trusted markup. `sayTwiML` (`twilio.go`) builds the `<Say>` document by `encoding/xml`-marshaling a typed struct (`twimlResponse`/`twimlSay`), never raw string concatenation — a message containing TwiML-shaped text (e.g. `</Say><Redirect>...`) must render as literal spoken text, not inject a different verb. `Voice`/`Language` go through the same struct as `xml:"...,attr"` fields, so they get correct attribute escaping too, even though today they're only ever operator-supplied config, not request input. Keep using `encoding/xml` struct marshaling (not string concatenation) for any future TwiML-building code in this package
- **Security fixes in PRs** — describe security-related changes in neutral functional terms only, not called out as security fixes in the title/description
- **Run `govulncheck ./...` on dependency changes** — alongside `gosec` (which only analyzes this repo's own code), run this whenever `go.mod`/`go.sum` changes (a new dependency, or a version bump) to catch known vulnerabilities in the dependency tree itself. It must report 0 vulnerabilities reachable from our code before opening a PR; a vulnerability present in a dependency but not reachable through anything we call is worth noting in the PR but isn't a blocker — see `internal/eventbus`'s `klauspost/compress` bump for a real precedent (GO-2026-5841, upgraded proactively even though unreachable, since the fix was free)
